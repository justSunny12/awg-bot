# AmneziaWG Telegram-бот

Управление самостоятельно развёрнутым AmneziaWG VPN через Telegram. Роли
админ/пользователь/друг, инвайты, периоды подписки с блокировкой трафика при истечении,
накопительная статистика, карантин чужих пиров, условная маршрутизация
(российский IP для российских сервисов), локальный мониторинг железа хоста,
самообновление.

Пиры заводит **только бот** — он единственный источник истины по составу
конфига. Пользователи подключаются приложением Amnezia (формат `vpn://` заморожен),
но серверная сторона приложения не поддерживается: всё, что появилось в
`awg0.conf` мимо бота, считается аномалией и уходит в карантин.

Этот файл — обзор проекта и архитектуры. Дальше:

- **[docs/README-bot.md](docs/README-bot.md) §6c–6d** — условная маршрутизация и агент шлюза целиком
- **[docs/RELEASING.md](docs/RELEASING.md)** — нумерация версий и порядок выпуска

## Архитектура

Бот co-located с awg на одном хосте и управляет им локально. Единственный внешний
канал — Telegram Bot API.

AmneziaWG установлен на самом хосте (`awg`, `awg-quick`), бот вызывает его
команды напрямую; параметры интерфейса — раздел `awg:` в `conf/app.yaml`.

```
┌───────────────────────────────────────────────────────────┐
│  Хост (AmneziaWG + бот на одном хосте)                    │
│                                                           │
│  awg-bot (systemd)                                        │
│   • Telegram Bot API   ← единственный внешний канал        │
│   • SQLite (состояние)                                    │
│   • APScheduler   опрос трафика, мониторинг, живость шлюза │
│   • inotify-вотчдог  awg0.conf                             │
│        │                                                  │
│        ▼  awg / awg-quick                                 │
│  AmneziaWG: awg0.conf, iptables-блокировки по адресам      │
│                                                           │
│  метрики CPU/RAM/диск — бот читает сам: /proc + statvfs    │
└───────────────────────────────────────────────────────────┘
```

Почему только co-located: управление awg локальное (по сети до него бот не
ходит), а сам бот выходит в Telegram через тот же хост. Разносить бота на
отдельный хост смысла нет — в РФ при заблокированном Telegram такой бот терял
бы и доступ к Telegram, и к awg, то есть не закрывал бы ни одной задачи. Метрики
железа снимаются локально, без агентов и сетевых приёмников.

## Устройства и роли

**Устройство** = пир AmneziaWG. Тип определяется по факту (без ярлыков-прокладок):

- **управляемое** (`is_managed`) — создано ботом, приватный ключ есть: может
  выдавать ссылку/QR/файл, передавать другу, менять лимит.
- **без ключа** — пир, найденный в конфиге сервера мимо бота. Реконсиляция кладёт
  его в карантин («Устройства без профиля») и поднимает тревогу админу со звуком.
  Помечается суффиксом `*`. Ключа у бота нет и взять его неоткуда, поэтому
  выдать ссылку нельзя: только переименовать, привязать к профилю или удалить.

**Роли** (проставляет middleware по tg_id):

- **admin** (из конфига) — полный доступ ко всему.
- **client** — свой профиль: свои устройства (выдача конфигов, переименование,
  лимиты), передача устройства другу. Не может трогать чужое.
- **guest** (гость) — держатель переданных ему устройств без своей подписки:
  управляет только ими, принимает устройства от одного владельца;
  переименование недоступно (README-bot §6e).

**Имена живут только в БД бота** — сервер про них не знает, в конфиге пира их
нет. Синхронизировать не с чем и не с кем.

**Первое устройство админа заводит сам бот** при первом старте: без него у
администратора не было бы доступа к боту, а созданный руками пир уехал бы в
карантин. Ссылка приходит в Telegram отдельным сообщением с кнопкой «Скрыть».

## Условная маршрутизация

Российский IP для российских сервисов — банков, госуслуг, маркетплейсов, которые
не пускают с зарубежного адреса. Помеченный трафик уходит линк-туннелем на шлюз
с российским адресом (например Raspberry Pi в локальной сети), остальное
выходит обычным путём с ВПС.

**На шлюз идёт только то, что в наборе.** Набор перечисляет российские сервисы;
всё прочее — заграница по умолчанию. Отсюда три свойства: канал шлюза не
становится общим потолком по полосе, пустой набор безопасен (равносилен
выключенной функции), а отказ шлюза мягкий — «сервис ругается на адрес», а не
«нет интернета».

**Конфиги устройств при этом не меняются** — режим это серверное состояние, а не
отдельные учётные данные. Выданные `vpn://` продолжают работать, переключение
мгновенно и обратимо.

Флаг двухслойный: админ разрешает функцию профилю, пользователь включает её у
себя. Базовый список бот качает сам; сверх него у каждого профиля свой личный.
Живость шлюза меряется проходимостью — уликами счётчиков линка и TCP-зондом
через него, — а не возрастом хендшейка; решает скользящее окно замеров
(`routing.failover.window_samples`, порог `min_availability`). Шлюзов может
быть два: второй ждёт в резерве, автомат переключения решает по зонду с ВПС.

**Агент шлюза.** На шлюзе работает тот же код в роли `gateway` — свой бот со
своим токеном: монитор здоровья, обвязка nft, линк и аплинк, VPN-транзит для
локальной сети за шлюзом. С ВПС его связывает **управляющий канал** внутри
линка — канал состояния, не исполнения: соединение ставит шлюз, он отдаёт
снимок фактов, а сервер шлёт ему данные — документ конфигурации слота
(настройки обвязки, конфиг линка и аплинка, почта, токен бота),
фиды, роль слота; обратно агент присылает свои настройки, и сервер держит
их в своём бэкапе — у шлюза своих копий нет. Конфиги WireGuard из канала принимаются белым списком
ключей, новые ключи линка и аплинк ставятся только после «Применить» человека
в чате бота шлюза. Код по каналу не ездит: шлюз ставится **одной командой
из бота сервера AWG** — строкой установки с токеном подключения, а в чат
бота сервера вводят код подтверждения с экрана шлюза; до верного кода линк
нового шлюза в карантине. Дальше код агента приходит обновлением по команде
сервера.

**Адреса в туннеле.** Локальные сети за шлюзами видны с устройств админа и из
сетей других шлюзов не по настоящим адресам, а по постоянным двойникам в
служебном пространстве сервера (`routing.lan_space`, по умолчанию
`10.240.0.0/12`: своя /16 на слот, две последние цифры адреса те же —
`192.168.1.10` за первым шлюзом это `10.240.1.10`). Переводит только ВПС
(таблица `inet awg_lan_map`), поэтому одинаковые подсети за разными шлюзами
друг другу не мешают, а на роутерах маршрутов не нужно. Связь подсетей —
часть VPN-транзита: слоты с ним связаны всегда.

Пока `routing.gw_interface` пуст, функция спит целиком: UI её не показывает,
реконсиляция не трогает систему. Это же и аварийный рубильник.

Обвяз ставится скриптами: `install/routing-host-setup.sh` (ВПС),
`install/routing-link-setup.sh` (линк до шлюза: ключи, смена ключей, линк на
ключах команды подключения), `install/routing-gw-setup.sh` (шлюз). Диагностика —
`awg-bot routing-doctor`, она называет отказавший слой, а не просто «не
работает».

## Установка

Поставка — один архив, установщик внутри. На чистом хосте — одна команда:

```bash
curl -fsSL https://raw.githubusercontent.com/<repo>/main/install/awg-bot-install.sh | sudo bash
```

Вопрос ровно один — токен бота; кто админ, установщик выясняет одноразовым
кодом в чате. Всё остальное он делает сам: ставит AmneziaWG версии, прибитой к
поставке, создаёт сервер с нуля, разворачивает код в `/opt/awg-bot`, venv,
конфиг, секреты, systemd-сервис, спрашивает одной строкой про файервол и
печатает конфигурацию первого устройства в терминал. За собой убирает архив и
временный каталог. Дальше управление — командой `awg-bot`:

```
reconfigure  update  backup  restore  uninstall
status  start  stop  restart  logs
firewall …              файервол хоста (таблица awg_bot_guard)
ssh …                   шлюз: порт SSH и фильтр снаружи
routing-doctor          диагностика условной маршрутизации по слоям
lan …                   шлюз: свои списки VPN-транзита, обновление фидов
gw-kit --stdout         поставка для шлюза без доступа к GitHub (без ключей и токенов)
join <команда>|--status шлюз: подключиться к серверу AWG командой из его бота
awg status|install|reload|prune|plan   ядро AmneziaWG версии, прибитой к поставке
first-device            конфигурация первого устройства админа в терминал
resolver …              свой резолвер пользователей; resolver admin … — резолвер админа
```
Полный список — `awg-bot` без аргументов.

**Шлюз** ставится не этой строкой, а той, что пришлёт бот сервера AWG
(«🛰 Шлюзы» → «🛰 Подключить шлюз»): `curl … | sudo bash -s -- --join AWGJ1.…`
ставит ровно выпуск, названный сервером, и печатает код подтверждения — его
вводят в чат бота сервера. Эта строка с токеном попадёт в журнал sudo
(`auth.log`) и в историю оболочки — это не страшно: без кода, введённого в бот, токен бесполезен,
а через час он умирает сам; дальше по цепочке (установщик → `awg-bot` →
`tools.join`) токен идёт только окружением, не аргументом. Шлюзу без доступа к GitHub поставку собирает
`awg-bot gw-kit --stdout` на сервере (`docs/README-bot.md` §6d).

Топология не спрашивается: внешний адрес определяется сам (`ip route get`, а за
NAT — внешним запросом), порт и подсеть берутся у созданного сервера либо у
живого, если он уже стоял. Файервол — один вопрос в конце установки, дальше он
живёт в боте (⚙️ Настройки → 🛡 SSH-доступ).

**Самообновление.** Бот раз в сутки и при старте смотрит релизы репозитория,
выбирает цель — последний релиз, адресованный своей роли, — и предлагает
обновиться кнопкой: качает ассет, сверяет sha256 и зовёт `awg-bot update`.
Условия цели — минимум, с которого на неё прыгают напрямую, и версия другой
стороны (серверу — шлюзы, агенту — сервер) — лежат в метаданных релиза
(второй ассет `awg-bot-release.json`): релиз, которому другая сторона ещё не
готова, ждёт её, а не ставится. Вторая половина обновления исполняется уже
новым кодом — иначе правка в самом скрипте не смогла бы применить себя;
отказ до старта сервиса возвращает и прежний код, и прежнее окружение Python.

**Самопроверка на старте** (`runtime/preflight.py`) отделяет фатальное от
замечаний: без обязательных секретов и топологии бот не поднимется, а всё
остальное — недоступный IMAP, неподнявшийся шлюз, нечитаемый конфиг — уезжает
админу отдельным сообщением, не мешая работе.

## Приостановка подписки («в отпуск»)

Пауза **замораживает время**: `period_end` сдвигается вперёд на зарезервированные
дни, VPN-доступ отключается (PAUSED-каскад на пользователя и устройства). Дни паузы —
**счёт у профиля** (`conf/pause.yaml`): годовая подписка получает
`pause_max_total_days` (28) при создании на год и при каждом продлении на год,
даже несвоевременном, накопление до двух таких; ежемесячная —
`monthly_pause_days` (2) за каждый своевременно оплаченный месяц (создание и
продление, пока подписка не истекла и без отсрочки), накопление до 12 таких;
смена типа переносит остаток в пределах максимума нового типа; день/неделя
счёт не пополняют, у бессрочной он всегда ноль. Ни «максимума за один
вход», ни ограничения остатком подписки нет. Списание по факту с округлением
вверх: 1 минута паузы = 1 день; неиспользованный остаток при досрочном выходе
возвращается в `period_end` и на счёт. Кнопка главного меню называется
«⚙️ Управлять подпиской», только пока есть рычаг — войти в паузу или снять
свою; иначе «📝 Моя подписка».

**Вход** (пользователь, «Управлять подпиской»): выбор длительности кнопками
7/14/«весь остаток» (недоступные пресеты скрыты, дубли не показываются;
«✏️ Другое» — ввод числа 1..доступного, скрыто, когда вводить нечего) →
предупреждение о тупике (VPN выключится, выйти досрочно можно только через
бота; если Telegram доступен лишь через этот VPN — сам не выйдешь) →
подтверждение. Кнопка входа не прячется при нулевом остатке — по нажатию
объясняется: дни на счету закончились. На экране подписки — счёт
`Приостановка подписки: доступно N дней` с правилами начисления под ним; дни
не сгорают ни по какому сроку.

**Три выхода из паузы:**

1. **Кнопка «Возобновить»** в боте (пользователь) — в любой момент.
2. **Админ**: в карточке пользователя при активной паузе самой верхней кнопкой
   «▶️ Вывести из приостановки» — тот же пересчёт дней. Запасной выход, если
   пользователь заперся.
3. **Аварийный e-mail-выход** (опционально): при входе в паузу пользователю выдаётся
   одноразовый код (8 симв., алфавит без похожих 0/O/1/l). Заперевшись без
   Telegram, пользователь шлёт письмо с кодом **в теме** на настроенный адрес — бот
   опрашивает IMAP-ящик исходяще (портов на хосте не открываем), находит код,
   снимает паузу и отвечает «Код принят, доступ восстановлен». Свойства:
   `From` не является аутентификацией (спуфится) — секрет только код; тело
   письма не читается вообще; невалидный код игнорируется молча (письмо
   помечается прочитанным, ответа нет); код одноразовый и живёт только пока
   активна пауза. Настройка — из чата: «⚙️ Настройки → ✉️ E-mail →
   ✉️ Подключить ящик» (для gmail.com, icloud.com и yandex.ru серверы
   подставляются сами), затем тумблер «Аварийный выход», адрес для кода и
   интервал опроса (не менее 60 сек). Логин и пароль ящика — в БД, серверы —
   `conf/email.yaml`; ящик не подключён — фича спит.

Авто-выход по истечении зарезервированного срока делает watchdog
(`check_pauses`); бессрочную админскую паузу (admin_open) снимает только админ.

## Объявления

Админ выбирает профили-адресаты и режим. **Простое** объявление уходит
владельцам отмеченных профилей и тем, кому они раздали устройства: их это
касается напрямую, а узнать иначе неоткуда. **С продлением подписки** — только
владельцам: перед отправкой подписка каждого продлевается на заданное число
дней (активной — конец периода + N, истёкшей — сегодня + N, бессрочной —
ничего), и к тексту у каждого своя шапка с датами. Дальше одинаково: ввод
текста (можно с картинками), превью с проверкой разметки, подтверждение, отчёт
о доставке.

## Модель конфигурации и безопасности

- **Топология и правила — в yaml** (`/etc/awg-bot/conf`): источник истины, генерит
  установщик, правится руками на холодную, переживает обновление кода. Часть
  ключей горячие — читаются в точке использования и применяются без рестарта.
- **Секреты — только в env** (`/etc/awg-bot/env`, `600`). Недостающие обязательные
  ключи ловит `config.validate()` при старте с адресным сообщением.
- **Крипто-материал AWG** (ключ сервера, psk, обфускация awg-протокола, порт)
  читается **live с сервера** и кэшируется — второго источника истины нет.
  Публичный ключ выводится из приватного, а не читается отдельным файлом:
  файл жил своей жизнью и мог разойтись с ключом молча.
- **Приватные ключи управляемых устройств** живут в БД (`/var/lib/awg-bot`);
  единственная копия вне сервера — **шифрованный бэкап** сервера AWG (SecretBox,
  ключ — из ключевой фразы); без фразы бэкапов нет, открытых не бывает.
- **Пер-пирный SSH-фильтр**: SSH к хосту из туннеля разрешён только с адресов
  админских устройств. Точка врезки — INPUT хоста (пакет на собственный адрес
  транзитом не идёт).
  Проверять фильтр нужно **по счётчикам пакетов**: набор правил может выглядеть
  безупречно и стоять мимо потока.
- **Пользователь «Администратор»** неудаляем и не ограничивается (блок/лимит/пауза
  недоступны, defense-in-depth в сервисе).
- **Файервол — одна точка**: nft-таблица `awg_bot_guard`, которую ведёт бот
  (SSH-вайтлист, изоляция пиров, NAT пользователей); секреты в env `600`.
- **Время — в поясе хоста, с меткой.** Пояс показа — пояс сервера (у агента —
  шлюза), как в `timedatectl`; ключ `timezone` в `app.yaml` — необязательное
  переопределение. У каждого времени в сообщениях — смещение: «истекает 12.10
  18:00 (UTC+5)», «обновлено 15.10 08:08:14 (UTC+5) 🔄»; у дат и «5 мин назад» —
  нет. Хранение от пояса показа не зависит: всё в БД и состоянии — ISO-8601 со
  смещением UTC+3 («+03:00»), читается любое смещение.

## Структура (пакет по слоям)

Направление зависимостей: `core ← util ← infra ← domain ← bot ← runtime`,
`config` доступен всем. Запуск — `python -m awgbot` (обёртка `__main__.py`);
форграунд — `./run.sh`.

Разделение «чистое против грязного» проведено дважды и одинаково: `configgen`
против `awg`, `domain/routing` против `infra/routing`. Чистое тестируется без
сервера, грязное — руками.

```

             settings (горячий кэш conf/*.yaml), enums, models, blocks (битмаски
             блокировок), access_cache (кто это — для middleware), zone (пояс показа:
             ключ timezone или пояс хоста)
  util/      чистые помощники: timeutil (пояс показа и метка «(UTC+5)», хранение UTC+3,
             форматтеры), nets (подсети), kvfile,

             (ключ из ключа линка, распознавание прежнего файла конфигурации шлюза),
```

### Новый раздел настроек

Разделы «⚙️ Настроек», общие для основного бота и агента шлюза, живут в
`awgbot/bot/sections/` по модулю на раздел; роль приходит словарём
(`bot/roles.py`, параметр `br`), ветвлений по имени роли в модулях нет —
есть `br.has.<блок>` и слова роли. Новый раздел:

1. модуль `awgbot/bot/sections/<id>.py`: `ID`, `LABEL`, `BACK`, `KEYS` (ключи
   настроек раздела), `BOUNDS` (границы ввода), `CYCLES` (кнопки-циклы),
   `ACTIONS` (действия сверх open/toggle/edit/cycle; `Confirm` — с
   подтверждением), по нужде `DEFAULTS` (умолчания ключей, пока их нет в
   conf; у тумблера без умолчания — «включено») и `SCALE` (множитель
   хранения: человек вводит минуты, conf держит секунды), `text(br, …)`,
   `keyboard(br, …) -> InlineKeyboardMarkup` (по аннотации построитель
   попадает в сторож полноты эталонов), `async screen(br, services, key)`;
   клавиатура — `ui.rows(...)`: ряд — список кнопок, кнопка — кортеж
   `(подпись, колбэк)`, `None` — пропуск условной кнопки; хвост «⬅️ Назад» —
   `back_button(br[, раздел])` из `sections/_kb.py`; колбэки кнопок — только
   через `br.cb.pack(раздел, действие, ключ)`;
2. модуль — в `MODULES` (`sections/__init__.py`);
3. `ID` — в `settings_root` словаря той роли, у которой раздел есть (у
   обеих — в оба экземпляра; вложенный раздел — в `subsections`); новое слово роли — поле `BotRole` без
   умолчания и значение в `MAIN` и `GATEWAY` (законно пустое — в `OPTIONAL`);
4. снимки раздела в каталоге эталонов (`tests/screens/shots_<роль>_<раздел>.py`,
   порядок — списком в `tests/screens/shots_<роль>.py`) и
   `pytest tests/screens --update-screens`.

Диспетчеры, `routers_for`, реестр экранов (`set_<id>` находится сам), отмена
под вводом и ядро ввода `handlers/settingscore/` не трогаются: роутер
разделов узнаёт колбэк через переводчик роли и доступность раздела, корень
настроек рисуется из `br.settings_root`; границы, подпись, единицу, умолчание
и множитель ключа с вводом числа ядро ввода берёт из модуля (`sections.bounds`,
`sections.default`, `sections.scale`). Ролевые
разделы, у которых свои обработчики («🖥 Сервер AWG», «💳 Подписки»,
«🛡 SSH-доступ»), рисуются экранами роли (`br.role_screens`) и в `sections/`
пока не переехали.

## Тесты

Пакет покрыт тестами пяти уровней (`tests/`, pytest):

```
tests/unit/         чистая логика без БД/сети (timeutil, configgen, домены
                    маршрутизации, secrets_util, hostmetrics, awg-парсеры,
                    атомы экрана и заполненность словаря роли, точечные
                    раскладки клавиатур (test_ui_layout), сторожа мёртвых
                    имён (test_dead_names) и терминов (test_ui_terms), а также
                    разбор самих shell-скриптов поставки)
tests/smoke/        импорт всего пакета, config.validate(), сборка aiogram-роутеров
tests/integration/  настоящая временная SQLite + фейковый awg-слой (db, services)
tests/e2e/          сквозные сценарии: жизненный цикл, лимиты трафика,
                    пауза/грейс, мониторинг, маршрутизация — побочные
                    эффекты действий; вид экрана держат эталоны
tests/screens/      эталоны экранов: каждый снимок — через настоящий диспетчер
                    роли на заглушке сессии Bot API; эталоны admin/client/
                    guest/gateway.txt
```

```bash
python3 -m venv venv && ./venv/bin/pip install -r requirements-dev.txt
./venv/bin/python -m pytest              # весь набор
./venv/bin/python -m pytest -m unit      # один уровень (unit|smoke|integration|e2e|screens)
./venv/bin/python -m pytest tests/screens --update-screens   # перезаписать эталоны экранов
```

Эталоны экранов ловят то, чего не видят тесты, зовущие обработчик напрямую:
кнопку, потерянную при переносе (порядок роутеров, фильтр, упаковка колбэка),
— у человека она ушла бы в «Кнопка устарела». Снимок — одно действие
(нажатие, `/start`, текст, файл или событие без действия человека вроде
уведомления), запись — всё, что бот после этого сказал Telegram: текст в HTML,
кнопки рядами с `callback_data`/`url`, всплывашки, правки и удаления. На
каждом снимке проверяются лимиты Telegram (4096 знаков текста, 1024 подписи,
64 байта колбэка, 200 единиц UTF-16 всплывашки, не больше 10 рядов кнопок),
разметка HTML, форма подтверждения (в ряду из двух кнопок с «⬅️ Отмена»
она первая и не красная) и раскладка кнопок: подпись в ряду из двух и более
— не длиннее 18 знаков (кроме разрешённых снимку поимённо), «🏠» нигде,
кружок 🟢/🔴 — только состоянию объекта (устройство, профиль) и действию
«🔴 Выключить…», у тумблеров — ✅/☑️. Статика
(`tests/unit/test_ui_layout.py`): `InlineKeyboardBuilder` в коде бота нет
(раскладка — `ui.rows`), хвосты «⬅️ Назад» / «⬅️ В меню» — только из `ui`,
«🏠» нет и в литералах клавиатур. Каталог
снимков — `tests/screens/shots_<роль>_<раздел>.py` (порядок —
`tests/screens/shots_<роль>.py`), сравнение — по файлу эталона
целиком.

Эталоны и остальные уровни не дублируют друг друга. Как выглядит экран —
текст, подписи и ряды кнопок, колбэки — держит эталон; тесты обработчиков и
e2e проверяют то, чего в эталоне нет: записи в БД, вызовы сервисов,
состояние FSM, уведомления другим людям, файлы, удаления сообщений, границы
листания. Утверждение об экране, которое уже есть в эталоне, в e2e не
пишется. Инвариант «одно живое меню» на переходах держит отдельно
`tests/e2e/test_nav_invariant.py`.

Два статических сторожа в `tests/unit/` следят за самими текстами и
клавиатурами. `test_dead_names`: публичное имя модуля `texts/*`,
`keyboards/*` или `bot/sections/*`, на которое в `awgbot/` никто не
ссылается (своё определение и реэкспорт в `__init__` не в счёт), — красное;
ссылка только из тестов тоже не считается — такое имя держит тесты, а не
интерфейс, и снимается вместе с ними. `test_ui_terms`: строки, которые видит
человек (`texts/*`, `keyboards/*`, `bot/sections/*`, `guides.py`, `bot/ui.py`,
`bot/roles.py`, тексты уведомлений домена `domain/notices/`, атомы
`util/textfmt/`, подсказки установочных скриптов), — без бытовых слов о сети
и жилье, без «ВПН», без прежних имён разделов; исключения — по месту, с
объяснением.

Правка текста или клавиатуры: поправить код → `pytest tests/screens
--update-screens` → дифф `tests/screens/*.txt` идёт в тот же коммит. Он
показывает каждый задетый экран обеих ролей, и вычитка идёт по нему; без
перезаписи тест падает с этим же диффом.

Тесты не трогают сервер и Telegram: awg- и routing-слои подменяются in-memory
фейками, БД — временный файл. Установочные скрипты в CI не гоняются, но их
текст разбирается тестами: самые дорогие ошибки там — порядок правил и подсказка
оператору, называющая не то. Минимальная версия — Python 3.12 (`StrEnum`).
