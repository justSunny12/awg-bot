# Стенд резерва серверов AWG

Полная картина пары серверов на одной Linux-машине: сервер A, сервер B, шлюзы
основного сервера G1 и G2, шлюз резерва GR, «интернет» (маршрутизатор с NAT),
«РФ-сайт» и пользователи cA и cB — каждый в своём сетевом пространстве (`lab-<узел>`).
«Публичные» адреса — 203.0.113.0/24 и 198.51.100.0/24, сети шлюзов и пользователей —
за NAT маршрутизатора; топология — `topo.sh`.

На стенде проверяют то, чего не проверить юнит-тестами: модуль AmneziaWG в
пространствах, аварии сети, переезд. В поставку хостов стенд не входит и
установщиком не ставится; его прогон — перед предрелизной сборкой.

## Виртуальная машина

Нужен Linux с тем же ядром и модулем, что на хостах: Debian 13, модуль
AmneziaWG — сборкой по манифесту `install/awg.lock`. На macOS — Lima:

```sh
limactl create --name=awg-lab --cpus=4 --memory=6 --disk=40 \
    --mount=<путь к репозиторию>:w template:debian-13
limactl start awg-lab
limactl shell awg-lab
```

Каталог репозитория виден в ВМ по тому же пути. Один раз внутри ВМ:

```sh
cd <путь к репозиторию>
sudo install/awg-kernel-install.sh install     # модуль и amneziawg-tools по awg.lock
python3 -m venv ~/venv
~/venv/bin/pip install -r requirements.txt -r requirements-dev.txt
```

## Прогон

```sh
sudo -E tests/lab/run.sh                    # самопроверка, топология, сценарии, набор тестов
sudo -E tests/lab/run.sh --no-suite         # без набора тестов
sudo -E tests/lab/run.sh --only s00_topology
```

`run.sh` по порядку: `install/reserve-zone-setup.sh --selftest`, подъём
топологии (`lab.sh up`), сценарии `scenarios/*.sh` (перед каждым — `net.sh
heal`; сценарий печатает причину и выходит не нулём, если не прошёл), снятие
топологии и затем весь набор тестов из `~/venv` того, кто запустил `sudo`
(`TMPDIR` — `/var/tmp/awglab-tmp`, не tmpfs): обвязки идут на GNU sed и
coreutils, как на хостах. Итог — «пройдено N, провалено M», код не ноль при
любом провале.

## Сценарии

| сценарий | что проверяет |
|---|---|
| `s00_topology` | топология живая: публичные адреса видят друг друга, частные сети выходят через NAT, рычаги `kill` и `heal` работают |
| `s01_zone` | зона резерва: оболочка, переезд с клоном (сокет у хоста), NETMAP подсети клона (блок пула в состоянии и таблице зоны, маршрут блока через veth, адрес устройства 1:1 на блок), резолвер зоны, CAKE `triple-isolate` при NETMAP (если `cake=on`), возврат со сбросом `netmap`, очистка |
| `s02_guest` | бот основы на резерве: открытие по долям, ответ пользователю, песочница юнита, шифрованный снимок `rep.bin` и подъём зоны из него; **черновик**, на стенде не прогонялся |
| `s03_move` | право отвечать в Telegram при переезде кнопкой и возврате на макете Bot API: основа поллит, вебхук «резерва» — 409 и стоп поллинга за один запрос, доставка на вебхук, `deleteWebhook` без сброса очереди при возврате; **черновик**, на стенде не прогонялся |
| `s03_vote` | постоянные линки шлюзов к резерву и переезд по взглядам: сторона зоны из `reserve/links/`, линк `awgrsv` на шлюзе (вход — только ответы, пересылка по набору `rsv_open4`), гостевой канал, матрица случаев (основа выключена, шлюз выключен заранее, разрыв только до резерва, случай 5), Н4 и аварийный код, случаи 3 и Н3; **черновик**: план — в шапке, сценарий пока ничего не делает и выходит с кодом 0 — `run.sh` засчитывает его пройденным |
| `s04_open_sandbox` | процесс открытия в песочнице `systemd-run` бота резерва: хранилище гостя у хоста до юнита, `done`, env гостя виден хосту, юнит гостя запущен, `--wipe`; пакет-снимок журнала (`pkg3`) с событиями в `reserve/jrn/` — шаг `journal`, событие после снимка в базе гостя; `reserve/jrn/` в песочнице читается и не пишется, из каталога данных видны ровно пакет и журнал |
| `s05_journal` | журнал на паре серверов (`pairlab.sh`): 40 правок на A подтверждены резервом, A отрезана и правит дальше, затем гибнет; B открывает по своей доле и доле Шлюза 1 — база гостя равна базе A по последнему подтверждённому событию, эпоха гостя — A + 1; переезд кнопкой — правка бота основы на резерве в базе A не дольше 10 с |
| `s06_return_tail` | хвост старой эпохи: A отрезана от B и шлюзов, макет Bot API ей доступен; админ основы вводит аварийный код в боте B, бот основы на резерве ставит вебхук, A на 409 следует, её правки — хвост; после восстановления связи хвост перенесён, спорная правка остаётся значением держателя; возврат кнопкой — Т-Ж4 от бота основы (не гостя) одним сообщением |

## Пара серверов (`pairlab.sh`, `pairnode.py`)

Сценарии журнала (`s05_journal`, `s06_return_tail`) поднимают пару серверов: A
(«Alpha», основа, слушает канал пары) и B («Beta», резерв) — `pairnode.py` в
пространствах `lab-A` и `lab-B` (вход — `nsenter --net`, пространство монтирования
общее с хостом, как у бота и юнита процесса открытия на хосте). У каждого — своя
база, каталог настроек и env в `/var/lib/awglab-pair/<узел>` (не `/tmp`: у песочницы
процесса открытия `PrivateTmp`), свой `awg0` и линк пары `awgpair` на настоящем
AmneziaWG; строка пары и ключи — как после сопряжения. Работают сервисы основного
бота, канал пары, задания резерва планировщика, исполнитель действий и поллинг на
макете Bot API (макет — в `lab-inet` на `:8081`). Бот основы на резерве — тот же
`guest_main.py` в пространстве зоны (юнит зоны ходил бы в настоящий Telegram);
правки в нём — файлами в `$PL/G` (`LAB_GUEST_CMD`). Команды узлам — файлами в
`cmd/` (`load`, `set`, `share`, `code`, `open_share`, `move`, `return`, `backup`),
состояние — `status.json`.

Мир стенда вместо того, чего у него нет: запись DNS — файл `shared/dns.json`
(системный резолвер, авторитетный сервер и провайдер записи узлов читают и пишут
его); «шлюз с агентом новой линии есть» — агентов шлюзов стенд не поднимает, долю
Шлюза 1 сценарий берёт у основы; оболочку зоны на B ставит сценарий (на хостах её
держат стороны линков шлюзов); факт записи при аварийном открытии — отметкой
`tg_take`, которую процесс открытия кладёт после `record_fact` (провайдера и
авторитетного DNS у стенда нет); пересылка (`ip_forward`) в пространствах серверов
включена, как на хостах AWG. Процесс открытия идёт с теми же свойствами песочницы
плюс два отличия стенда: venv из `/home` пользователя (tmpfs вместо `ProtectHome=yes` и
привязка только для чтения) и `NetworkNamespacePath` пространства B.

Не покрыто стендом: сессия пользователя, оставшаяся на A, вместе с трафиком клона на
B — лимит по сумме и DROP у обоих (нет конфигов пользователя в `cA`, трафика через оба
туннеля и опроса трафика у основы в следовании).

Что нужно черновику `s03_vote` сверх топологии — в его шапке: слушатель
гостевого канала резерва и клиент гостевого канала на шлюзе без Telegram
(обёрток для стенда ещё нет), макет Bot API и макет авторитетного DNS для
записи переезда (провайдера записи для стенда тоже ещё нет).

## Скрипт зоны

`install/reserve-zone-setup.sh` можно звать и отдельно:

- `--plan` (без root) — что умеет хост: `store` (tmpfs без свопа с ядра 6.4,
  иначе ramfs), `cake`, `netns`, `awg`, свободный порт вебхука `webhook_port`
  из 443/80/88/8443, `zone` — есть ли уже зона;
- `--selftest` (root) — на установленном модуле проверяет две опоры схемы
  зоны: UDP-сокет интерфейса остаётся у хоста после переноса интерфейса в
  пространство и переименования (`RESULT_SOCKET_AT_HOST`), и `awg set …
  persistent-keepalive 25-35` принимает диапазон (`RESULT_KEEPALIVE_RANGE`);
  `RESULT_TUNNEL_PING` — туннель через перенесённый интерфейс живой. Код 0 —
  обе опоры на месте. Временные пространства и интерфейсы снимаются при любом
  выходе.

## Ручная работа

```sh
sudo tests/lab/lab.sh up | down | status
sudo tests/lab/lab.sh exec G1 ping -c1 203.0.113.5
```

Рычаги аварий (`net.sh`) — правила nft в пространстве маршрутизатора, узлы о
них не знают:

| команда | что делает |
|---|---|
| `net.sh kill <узел>` | узел «умер»: весь его трафик отброшен |
| `net.sh cut <узел1> <узел2>` | разрезать путь между двумя узлами в обе стороны |
| `net.sh block-rf <узел>` | узел недоступен из частных сетей (блокировка из РФ) |
| `net.sh heal` | снять все рычаги |
| `net.sh show` | действующие рычаги |

Макет Bot API (`botapi.py`) — несколько ботов, `getUpdates` с подтверждениями,
вебхук с `secret_token` и сертификатом, отказ 409 при активном вебхуке,
отправки — в журнал JSONL (с адресом отправителя `from`: у основы и бота основы на
резерве токен один); боты стенда ходят в него через
`TelegramAPIServer.from_base`:

```sh
~/venv/bin/python -m tests.lab.botapi --listen 127.0.0.1:8081 --journal /var/tmp/botapi.jsonl
```

Служебное: `POST /inject/<токен>` — положить боту обновление, `GET
/journal/<токен>` — его журнал.
