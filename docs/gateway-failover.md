# Резервный РФ-шлюз — концепт

Статус: **реализовано в v2.24.0** (17–18.09.2026), тексты экранов — на
вычитку. Продолжение `docs/conditional-routing.md`: та же фича, тот же линк, тот
же агент — добавляется второй шлюз и переключение между ними без участия
человека. §13 описывает реализацию так, как она легла в код.

Исходная ситуация: две квартиры с белыми адресами, две Raspberry Pi. Цель —
отказ одной квартиры (питание, провайдер, железо) не должен превращаться в
«российские сервисы ругаются на адрес» у всех, кому разрешён РФ-доступ.

---

## 1. Суть

**Два шлюза, один несёт трафик, второй ждёт.** Оба линка подняты постоянно, оба
меряются каждый такт. Когда активный не проходит проверку три такта подряд, а
резерв три такта подряд проходит, маршрут в таблице фичи перекладывается на
резерв — одной командой `ip route replace`. Клиентские правила, наборы, dnsmasq,
конфиги устройств не меняются.

**Липкость.** Оживший прежний шлюз в резерв не возвращает трафик обратно.
Каждое переключение меняет исходящий российский адрес, а значит рвёт сессии в
банках и госуслугах у всех включённых профилей; дёргать людей ради «правильного
дома» незачем. Вернуться — только руками из настроек или когда упадёт уже
новый активный.

**Предпочтительный шлюз.** Один из слотов помечается галочкой в настройках. Он
берёт трафик при холодном старте — когда ВПС перезагружался и сессии всё равно
порваны. При обычном перезапуске бота активный остаётся сохранённым: рестарт
бота не повод менять людям адрес.

**Ручной переезд в обе стороны.** Из карточки любого слота трафик можно
переложить на него, и обратно, без порогов и интервалов — для обслуживания
малины, роутера или провайдера в одной из квартир.

**Машины разные.** Первая малина — NAS, домашняя схема, прочие сервисы;
вторая — только наш агент с ботом, ничего больше. Отсюда: домашние подсети
и доступ админа по туннелю по сути только у первого слота, второй слот
заводится путём «новая машина», а замечания про NAS и торренты к нему не
относятся.

**Что не меняется:** конфиги устройств, статусная строка у клиентов, агент на
малине (кода не получает), безопасность бандла и пометки шлюза, списки и
разрешения профилей.

## 2. Топология

```
телефон ──awg──► ВПС
                 │  src ∈ включённые  И  dst ∈ набор РФ-сервисов
                 ▼
          таблица фичи (100): default dev <активный линк>
                 │
     ┌───────────┴───────────┐
     ▼                       ▼
 awglink  ──► ГВ-1 (дом 1)   awglink2 ──► ГВ-2 (дом 2)
   ▲ несёт трафик              ▲ в резерве, линк поднят, зонд ходит
```

Каждый шлюз — отдельный линк-интерфейс на ВПС со своими ключами, psk и своей
обфускацией. В один интерфейс двух пиров не положить: у пира шлюза
`AllowedIPs = 0.0.0.0/0`, и крипто-маршрутизация WireGuard не терпит
пересечения — второй пир просто перекрыл бы первый. Порт у второго линка другой:
UDP 443 держит первый.

Направление установления линка прежнее: шлюз инициирует, `PersistentKeepalive`,
входящих на домашний адрес не требуется. Для второго дома — то же.

### Узлы

| | ВПС | ГВ-1, ГВ-2 |
|---|---|---|
| Что знает о втором шлюзе | всё: слоты, линки, активный, стрики | ничего |
| Кто решает, кто активный | бот ВПС | — |
| Что меняется при переключении | один маршрут в таблице 100 | ничего |
| Агент | — | тот же, свой токен, своя пометка по ключу линка |
| Что ещё на машине | бот | ГВ-1: NAS, домашняя схема, сервисы; ГВ-2: ничего, кроме агента |

Агент не знает, активный он или резервный, и это нормально: канала управления
между хостами нет по построению, а «несёт ли трафик» ему для работы не нужно.
Строку «резерв/активный» в панель агента не добавляем — она врала бы после
каждого переключения до следующего бандла.

## 3. Модель данных

### Таблица `gateways` вместо флага

Флаг `devices.is_gateway` с уникальным индексом «не более одного» заменяется
таблицей слотов:

```sql
CREATE TABLE gateways (
    id            INTEGER PRIMARY KEY,          -- слот: 1, 2 (…)
    device_id     INTEGER NOT NULL UNIQUE,      -- устройство админа (аплинк малины)
    link_if       TEXT    NOT NULL UNIQUE,      -- awglink, awglink2
    link_port     INTEGER NOT NULL UNIQUE,      -- 443, 8443
    link_cidr     TEXT    NOT NULL UNIQUE,      -- 10.99.99.0/30, 10.99.99.4/30
    preferred     INTEGER NOT NULL DEFAULT 0,   -- 0/1: берёт трафик при холодном старте
    home_subnets  TEXT    NOT NULL DEFAULT '',  -- "192.168.1.0/24 192.168.2.0/24"
    label         TEXT    NOT NULL DEFAULT '',  -- «дом 1» — подпись в текстах, необязательна
    created_at    TEXT    NOT NULL
);
CREATE UNIQUE INDEX idx_gateways_preferred ON gateways(preferred) WHERE preferred = 1;
```

Предпочтительный — не более одного, это держит частичный уникальный индекс,
как сейчас держал единственность шлюза. Порядок в списках и при равных
условиях (кандидат на переключение, спор за домашнюю подсеть) —
предпочтительный первым, затем по номеру слота.

`is_gateway` у устройства становится производным: есть строка в `gateways` с
таким `device_id`, либо с `device_id` оригинала пары в окне переезда (сейчас это
`is_gateway_eff` через `twin_of` — остаётся тем же подзапросом, только к новой
таблице). Всё, что ветвится по `dev.is_gateway` (лимиты, блокировки, выдача,
сортировка, потребление), не трогается.

**Что в состоянии, а не в конфигурации** (таблица `state`):

| ключ | значение |
|---|---|
| `routing_active_gateway` | id слота, который несёт трафик |
| `routing_gw_<id>_up_streak` | хороших замеров подряд по слоту («стабильно жив»); окно замеров — в памяти бота |
| `routing_gw_<id>_announced` | сообщали ли об отвале этого слота |
| `routing_switched_at` | момент последнего автоматического переключения (защита от качелей) |
| `routing_manual_hold` | слот, на который переключили руками при его отказе: автомат не перекладывает |
| `routing_host_boot_at` | момент загрузки хоста, виденный ботом: сдвинулся — холодный старт |
| `routing_gw_ping_<id>`, `routing_gw_extip_<id>` | пинг с ВПС до шлюза и внешний IP шлюза, с моментом замера (кэш на сутки) |
| `gw_bundle_issued_at_<id>`, `gw_bundle_ssh_allow_<id>` | выпуск бандла — по слоту |
| `routing_link_ok`, `routing_link_up_streak`, `routing_link_announced` | как сейчас, относятся к **активному** |

### Миграция

Одноразово при старте (флаг в `state`, как у балансов паузы):

1. устройство с `is_gateway = 1` → строка `gateways(id=1, link_if = routing.gw_interface,
   link_port = ListenPort из живого конфига линка, link_cidr из `ip addr` линка,
   preferred = 1, home_subnets = routing.home_subnets из app.yaml через пробел)`;
2. `routing_active_gateway = 1`; `gw_bundle_issued_at` → `gw_bundle_issued_at_1`;
3. колонка `is_gateway` и индекс остаются до следующего подъёма минимума, но не
   читаются и не пишутся (миграции у нас не откатываются, снимать сразу незачем).

Шлюза не было — таблица пустая, поведение прежнее.

### Конфигурация (`app.yaml`)

```yaml
routing:
  gw_interface: "awglink"     # как сейчас: непустой = обвязка развёрнута, фича не спит.
                              # Это интерфейс ПЕРВОГО слота; остальные — в БД.
  home_subnets: []            # УСТАРЕЛО: читается один раз при миграции в слот 1,
                              # дальше подсети живут в карточке шлюза
  link_ports: [443, 8443]     # порты линков по слотам; второй — не 443 (занят первым),
                              # 8443 — так же теряется среди QUIC-подобного, как и 443
  link_cidrs: ["10.99.99.0/30", "10.99.99.4/30"]
  gateways_max: 2             # больше двух — смысл только при трёх квартирах
  failover:
    enabled: true             # автоматическое переключение; false — только руками
    min_interval_minutes: 10  # не чаще одного автоматического переключения
    standby_probe_minutes: 5  # зонд резерва наружу — редко, ±40 % джиттера; между
                              # зондами живость по хендшейку линка
    window_samples: 10        # скользящее окно замеров активного (10 × 30 с = 5 мин)
    min_availability: 50      # ниже порога = пятый неуспешный в окне → переключение сразу
```

Всё, кроме `gw_interface`, — горячие ключи. Такт зонда, ширина окна, порог
доступности и автопереключение правятся из бота: ⚙️ Настройки → Условная
маршрутизация → «📡 Мониторинг и резервирование» (6.13). Правило прежнее:
пустой `gw_interface` ⇒ фича спит целиком, и второй слот тоже.

## 4. Обвязка ВПС

### Линки

Скрипт `routing-link-setup.sh` уже параметризован `LINK_IF`, `LINK_PORT`,
`LINK_CIDR`, `LINK_VPS_ADDR`, `LINK_GW_ADDR`, `CONF`, `GW_CONF_OUT`,
`GW_BUNDLE_OUT`. Второй слот — тот же скрипт с другим набором переменных. Что
дорабатывается:

- **юнит по интерфейсу**: `awg-link@.service` (шаблон, `LINK_IF=%i`) вместо
  единственного `awg-link.service`. Первый слот переезжает на шаблон при первом
  `--reassert` после обновления: старый юнит выключается, включается
  `awg-link@awglink`; интерфейс при этом не опускается;
- выходные файлы по интерфейсу: `/root/gw-<if>.conf`, `/root/awg-gw-bundle-<if>.sh`
  (для первого слота имена прежние — бандл `awg-gw-bundle.sh`, чтобы инструкции и
  установщик на шлюзе не менялись);
- `--rollback` и `--rekey` — только своего `LINK_IF`;
- бандл несёт `LINK_IF` своего слота (уже несёт), скрипт шлюза берёт его оттуда
  (уже берёт). На стороне малины ничего не меняется.

Порт линка слота — по живому конфигу на ВПС: `gateway_sync_link_ports()` при
старте сверяет `ListenPort` файла `<link_if>.conf` со строкой слота, при
расхождении правит слот, перерисовывает файервол хоста и напоминает админу
перевыпустить конфигурацию шлюза (у той стороны Endpoint старый). Так порт
меняется одной правкой файла и перезапуском линка, без ручной правки БД.

Порт второго линка в файерволе хоста открывается тем же путём, что и первого:
`nftguard` собирает `udp_ports` из `ListenPort` всех интерфейсов awg, а список
интерфейсов дополняет одним `ROUTING_GW_INTERFACE` (`nftguard.py`, ~266). Туда
дописываются `link_if` всех слотов — и порт 8443 открывается при следующей
реконсиляции файервола, отдельного правила не нужно.

### Таблицы и метки

| что | сейчас | станет |
|---|---|---|
| таблица фичи 100 | `default dev awglink` | `default dev <link активного слота>` |
| ip rule фичи | `fwmark 0x1/0x1 lookup 100` | без изменений |
| таблица слота *i* | — | `100 + i`: `default dev <link слота>` — только для зонда резерва |
| ip rule слота *i* | — | `fwmark <1<<i>/<1<<i> lookup 100+i` |
| MSS-кламп | `-o awglink` | по правилу на каждый линк |
| исключение из MASQUERADE | `-s клиенты -o awglink` | по правилу на каждый линк (ставит `--reassert` своего юнита) |
| маршруты домашних подсетей | все в `gw_interface` | подсети слота — в линк слота, независимо от того, кто активный |

Биты меток слотов (0x2, 0x4) с клиентской маркировкой (0x1) не пересекаются, а
маркируется только зонд (`SO_MARK` на своём сокете); в цепочку `AWGBOT_RT` они
не попадают. Так зонд резерва идёт ровно тем путём, которым пойдут клиенты после
переключения — через тот же линк, тот же NAT шлюза.

`ensure_policy()` доводит всё это разом и по-прежнему зовётся по событию: смена
вердикта, первый тик после старта, каждый десятый тик, а теперь ещё и после
переключения.

**Переключение** = `ip route replace default dev <link> table 100` +
`routing_active_gateway = id` + сброс стриков активного. Один exec, доли
секунды, маркировка не снимается ни на такт: клиентские пакеты просто начинают
уходить в другой линк. conntrack на ВПС переживает это без потерь — NAT для
маркированного трафика на ВПС не делается (исключение из MASQUERADE); рвутся
сессии на стороне сервисов, потому что у них меняется адрес клиента.

### Локальные подсети

Две квартиры с одинаковой подсетью (обе `192.168.1.0/24`) — обычное дело, но
не наш случай: у второй малины домашней сети, до которой нужно доставать, нет,
и подсети задаются только первому слоту. Правило на случай, если зададут обоим:
маршрут в основной таблице один, значит достаётся предпочтительному, при
равенстве — меньшему слоту; карточка второго показывает предупреждение, а перед
сохранением подсети бот говорит об этом прямо. Лечится сменой подсети в одной
из квартир; делать за человека тут нечего.

## 5. Зонд и автомат

### Что меряется

Такт `probe_seconds` (30 с), как сейчас. За такт:

- **активный** — зонд с меткой фичи (0x1) по таблице 100. Меряем ровно то, чем
  ходят клиенты, и заодно проверяем, что таблица указывает куда надо;
- **резерв** — зонд с меткой своего слота по своей таблице, те же цели и
  порт, две попытки, таймаут короче (2 с). Но **редко и с джиттером**:
  `failover.standby_probe_minutes` (5) ± 40 %. Строго периодический коннект
  наружу с домашнего адреса каждые полминуты — маячок, сигнатура для ТСПУ;
  активный такого следа не оставляет, у него клиентский трафик. Между зондами
  живость резерва — по свежести хендшейка его линка (локальный exec, наружу
  ничего): резерв «в порядке» = последний зонд прошёл И хендшейк свежее 180 с.
  Такой шлюз гарантированно примет нагрузку: есть интернет, есть линк. Стрик
  резерва копится каждый такт по этому условию, так что на момент переключения
  все нужные стрики кандидата уже есть. Новый слот зондируется сразу, не
  дожидаясь интервала. Хендшейк требуется и в такт зонда: пройденный зонд без
  свежего хендшейка означает, что путь ушёл мимо линка (правило слота не на
  месте), и такой резерв кандидатом не считается. По той же причине первый
  такт после старта ставит таблицы и правила слотов **до** зондов.

Оба зонда снаружи замка, как сейчас; идут параллельно (`_any_reachable` уже ходит
к целям разом). Хендшейк по-прежнему только уточняет адрес ремонта:
`PROBE_NO_PATH` против `PROBE_DOWN`, по интерфейсу слота.

### Решения такта

Одно понятие **«недоступен»** на все решения: в скользящем окне последних
`failover.window_samples` (10 замеров ≈ 5 мин) неуспешных не меньше, чем
допускает порог `failover.min_availability` (50 % → 5 из 10), подряд или
вразнобой. Стрика «плохих подряд» нет вовсе. Второе понятие — **«стабильно
жив»**: три хороших замера подряд (`up ≥ 3`). Вычисляются в таком порядке,
одной транзакцией:

1. **Не задействовано** (фича выключена, обвязка больна) → маркировка снята
   немедленно, окна и стрики в ноль. Как сейчас.
2. **Окно и стрик хороших** каждого слота. Окно живёт в памяти бота (писать
   его в БД каждый такт незачем), после перезапуска копится заново; стрик
   хороших — в `state` с потолком.
3. **Переключение** (только при `failover.enabled`): активный недоступен, есть
   другой слот с `up ≥ 3`, с прошлого автоматического переключения прошло ≥
   `min_interval_minutes` → активным становится он (при нескольких —
   предпочтительный, затем меньший слот). Переключаемся тут же, на пятом
   неуспешном, не дожидаясь заполнения окна; окно скользит, и неудачи старше
   пяти минут поводом не становятся. Маршрут перекладывается тут же, окна
   обоих начинаются заново, маркировка **остаётся включённой**. Уведомление
   «переключился».
4. **Гашение и возврат** — активный недоступен без кандидата → маркировка
   снята; `up ≥ 3` → включена. Гашение и переключение — одно и то же
   условие, поэтому при живом резерве маркировка не снимается ни на такт.
5. **Объявления** — в том же такте, что и действие (см. §7). Резерв: письмо,
   когда он молчит всё окно (десять неуспешных подряд), без звука.

Из 3 и 4 следует поведение в деградации: маркировка снята, активный
недоступен, резерв набрал три хороших → шаг 3 делает его активным, шаг 4
включает маркировку. То есть «резерв ожил» вытаскивает фичу из деградации
без участия человека, но не раньше, чем он подтвердил себя тремя замерами.

Липкость — прямое следствие шага 3: пока активный доступен, никто его не
трогает, сколько бы хороших замеров ни набрал резерв.

### Защита от качелей

`min_interval_minutes` — не «пауза после переключения», а минимальный
интервал между двумя **автоматическими** переключениями. Первое после долгой
тишины — мгновенно по порогу. Если в течение интервала упал уже новый активный,
бот не мечется, а гасит маркировку по обычному порогу: два переключения за
десять минут означают, что лежит что-то общее (провайдер, ВПС), и третий адрес
за десять минут людям не поможет. Ручное переключение интервал не учитывает и
не сбрасывает.

### Старт: холодный и тёплый

Два разных случая, и различать их надо честно:

- **тёплый старт** — перезапустился только бот (обновление, кнопка, сбой
  процесса). Линки не опускались, conntrack на месте, у клиентов ничего не
  рвалось. Активный — из `routing_active_gateway`, как было. Менять адрес
  людям из-за рестарта бота нельзя;
- **холодный старт** — перезагружался ВПС. Линки поднялись заново, conntrack
  пуст, сессии и так порваны — момент бесплатно вернуться на
  предпочтительный. Активный — предпочтительный слот, если он есть.

Признак холодного старта — сдвинулся момент загрузки хоста (сейчас минус
аптайм из `/proc/uptime`) относительно запомненного в `routing_host_boot_at`.
Именно момент загрузки, а не последний такт живости: первый такт стартует
вместе с планировщиком, раньше этой проверки, и по нему холодный старт не
отличить. Нет сохранённого активного или момента загрузки (первый запуск
после обновления, свежая установка) — тоже холодный.

Предпочтительный на холодном старте **обязательно проверяется** (preflight
зондирует его первым); не отвечает → берётся сохранённый активный, если он
другой и отвечает, иначе любой отвечающий, иначе предпочтительный всё равно
(маркировка снята по обычному порогу, автомат разберётся по тактам). Второй
шлюз — право админа, не обязанность: с одним слотом всё работает как до
этого. Preflight пишет замечание по
каждому слоту, который не прошёл, с его именем.

Ребут ВПС: оба юнита поднимают свои линки и исключения из MASQUERADE, бот на
старте доводит таблицы и маршруты `ensure_policy()`.

### Ручное переключение

Из карточки слота, в любую сторону, без порогов: маршрут перекладывается
сразу, стрики нового активного наследуются от его слотовых (обычно `up ≥ 3`),
`routing_switched_at` не трогается — интервал защищает от автомата, не от
человека. Для обслуживания дома 1 этого достаточно: переложить на дом 2,
работать, переложить обратно.

**Ручное удержание.** Переключили руками на шлюз, который сейчас не отвечает,
— значит, так надо: автомат его не перекладывает обратно
(`routing_manual_hold`), маркировка гасится по обычному порогу. Удержание
снимается, когда этот шлюз набрал три хороших замера: упадёт снова — автомат
переключит на живой резерв с уведомлением, как обычно. Переключение руками на
живой шлюз удержания не ставит.

### Пинг до шлюза и внешний IP

**Пинг с ВПС до шлюза**: ICMP по линку на адрес шлюза в /30 (файервол шлюза
пускает ICMP с ВПС по линку), медиана трёх, локальная команда — наружу с
домашнего адреса ничего не уходит. Подпись — с именем ВПС: «Пинг с AWG-SRV:
43 мс» (hostname хоста; без него — «с сервера»).

**Внешний IP шлюза**: эндпоинт пира линка из `awg show dump` — ВПС видит
адрес дома с каждым хендшейком, никаких сторонних сервисов и следов наружу.
Строка «↗️ Внешний IP: 203.0.113.10» в карточках слота и устройства-шлюза;
читается живьём, кэша не нужно.

- Единицы пинга — русские сокращённые: до секунды `43 мс`, дальше `1,2 с`.
- Пинг кэшируется на сутки в `state` по слоту; показывается из кэша.
- Пустой кэш заполняется лениво при первом открытии экрана с ним; «не
  измерен» на экране не бывает, только «шлюз не отвечает» / «не определён».
- Инвалидация — при отвале хоста: стрик `down` слота дошёл до порога → кэш
  пинга снят; следующее открытие экрана меряет заново.
- `iputils-ping` ставится установщиком при первом запуске и при обновлении.
- Кнопка «📡 Пинг» меряет пинг заново, кэш обновляется, ответ на кнопку
  значением, карточка перерисовывается.

### 6.4. Назначение в слот (`rt_gw`, ref = слот)

**Назначение всегда идёт полным путём** — и для нового устройства, и для
уже созданного: ключи линка слота выпускаются заново, спрашивается токен
агента слота (один раз), в чат приходят инструкция первого применения и
открытый файл. Устройство, созданное в боте раньше, линка не знает, и
«короткий» путь с шифрованным файлом для него был бы пустым обещанием.
Шифрованный файл остаётся только у «⚙️ Конфигурация шлюза» (перевыпуск на
уже настроенную машину) и у запасного пути через пересланный токен агента.
Файл первого применения после успешного применения **удаляет себя сам**
(внутри ключи); повторный запуск установщика с ролью gateway на машине, где
агент уже стоит, не спрашивает ничего — применяет файл и перезапускает
агента, всё в этом пути идемпотентно.

Тот же экран, что сейчас, с уточнением, о каком слоте речь. Первый слот —
текст без изменений (`GATEWAY_CHOOSE_INTRO`). Резервный:

```
🛰 Резервный шлюз

Ещё одно устройство — со своим внешним IP. Когда основной шлюз перестанет
отвечать, трафик пойдёт через него.

Шлюзом можно назначить одно из твоих уже созданных в боте устройств или
создать новое.

Для резервного шлюза поднимется второй линк — свои ключи, порт 8443. Первый
файл применяется на машине руками, как и у основного.
```

```
[📱 Из моих устройств]     ← если есть кандидаты
[➕ Новое устройство]
[⬅️ Назад]
```

Кандидаты — устройства админа, выпущенные ботом и не занятые другим слотом.
Замена устройства в слоте: тот же экран, заголовок «🔁 Заменить устройство: «Pi2»»,
подтверждения — как сейчас у смены шлюза (`gateway_mark_ask`), с добавкой
«Слот резервный: трафик клиентов не затронут» либо «Это активный шлюз: на
время замены трафик пойдёт через «Pi2»» (если второй жив) / «…российские
сервисы откроются с зарубежного адреса, пока новое устройство не поднимется».

Устройство «Шлюз 2» — имя новой машины во втором слоте (`_GW_NEW_NAME` + номер
слота). Токен агента: **у второго шлюза свой бот и свой токен** — та же
причина, что и у первого: домашняя машина не должна знать чужой токен, а два
агента с одним токеном будут перехватывать апдейты друг у друга. Спрашивается
один раз на слот, хранится как `GW_BOT_TOKEN_2` в env. Текст вопроса — прежний
`GATEWAY_ASK_TOKEN` с первой строкой «🤖 Токен бота резервного шлюза».

Итог назначения — как сейчас: заголовок, файл первого применения и инструкция
`gateway_install_instructions`. В инструкции для второго слота — имя файла
`awg-gw-bundle-awglink2.sh` и та же одна команда; установщик на шлюзе принимает
путь из `--bundle`, менять его не нужно.

### 6.5. Что происходит при добавлении второго слота (без экрана)

По подтверждению «➕ Да, новое устройство» / «🛰 Да, это шлюз», в таком порядке,
и любой отказ откатывает предыдущие шаги:

1. `routing-link-setup.sh --apply` с `LINK_IF=awglink2 LINK_PORT=8443
   LINK_CIDR=10.99.99.4/30 …` — ключи, конфиг, интерфейс, юнит `awg-link@awglink2`;
2. порт 8443/udp — в файервол хоста: перерисовка `nftguard` сразу, не при
   следующей плановой;
3. строка в `gateways`;
4. `ensure_policy()` — таблица 101, правило по метке 0x2, MSS-кламп на `awglink2`;
5. бандл слота: `ADMIN_IPS` те же, `GATEWAY_PUBKEY` — ключ устройства этого слота,
   `UPLINK_B64` — его конфиг аплинка;
6. файл первого применения в чат.

Активный слот при этом не меняется. Пока у нового слота нет хендшейка, в списке
он `⏳`, зонд по нему идёт, стрик копится с нуля — и переключаться на него
автомат сможет только после трёх хороших замеров.

### 6.6. Ручное переключение (подтверждение)

В обе стороны: с активного на резерв и обратно, из карточки того слота,
который должен взять трафик. Никаких порогов и интервалов — это действие для
обслуживания. Резерв в порядке:

```
▶️ Переключить трафик на «Pi2»?

Российские сервисы у всех включённых профилей начнут выходить с адреса дома 2.
Исходящий адрес сменится — приложения могут попросить войти заново.

«NASPi» останется в резерве. Автоматически бот обратно не вернёт.
```

```
[⬅️ Отмена]  [▶️ Да, переключить]
```

Резерв не отвечает:

```
⚠️ «Pi2» не отвечает уже 14 мин.

Переключить трафик на шлюз, через который наружу сейчас не пройти? Российские
сервисы у всех включённых профилей перестанут открываться, пока он не оживёт —
или до ручного переключения на живой шлюз.
```

(автомат при этом не мешает: ручное переключение на лежащий шлюз ставит
удержание, см. §5)

```
[⬅️ Отмена]  [▶️ Всё равно переключить]
```

По «Да»: маршрут перекладывается, стрики нового активного наследуются от его
слотовых, `routing_switched_at` не трогается (интервал — для автомата).
Ответ на кнопку: «Трафик идёт через «Pi2»», возврат в карточку.

### 6.7. Конфигурация шлюза (`rt_bundle`, ref = слот)

Экран `ROUTING_BUNDLE_INTRO` без изменений, заголовок с именем:
«⚙️ Конфигурация шлюза «Pi2»». Файл — шифрованный ключом линка **этого** слота;
агент второго шлюза расшифрует только свой. Кнопка «⚙️ Конфигурация шлюза» в
карточке устройства (из «Моих устройств») ведёт сюда же со слотом устройства.

### 6.8. Домашние подсети (`rt_gw_home`, FSM)

```
🏠 Локальные подсети «Pi2»

Подсети за этим шлюзом, до которых твои устройства должны доставать через
туннель — NAS, роутер, домашние сервисы. Кому туда можно, решает файервол
шлюза (только устройствам админа); здесь — только путь.

Сейчас: не заданы.

Пришли подсети через пробел или с новой строки, например 192.168.2.0/24.
Пустое сообщение или «—» — убрать все.
```

```
[✖️ Отмена]
```

Разбор: `ipaddress.ip_network(strict=False)`, IPv4, не клиентская подсеть, не
подсеть линка. Каждая отклонённая строка — с причиной, по образцу
`routing_add_report`. Совпадение с подсетью другого слота — предупреждение из
6.3 прямо в отчёте, но сохраняется. После сохранения — `ensure_home_routes()`
и карточка слота.

Маршрут убранной подсети остаётся в ядре до ребута — осознанно, как сейчас.

### 6.10. Снять шлюз (подтверждение)

Резервный:

```

он идёт через «NASPi». Резерва больше не будет: если «NASPi» перестанет
отвечать, российские сервисы откроются с зарубежного адреса.
Устройство станет обычным: лимиты, блокировки, ссылки — как у всех.
```

```
[🛑 Да, убрать шлюз]
[Отмена]
```

Активный при живом резерве:

```
🛑 «NASPi» перестанет быть шлюзом.

Трафик клиентов перейдёт на «Pi2» прямо сейчас — исходящий адрес сменится,
приложения могут попросить войти заново. Линк awglink снимается, машина
потеряет его сама. Устройство станет обычным.
```

Активный без резерва — текст прежний (`gateway_remove_ask`): функция
выключится до назначения нового шлюза.

Действие: слот удаляется, `--rollback` своего линка (юнит, конфиг, исключение
из MASQUERADE, файервол хоста), таблица и правило слота снимаются; активный при
необходимости переключается; без слотов — `app.routing.enabled = false`, как
сейчас. Итоговый текст — `gateway_removed` с уточнением, через кого теперь
трафик.

«🛑 Не шлюз?» в карточке устройства ведёт в то же подтверждение своего слота.


### 6.12. Мониторинг и резервирование (`rt_mon`)

Последний пункт раздела перед «Назад». Такт зонда, ширина окна и порог
доступности — пикерами, автопереключение — тумблером; всё горячее, такт
переставляет задачу планировщика сам. Порог в неуспешных замерах считается
от окна с округлением вверх: недоступен, когда доступность в окне **ниже**
порога. Окно 5 и порог 50 % → 3 неуспешных (2 из 5 — это 60 %, ещё
доступен); окно 5 и 25 % → 4; окно 5 и 75 % → 2. Число всегда напечатано на
экране: «N неуспешных из K».

```
📡 <b>Мониторинг и резервирование</b>

Зонд активного шлюза ходит наружу каждые 30 с — это такт. Недоступность
считается по скользящему окну последних 10 замеров: если неуспешных в нём не
меньше 5 (доступность ниже 50 %), условная маршрутизация выключается, а при
живом резерве трафик переходит на него в тот же такт.

Резервный шлюз зондируется наружу редко — раз в 5 мин, между зондами
живость по хендшейку линка. Второе автоматическое переключение раньше чем
через 10 мин после первого не делается.

Сейчас: такт 30 с, окно 10 замеров (≈ 5 мин), порог 50 % (5 неуспешных из
10). Окно живёт в памяти бота и после перезапуска копится заново.
```

```
[🔘 такт 30 с] [такт 45 с] [такт 60 с]
[окно 5] [🔘 окно 10] [окно 20]
[порог 25 %] [🔘 порог 50 %] [порог 75 %]
[🟢 Автопереключение на резерв]
[⬅️ Назад]
```

### 6.13. Главное меню админа и клиентов

Без изменений. Статусный блок главного меню («🇷🇺 РФ-доступ: 🟢 сервер
работает») отражает маркировку, а не конкретный шлюз: клиенту всё равно,
какой из домов несёт трафик.

## 7. Уведомления

Все — только админу. Критичны (со звуком, сквозь тихие часы) только те,
после которых люди остались без РФ-доступа: «шлюзы пали», «оба лежат»,
«второе переключение не делаю». «Переехали на резерв» — без звука: люди с
РФ-адресом, это не авария. Имена — с подписью, если есть: «NASPi» (дом 1).

**Автоматическое переключение** (в момент шага 3 автомата):

```
🔁 РФ-шлюз переключён: «NASPi» (дом 1) не отвечает, трафик идёт через
«Pi2» (дом 2).

Исходящий адрес у клиентов сменился — российские приложения могут попросить
войти заново. Останусь на «Pi2» и после того, как «NASPi» оживёт.
Принудительно вернуть трафик обратно можно в карточке шлюза (⚙️ Настройки →
Условная маршрутизация → Шлюзы).
```

Отдельного письма ««NASPi» недоступен» при этом нет: переключение и есть
сообщение об отказе. Уточнение, где чинить, добавляется хвостом — тем же, что
сейчас: «Туннель до него жив — проверь аплинк и NAT на самом шлюзе.» при
`PROBE_NO_PATH`, подсказка про бандл при `PROBE_DOWN`.

**Прежний активный ожил** (только если о нём сообщали):

```
🟢 «NASPi» (дом 1) снова в строю — остаётся в резерве. Трафик идёт через
«Pi2» (дом 2).
```

**Оба лежат** — текущий `_txt_rt_gw_down` / `_txt_rt_gw_no_path` с добавкой
сразу за первой фразой: «Резервный «Pi2» (дом 2) тоже не отвечает.», затем
прежняя строка про эффект и подсказка про бандл. Возврат —
прежний `_TXT_RT_GW_UP`, с именем шлюза, через который пошёл трафик.

**Резерв молчит** (всё окно, десять неуспешных подряд, ≈5 мин, не critical):

```
⚠️ Резервный РФ-шлюз «Pi2» (дом 2) не отвечает уже 5 мин — резерва сейчас
нет. Клиенты не затронуты: трафик идёт через «NASPi» (дом 1).
```

и по возвращении: «🟢 Резервный РФ-шлюз «Pi2» (дом 2) снова отвечает.»

**Автомат не переключил из-за интервала** (когда упал новый активный раньше
`min_interval_minutes` после переключения):

```
🔴 «Pi2» (дом 2) перестал отвечать через 4 мин после переключения на него.
Второе переключение подряд не делаю: проблема выглядит системной.
Маркировка снята: российские сервисы временно открываются с зарубежного
адреса. Переключить принудительно можно в карточке шлюза (⚙️ Настройки →
Условная маршрутизация → Шлюзы).
```

**Дрейф состава устройств админа** (`gw_bundle_drift_notes`) — по каждому слоту,
с именем: «…Перевыпусти конфигурацию шлюза «Pi2»».

Клиентам о переключении не сообщается: для них меняется адрес, но не работает
ли функция; строка статуса остаётся зелёной. Если сервис попросил войти заново
— это привычное поведение, объяснять его через бота значит пугать без нужды.

## 8. Сценарии

### 8.1. Обновление с одного шлюза

Миграция §3 переносит «NASPi» в слот 1. Раздел показывает одну строку и
`[➕ Резервный шлюз]`. Никаких действий на малине: линк, ключи, бандл прежние,
юнит переезжает на шаблон при первом реассерте.

### 8.2. Добавление резервного, новое устройство

Раздел → `[➕ Резервный шлюз]` → 6.4 → `[➕ Новое устройство]` → подтверждение →
(первый раз) токен второго бота → §6.5 → инструкция и файл. На Pi2 — одна
команда с ноутбука, `/start` второму боту. В списке слот `⏳ [Резерв], проверка
связи`, затем `🟢 [Резерв]` после трёх хороших тактов (первый зонд нового
слота — сразу, без ожидания интервала). Трафик всё это время идёт через
«NASPi».

### 8.3. Добавление резервного из моих устройств

Pi2 уже устройство админа (домашняя схема второй квартиры). `[📱 Из моих
устройств]` → выбор → подтверждение. Линк для слота новый по построению
(ключей у машины нет) → файл первого применения, руками. Устройство получает
пометку; его аплинк едет в бандле в форме для шлюза, как у первого.

### 8.4. Дом 1 упал, дом 2 жив

Три плохих замера активного (≈90 с), резерв к этому моменту давно `up ≥ 3` →
переключение, уведомление §7. Маркировка не снималась ни на такт; у клиентов
сменился адрес. Дом 1 вернулся → «снова в строю, остаётся в резерве». Вернуть
трафик домой — 6.6.

### 8.5. Оба упали

Активный `down ≥ 3`, кандидата нет → гашение, как сейчас, с добавкой про
резерв. Ожил любой из двух → он становится активным (если это резерв — через
шаг 3) и маркировка возвращается после трёх хороших.

### 8.6. Общая беда: ВПС потерял связь с обоими домами на минуту

Оба `down` синхронно, переключение невозможно (кандидата нет) → гашение;
через минуту оба `up` → активный остаётся прежним, маркировка вернулась.
Переключения не было — правильно: не было смысла.

### 8.7. Провайдер дома 2 дребезжит

Резерв то отвечает, то нет. На активный это не влияет; письмо «резерва нет»
уйдёт только после 10 мин подряд молчания и повторится не раньше, чем резерв
отработает и снова замолчит.

### 8.8. Ручной возврат домой

6.6 из карточки «NASPi» → «Да» → маршрут переложен, ответ на кнопку. Никаких
уведомлений отдельным сообщением: действие своё.

### 8.9. Замена машины в слоте

Как «Сменить шлюз» сейчас, но только для своего линка: `--rekey LINK_IF=…`,
прежняя машина теряет линк, новой — файл первого применения. Слот, галочка
предпочтительного, подсети, подпись сохраняются. Активный слот при замене: если жив второй —
автомат переключит по обычному порогу (три плохих), либо переключить руками
до замены; экран подтверждения об этом говорит.

### 8.10. Переезд профилей (смена подсети/порта ВПС)

Двойники получают слоты на финале (`gateways.device_id` → двойник по каждому
слоту), бандлы выпускаются по слоту, по два файла подряд с подписями. Пока
окно переезда открыто, `is_gateway_eff` через `twin_of` работает для обоих.

### 8.11. Запасной путь: токен от агента

Агент второго шлюза, не найдя пометки, шлёт `GW1:…`, подписанный ключом
**своего** линка. Основной бот перебирает ключи всех слотов, находит слот по
подписи и устройство по ключу аплинка. Устройство занято другим слотом →
отказ с указанием слота; слот занят другим устройством → «замени машину в
карточке шлюза».

### 8.12. Перезапуск бота, ребут ВПС

Активный — из состояния. Стрики — из состояния (как сейчас). Юниты
`awg-link@awglink`, `awg-link@awglink2` поднимают линки до старта бота. Первый
тик после старта — `ensure_policy()` доводит таблицы всех слотов.

### 8.13. Обслуживание дома 1

Карточка «Pi2» → «▶️ Переключить трафик сюда» → «Да». Трафик через дом 2,
«NASPi» в резерве. Выключаем малину, роутер, что угодно: через 10 мин придёт
«⚠️ Резервный РФ-шлюз «NASPi» не отвечает — резерва сейчас нет», это ожидаемо.
Подняли — «🟢 Резервный … снова отвечает». Карточка «NASPi» → «▶️ Переключить
трафик сюда» → «Да». Автомат в это не вмешивается: активный («Pi2») всё время
отвечал.

### 8.14. Холодный старт ВПС

ВПС перезагрузился, пока трафик шёл через «Pi2» (после отказа дома 1, который
давно ожил). Аптайм хоста меньше, чем прошло с последнего такта → холодный
старт → активный = предпочтительный «NASPi». Сессии людей и так были порваны
ребутом, письма об этом нет — только строка в журнале. Перезапуск одного бота
в той же ситуации оставил бы «Pi2».

### 8.15. Одинаковые подсети в двух квартирах

См. §4 и 6.3: маршрут предпочтительному, при равенстве — меньшему слоту,
предупреждение в карточке второго и в отчёте после ввода. У нас не случится:
подсети есть только у первого слота.

## 9. Что с агентом

Кода почти нет (v2.24.1 добавил одну проверку в монитор здоровья —
«маскарад в аплинк», см. ниже). Проверка списка:

- бандл несёт `LINK_IF` своего слота — скрипт обвязки шлюза ставит конфиг под
  этим именем, юнит `awg-link-gw.service` — тот же, один линк на машину;
- `GATEWAY_PUBKEY` — ключ аплинка устройства слота; ветка `foreign` (слот
  помечен другой машине) — сравнение с одним ключом, своим для бандла. Ключ
  ищется среди аплинков машины: сначала поднятые интерфейсы, затем конфиги ещё
  не поднятых (v2.24.2 — юнит обвязки стартует раньше `awg-quick@` аплинка, и
  по одним живым интерфейсам машина после ребута выглядела чужой). Линки до
  ВПС (`awglink*`) аплинками не считаются: их ключ принадлежит паре ВПС↔шлюз.
  Не нашли аплинка вовсе — состояние `unconfirmed`, линк не трогаем;
- `gateway.link_interface` в `app.yaml` агента — из бандла (уже так);
- токен — свой на каждого агента;
- панель агента про роль слота молчит (см. §2);
- **GitHub в аплинк** (v2.24.6): агент обновляется с releases, а в
  юрисдикции шлюза GitHub без туннеля недоступен — четыре сети GitHub
  (api.github.com/meta: web/api/git) идут той же меткой, что Telegram;
  агент проверяет набор `gh_nets4` по таблице, старой обвязке советует новый
  файл конфигурации;
- **маскарад в аплинк** (v2.24.1): локальный пакет агента выбирает исходный
  адрес до метки в output и без маскарада улетает в туннель с домашним
  адресом — ВПС его отбрасывает. На первой малине это лечило чужое правило
  домашней схемы; чистая вторая машина без него нема. Правило
  `oifname <аплинк> masquerade` ставит сам скрипт обвязки, агент проверяет
  его по своей таблице.

Единственное, что стоит добавить на будущее: в отчёт применения бандла —
строку «Слот: резервный» из переменной бандла. Это статическая информация на
момент выпуска, и она врать не будет, только устаревать; оставляю открытым
вопросом.

## 10. Безопасность

Ничего нового по классам угроз. Что проверить:

- бандл слота шифруется ключом **своего** линка: бандл дома 2 не расшифровать
  агенту дома 1 и наоборот;
- `ADMIN_IPS` одинаковы для обоих: устройствам админа открыт доступ в обе
  домашние сети, каждой — через свой линк;
- клиенты между домами не ходят: на шлюзе изоляция от приватных сетей
  прежняя, а на ВПС маршрут в домашние подсети есть только у устройств админа;
- второй порт UDP на ВПС — второй такой же след, не новый тип; обфускация у
  линков разная по построению (генерируется скриптом на каждый);
- ключи второго линка лежат там же и с теми же правами, что и первого.

**Релиз только основного бота**: `#requires_main_2.22.0`, `#awg_gen1`, вторая
цифра (v2.24.0): схема БД, обвязка ВПС, новый раздел. Сам v2.24.0 становится
минимумом для последующих релизов основного бота (миграция флага в таблицу).
Агент не адресуется; бандлы обоих слотов после обновления перевыпускать не
нужно, если слот один и линк не менялся.

Этапы задумывались так, чтобы каждый был полезен сам по себе и проверялся
в жизни; в код легли первые два целиком, третий — по итогам эксплуатации:

1. **Слоты и второй линк.** Таблица `gateways`, миграция, шаблонный юнит,
   второй линк, карточки, список, конфигурация по слоту, домашние подсети в
   UI, предпочтительный слот и холодный старт, пинг до шлюза и внешний IP с кэшем,
   зонд резерва и письма «резерва нет / снова отвечает». Переключение — только
   ручное (6.6), в обе стороны. Результат: резерв стоит, меряется, видно, что
   он живёт, обслуживание дома 1 уже возможно.
2. **Автомат.** Шаг 3 такта, интервал, уведомления о переключении, тумблер
   автопереключения. Результат: отказ дома переживается без человека.
3. **Мелочи по итогам эксплуатации:** подпись слота в панели агента, строка
   «слот» в отчёте бандла, всё, что вылезет на реальных переключениях.

Тесты по этапам: миграция флага (с шлюзом, без, в окне переезда); автомат
(таблица переходов из §5 — переключение, липкость, интервал, гашение без
кандидата, возврат через резерв); экраны (все ветки 6.1–6.11 с одним и двумя
слотами); скрипт линка — второй интерфейс не трогает первый, `--rollback` по
интерфейсу; бандл слота расшифровывается только своим ключом; одинаковые
подсети.

## 12. Открытые вопросы

Решённые по ходу реализации: стартовый выбор (предпочтительный при холодном
старте по моменту загрузки хоста, сохранённый при тёплом), пинг (с ВПС до
шлюза по линку, кэш лениво), зонд резерва (редко, с джиттером, живость по
хендшейку между зондами), порог переключения (скользящее окно, 50 %),
снятие активного при живом резерве (переключить молча по подтверждению).

Остаются:

1. **Максимум слотов.** Два (`gateways_max: 2`). Три — схема не ломается, но
   экраны и тексты рассчитаны на пару («резервный»); при трёх слово
   становится неточным.
2. **Порт второго линка.** 8443 по умолчанию, только ключ в `app.yaml`;
   спрашивать в диалоге назначения — лишний вопрос ради редкого случая.
3. **Уведомлять ли клиентов о переключении.** Сейчас нет (§7). Если да —
   одно короткое сообщение тем, у кого режим включён хоть на одном
   устройстве: «РФ-доступ переключён на резервный шлюз: приложения могут
   попросить войти заново».
4. **Интервал между автоматическими переключениями** — 10 мин. Меньше —
   качели при общей проблеме, больше — долгая деградация при настоящем втором
   отказе.
5. **Подпись слота в панели агента** и строка «слот» в отчёте применения
   бандла — агент кода не получал намеренно, по итогам эксплуатации.

### 13.3. Скрипт линка: `install/routing-link-setup.sh`

- Юнит-шаблон `/etc/systemd/system/awg-link@.service`:

  ```ini
  [Service]
  Type=oneshot
  RemainAfterExit=yes
  Environment=LINK_IF=%i
  ExecStart=/usr/local/sbin/routing-link-setup.sh --reassert
  ExecStop=/usr/local/sbin/routing-link-setup.sh --down
  ```

  Остановка — через скрипт, а не абсолютным путём к `awg-quick`: тулзы лежат
  там, куда положил make, и захардкоженный `/usr/bin` однажды не сошёлся —
  остановка падала, интерфейс жил, и реассерт не применял смену порта.
  Реассерт переподнимает поднятый линк, только если порт в ядре разошёлся с
  `ListenPort` конфига. Шаблон прежней версии бот перезаписывает при первом
  старте.

  `--apply` включает `awg-link@$LINK_IF`. Переезд первого слота на шаблон —
  в `--reassert`: при `LINK_IF=awglink` и живом `awg-link.service` он делает
  `systemctl disable awg-link.service`, удаляет старый юнит, `enable
  awg-link@awglink`, `daemon-reload`; интерфейс не трогается, он уже поднят.
  Реассерт зовёт юнит при загрузке, то есть сам по себе переезд случился бы
  только на первом ребуте ВПС. Ждать его незачем: бот на старте, увидев
  развёрнутую обвязку без шаблонного юнита, один раз зовёт `--reassert`
  явно (в `_after_start`, рядом с остальными тяжёлыми шагами).
- Пути по интерфейсу: `GW_CONF_OUT=/root/gw-$LINK_IF.conf` (уже так),
  `GW_BUNDLE_OUT`: для `awglink` — `/root/awg-gw-bundle.sh` (прежнее имя),
  для прочих — `/root/awg-gw-bundle-$LINK_IF.sh`.
- `LINK_VPS_ADDR`/`LINK_GW_ADDR` выводятся из `LINK_CIDR`, если не заданы:
  первый и второй адрес /30. Сейчас они три отдельные переменные с
  умолчаниями под первый слот; бот передаёт только `LINK_IF`, `LINK_PORT`,
  `LINK_CIDR`.
- `--rollback` снимает только свой `LINK_IF`: юнит `awg-link@$LINK_IF`,
  конфиг, `gw-*.conf`, бандл, исключение из MASQUERADE `-o $LINK_IF`.
- Проверка занятости порта — уже есть; для второго слота отработает
  штатно.
- `awg-bot gw-bundle [--link awglink2]` — `cmd_gw_bundle` передаёт
  `LINK_IF` в окружение скрипта; без аргумента — первый слот, как сейчас.

На стороне шлюза (`routing-gw-setup.sh`, бандл, установщик) — ничего.

```python
def routing_liveness_tick(self) -> list[Notification]:
    if not routing.available(): return []
    engaged = self.routing_engaged()
    slots = self.db.gateways()
    if not slots: return []                      # шлюза нет — как сейчас при отсутствии
    active = self.active_gateway() or slots[0]
    results = {}                                 # slot_id → (verdict, ms)
    if engaged:

    with self.db.transaction():
        if not engaged: сброс всех стриков, ok=False   # решение, не измерение
        else:

    set_marking_enabled(ok) под замком, как сейчас
```

### 13.7. Порядок работ

тестами до следующего. Этап 2 — только 13.4 (такт) и тексты уведомлений.
