# Доступ между подсетями за шлюзами — концепт

Статус: **на вычитку** (19.09.2026). Продолжение `docs/gateway-failover.md`:
те же слоты, те же линки, тот же агент. Новой сущности нет — всё выводится из
`home_subnets`, которые у слота уже есть.

Исходная ситуация: две квартиры, две малины, у каждой своя домашняя подсеть
(192.168.1.0/24 и 192.168.68.0/24), обе — шлюзы слотов. Цель: из любой
квартиры доставать до устройств другой по настоящим адресам, без маскарада и
без правок на роутерах. Трафик идёт через ВПС по двум линкам.

---

## 1. Суть

**Никакой новой сущности.** У слота есть `home_subnets` — «что стоит за этим
шлюзом». Для слота N *чужие подсети* — объединение `home_subnets` всех
остальных слотов. Слот один — множество пустое, поведение не меняется.

**Не «связь квартир», а «доступ между подсетями за шлюзами».** Бот не знает,
зачем это нужно; он знает, что за каждым шлюзом есть подсети, и делает так,
чтобы каждая была достижима из-за любого другого шлюза. Ровно то же, что уже
делается для устройств админа на ВПС, продолженное на шаг дальше.

**Что не меняется:** конфиги устройств, клиенты, условная маршрутизация,
автомат переключения, домашняя схема на малинах (`home_split`). Доступ между
домами не зависит от того, какой шлюз активен: линки подняты постоянно, оба.

**Что нужно от домашнего слоя:** ничего. Ни один его файл в схеме не
участвует. Единственная предпосылка — устройства в квартире и так отправляют
пакеты в чужие приватные сети через малину (она у них шлюз по умолчанию или
на роутере стоит маршрут). Это и сейчас так в обеих квартирах.

---

## 2. Как ходит пакет

Пакет 192.168.1.5 (дом 1) → 192.168.68.7 (дом 2). Обратно — зеркально.

```
дом 1: 192.168.1.5 ──► Pi4 (end0)
   forward, policy accept; маскарада нет (saddr ∉ tunnel_nets4)
   маршрут 192.168.68.0/24 dev awglink        ← из AllowedIPs, ставит awg-quick
   криптофильтр awglink: 192.168.68.0/24 ∈ AllowedIPs пира ВПС   ← НОВОЕ
              │
              ▼ awglink
ВПС: криптофильтр пира Pi4 = 0.0.0.0/0          ← уже так, Table = off
   forward (awg_bot_guard, policy drop): iifname awglink oifname awglink2 accept   ← НОВОЕ
   маршрут 192.168.68.0/24 dev awglink2 (main)  ← уже так, ensure_home_routes
   маскарада нет (saddr ∉ tunnel_nets4); MSS-кламп на awglink2 — уже стоит
              │
              ▼ awglink2
дом 2: криптофильтр awglink2 у Pi5 (пир ВПС): CLIENT_SUBNET, LINK_CIDR
   + 192.168.1.0/24                              ← НОВОЕ (иначе пакет отброшен)
   forward (awg_gw_guard): iifname awglink2 ip saddr @peer_nets4 accept   ← НОВОЕ,
       выше iifname awglink2 ip daddr @private4 drop
   маскарада нет (saddr ∉ tunnel_nets4) → 192.168.68.7 видит 192.168.1.5
              │
              ▼ end0 → 192.168.68.7
ответ: 192.168.68.7 → шлюз по умолчанию (Pi5) → маршрут 192.168.1.0/24 dev awglink2 → …
```

Где что уже есть и что добавляется — по компонентам в §3. rp_filter на обеих
сторонах не мешает: обратный маршрут в подсеть-источник ведёт в тот же
интерфейс, откуда пакет пришёл.

Что из разговора оказалось не так: AllowedIPs пира шлюза **на ВПС** менять не
нужно — там `0.0.0.0/0` при `Table = off` с самого начала (иначе ВПС не мог бы
слать в линк произвольные адреса назначения). Серверная сторона принимает
всё, маршрутизирует по main-таблице, а домашние подсети в неё уже кладёт
`ensure_home_routes`. Не хватает только форвардинга линк ↔ линк.

## 3. Что меняется, по компонентам

### 3.1 ВПС: форвардинг между линками (`nftguard.py`)

В `chain forward` таблицы `awg_bot_guard` (policy drop) сейчас:
established/related, invalid drop, пир → пир только устройствам админа,
`saddr/daddr @tunnel_nets4 accept`. Пакет из awglink в awglink2 не подходит ни
под одно — падает в policy.

Добавляется, когда линков два и больше:

```
iifname { "awglink", "awglink2" } oifname { "awglink", "awglink2" } accept
```

Без наборов подсетей — намеренно. В линк со стороны шлюза попадает только то,
что пропустил его AllowedIPs (чужие подсети, клиентская подсеть, /30 линка),
список линков `nftguard` и так знает (`link_ifaces()`, по `Table = off`), а
таблица собирается и из CLI `awg-bot firewall`, где БД нет. Правило ставится
выше `saddr @tunnel_nets4`, после `invalid drop`.

При выключенном файерволе (форма NAT-only) фильтра нет — форвардинг решает
политика хоста, как и сейчас для всего остального.

Маскарад: `ip saddr @tunnel_nets4 oifname != {…} masquerade` — 192.168.x в
`tunnel_nets4` нет, не маскарадится. Маршруты: `ensure_home_routes` уже
кладёт каждую домашнюю подсеть в линк её слота в main-таблицу. MSS-кламп на
каждом линке уже стоит.

### 3.2 Конфигурация шлюза: AllowedIPs пира ВПС (`routing-link-setup.sh`)

Сейчас у пира ВПС в конфиге шлюза `AllowedIPs = $CLIENT_SUBNET, $LINK_CIDR`.
Добавляются чужие подсети:

```
AllowedIPs = $CLIENT_SUBNET, $LINK_CIDR, 192.168.1.0/24
```

Тогда `awg-quick up` на шлюзе сам ставит маршрут (у конфига шлюза `Table` не
выключен), ручной `ip route add` больше не нужен, а после ребута маршрут
возвращается вместе с линком.

Механика: бот передаёт скрипту линка `PEER_HOME_NETS="192.168.1.0/24 …"` в
окружении сборки бандла (рядом с `ADMIN_IPS`, `GATEWAY_PUBKEY`); скрипт в
`--bundle` правит строку `AllowedIPs` в `$GW_CONF_OUT` — по образцу правки
`Endpoint` под живой порт. `--apply`/`--rekey` пишут строку сразу с учётом
переменной. Шапка бандла получает `PEER_HOME_NETS` (фильтр `0-9./ `, как у
`ADMIN_IPS`), скрипт обвязки читает её из окружения и закрепляет в юните
`awg-link-gw.service` — так же, как `ADMIN_IPS`.

Конфиг линка изменился → агент при применении предупреждает про обрыв на
секунды (уже так: `inspect_bundle` → `link_changed`), скрипт переподнимает
линк.

### 3.3 Шлюз: `guard.nft` (`routing-gw-setup.sh`)

Новый набор и одно правило в `chain forward`, выше drop по приватным:

```
set peer_nets4 { type ipv4_addr; flags interval; elements = { $PEER_HOME_NETS } }

chain forward {
    oifname "$LINK_IF" ct state established,related accept
    iifname "$LINK_IF" ip saddr @admin4 accept
    iifname "$LINK_IF" ip saddr @peer_nets4 accept        ← НОВОЕ
    iifname "$LINK_IF" ip daddr @private4 drop
    iifname "$LINK_IF" accept
}
```

По **источнику**, не по назначению: пакет из чужого дома опознаётся тем,
откуда он, а куда именно в этом доме ему можно — «полный доступ», то есть
везде. Пустой `PEER_HOME_NETS` → пустой набор, правило не срабатывает,
поведение как сейчас.

**Сама малина** (не транзит, а `input`): `ip saddr @tunnel_nets4 jump
tunnel_in` — чужих подсетей в `tunnel_nets4` нет, пакет идёт в policy accept.
То есть с той стороны доступна и сама малина (SSH, её сервисы), как из своей
квартиры. Это и есть «полный доступ»; если когда-нибудь понадобится
ограничить — одно правило `ip saddr @peer_nets4 jump tunnel_in` с `admin4`
внутри. Открытый вопрос §9.

**Маскарад в LAN не ставится** — намеренно: `ip saddr @tunnel_nets4 oifname
"$WAN_IF" masquerade` чужие подсети не трогает, устройства в квартире видят
настоящие адреса второй квартиры. Цена — предпосылка из §1: ответ из LAN
должен дойти до малины (она шлюз по умолчанию, или на роутере маршрут в чужую
подсеть через малину). В обеих квартирах это уже так.

Агент проверяет набор по таблице, как проверяет `admin4`: набор `peer_nets4`
против `PEER_HOME_NETS` из юнита (`unit_admin_ips` → тот же приём). Проверка
«подсети за другими шлюзами» появляется в мониторе здоровья только когда
переменная в юните непустая; расхождение — «перевыпусти конфигурацию».

### 3.4 Бот: валидация домашних подсетей

Сейчас совпадение подсети у двух слотов — предупреждение в карточке и в
отчёте ввода («маршрут достаётся первому»). Становится **отказом при вводе**,
как только слотов два и больше: одинаковые или вложенные подсети у разных
слотов маршрутизировать в разные линки нельзя физически, а с доступом между
домами вложенность ещё и молча увела бы часть чужого дома в свой линк.

Проверка — `overlaps()`, не равенство: ловит и 192.168.0.0/16 против
192.168.1.0/24. Отказ по строке, как прочие отказы разбора:
«пересекается с 192.168.1.0/24 у «Pi4» (дом 1)».

Данные, введённые до этой версии, не трогаем: если пересечение уже есть,
карточка показывает то же ⚠️, что сейчас (текст обновлён, §6), а в чужие
подсети такая пара не попадает (§3.5). Починить — сменить подсеть в одной из
квартир; это всё равно единственное, что тут можно сделать.

### 3.5 Бот: вычисление чужих подсетей

`gateway_peer_nets(slot_id) -> list[str]`: `home_subnets` всех слотов, кроме
`slot_id`, в порядке слотов, без дублей, **исключая** те, что пересекаются с
собственными `home_subnets` слота (легаси-пересечение до валидации — §3.4).
Клиентская подсеть и подсети линков попасть не могут — их отбрасывает ввод.

Используется в двух местах: окружение сборки бандла (`_gw_bundle_env` →
`PEER_HOME_NETS`) и снимок зависимостей бандла (§4).

## 4. Перевыпуск конфигурации

Конфигурация слота N теперь зависит от чужих слотов. Что её меняет:

| событие | чья конфигурация устарела |
|---|---|
| изменены `home_subnets` слота N | всех остальных слотов |
| добавлен слот с непустыми `home_subnets` | всех остальных |
| снят слот с непустыми `home_subnets` | всех остальных |
| изменён состав устройств админа (как сейчас) | всех |

Механизм — тот, что есть: при сборке бандла слота запоминается снимок
зависимостей, тик сравнивает и напоминает один раз на расхождение. Сейчас
снимок — только `ADMIN_IPS` (`gw_bundle_ssh_allow_{slot}`); расширяется до
`ADMIN_IPS` + `PEER_HOME_NETS` (ключ `gw_bundle_deps_{slot}`; старый ключ
читается как снимок без чужих подсетей). После обновления напоминание придёт
обоим слотам сразу — и это правильно: до перевыпуска у шлюзов чужих подсетей
нет, а у бота есть, расхождение настоящее. Один раз на слот.

Напоминание про чужие подсети — своим текстом (§6), не «список устройств
изменился».

Снятие слота: `gateway_remove` уже перевыпускает первый слот при снятии
второго (`rekey slot 1`); чужие подсети первого слота при этом пустеют сами
собой, потому что считаются на момент сборки.

## 5. Экраны

Новых экранов нет. Меняются три текста и появляется одна строка.

**Карточка слота** — после строки домашних подсетей, только когда у слота
есть чужие подсети:

```
🏠 Домашние подсети: 192.168.68.0/24
Устройства админа достают до них через этот линк.
🔀 Из-за других шлюзов сюда: 192.168.1.0/24 («Pi4», дом 1) — и обратно.
```

**Ввод домашних подсетей** (`gateway_home_text`) — абзац о том, что подсети
становятся достижимы и из-за других шлюзов.

**Отчёт после ввода** (`gateway_home_report`) — если слотов больше одного,
строка о перевыпуске конфигурации остальных.

**Экран «Конфигурация шлюза»** (`ROUTING_BUNDLE_INTRO`, п.1) — в перечень
того, что внутри, добавляется «подсети за другими шлюзами».

> (дом 1) и примени на той стороне.

## 7. Эксплуатация

- **Задержка** ~150 мс туда-обратно: дом → ВПС → дом. Для SSH, веб-панелей,
  файлов — незаметно; для чего-то интерактивного по UDP — терпимо.
- **Живёт, пока подняты оба линка.** Резервный шлюз тоже держит линк
  постоянно, но если его квартира без связи — доступа в неё нет, и это не
  поломка. Автомат переключения к этому отношения не имеет: доступ между
  домами не зависит от того, чей линк несёт клиентский трафик.
- **Пропускная способность** — минимум из двух домашних аплоадов, через ВПС.
- **Проверка после раскатки** — по шагам, с пингом после каждого:
  1. обновить основного бота: появляется форвардинг линк ↔ линк на ВПС;
     `nft list chain inet awg_bot_guard forward` показывает правило;
  2. перевыпустить конфигурацию обоих слотов, применить на каждой малине;
     `awg show awglink2 allowed-ips` на Pi5 показывает 192.168.1.0/24,
     `ip route get 192.168.1.5` — через awglink2;
     `nft list set inet awg_gw_guard peer_nets4` — чужая подсеть;
  3. `ping 192.168.68.7` с устройства в доме 1; ответ приходит — готово;
     нет ответа при живом линке — смотреть, доходит ли ответ до малины
     (`tcpdump -i end0 icmp` на Pi5): не доходит — маршрут в LAN (§1).

## 8. Реализация — план

1. `gateway_link.py`: `gateway_peer_nets()`, `PEER_HOME_NETS` в `_gw_bundle_env`,
   снимок зависимостей бандла `gw_bundle_deps_{slot}` и напоминание своим
   текстом; валидация пересечений в `gateway_set_home_subnets` (отказ при
   ≥2 слотах, `overlaps`).
2. `routing-link-setup.sh`: `PEER_HOME_NETS` в AllowedIPs конфига шлюза
   (`--apply`, `--rekey`, правка в `--bundle`), переменная в шапке бандла.
3. `routing-gw-setup.sh`: `PEER_HOME_NETS` → юнит, набор `peer_nets4`,
   правило accept в forward выше drop; `--plan` перечисляет.
4. `nftguard.py`: правило линк ↔ линк в forward при ≥2 линках.
5. Агент: проверка набора против юнита (`gwguard.unit_peer_nets()`), в
   `plumbing_checks` только при непустой переменной.
6. Тексты §6, карточка, экран конфигурации; `render_gateway_texts.py`.
7. Тесты: вычисление чужих подсетей (один слот, два, легаси-пересечение),
   отказ ввода при пересечении и вложенности, окружение бандла, строка
   AllowedIPs после `--bundle` (скрипт линка гоняется по-настоящему, как в
   `test_bundle_header_carries_gateway_fields`), набор и порядок правил в
   guard, правило forward на ВПС, напоминание один раз, тексты.
8. Версия: третья цифра (v2.24.7) — новая функциональность внутри той же
   фичи; адресаты обе роли (бандл, агент). Обеим малинам — перевыпуск и
   применение конфигурации.

## 9. Открытые вопросы

1. **Доступ к самой малине с той стороны.** Сейчас — полный (input policy
   accept). Оставить, или пускать только устройства админа, как из туннеля?
   Предлагаю оставить: «полный доступ» так и звучит, а обе квартиры — свои.
2. **Маскарад в LAN как запасной режим.** Если в какой-то квартире малина не
   шлюз по умолчанию и маршрут на роутере поставить нельзя, спасёт
   `ip saddr @peer_nets4 oifname "$WAN_IF" masquerade` — ценой настоящих
   адресов. Не делаю; если понадобится — флаг слота, не глобальный.
3. **Три слота.** Схема обобщается сама (объединение остальных), потолок
   `gateways_max` = 2, менять не предлагаю.
4. **IPv6** — нет, как и везде в фиче.
