# Выпуск релиза

Как нумеруется версия, что стоит в метаданных релиза и в шапке записи
журнала и в каком порядке собирается и выкладывается релиз. Документ —
источник правил; журнал — `docs/CHANGELOG.md`, метаданные —
`docs/releases/vX.Y.Z.P.json`, поставка — `build_release.sh`.

---

## 1. Номер версии: X.Y.Z.P

Четыре цифры. Поднимается ровно одна, младшие обнуляются.

| цифра | когда поднимается |
|---|---|
| **X** — ведущая | новая зона ответственности приложения; глобальные, возможно обратно несовместимые изменения; архитектурный скачок; функционал, по объёму сопоставимый с половиной проекта |
| **Y** — мажор | новый функционал; ощутимые обратно несовместимые изменения — смена схем таблиц, существенные (но не глобальные) изменения архитектуры; значительные изменения UI/UX; крупный рефакторинг |
| **Z** — минор | незначительные изменения существующего функционала; правки UI/UX, не ломающие принципы взаимодействия; микрофичи, которые чуть упрощают существующие паттерны или чуть расширяют их зону влияния; точечный рефакторинг |
| **P** — патч | точечные хотфиксы; точечные правки оптимизации или логики существующего функционала; косметика UI — переписывание текстов и заголовков, смена эмодзи, перефразирование и дополнение текстов |

Версия одна на обе роли (основной бот и агент шлюза): поставка одна.
Четвёртая цифра в номере не пишется, когда она ноль (`3.0.0`, не `3.0.0.0`).
Номер выбирается по **самому крупному** изменению среди вошедших в релиз
коммитов: одна смена схемы БД среди десяти правок текстов — мажор.

Где живёт номер: `awgbot/__version__.py` (`__version__ = "X.Y.Z.P"`), тег
`vX.Y.Z.P`, заголовок записи журнала `## vX.Y.Z.P — …`, заголовок релиза на
GitHub `vX.Y.Z.P — …`.

---

## 2. Метаданные релиза и шапка записи журнала

Условия обновления — адресаты, минимумы, поколение ядра и условия на версию
другой роли — едут **метаданными релиза**: второй ассет `awg-bot-release.json`
рядом с `awg-bot.tgz` (бот читает его до скачивания поставки; целостность —
`assets[].digest`, как у поставки). Источник — файл в репозитории
`docs/releases/vX.Y.Z.P.json`; его пишет `tools/release_meta.py` (§4, шаг 3).
Схема 1:

```json
{
  "schema": 1,
  "version": "3.3.1",
  "awg_gen": 1,
  "roles": {
    "main": {"requires": "3.3.0", "needs_gw": "3.3.0"},
    "gw":   {"requires": "3.3.0", "needs_main": "3.3.0"}
  }
}
```

- `version` — номер релиза без `v`, обязан совпасть с тегом (иначе бот
  считает ассет битым); `awg_gen` — `AWG_GENERATION` из `install/awg.lock`.
- `roles` — адресаты: есть ключ роли — релиз ей адресован (`main` —
  основной бот, `gw` — агент шлюза); правила, кому ставится, — те же, что
  у строк `#requires_*` ниже. `requires` у роли обязателен — минимум.
- `needs_gw` — только у `main`: серверу этого релиза нужны шлюзы не ниже X;
  `needs_main` — только у `gw`: агенту нужен сервер AWG не ниже X. X — три
  цифры, и это версия, которая той роли была адресована и раскатана.
  Ставятся по явной строке коммита (§3); нет строки — нет условия. Условие
  идёт по цепочке (релиз допустим, если выполнены условия всех релизов роли
  от установленного до него), поэтому **у хотфикса X.Y.Z.P `needs_*` нет**:
  условие базы держит и её хотфиксы. С 3.4.0 условие — **правило порядка**
  хода набора обновлений (README §9a): `needs_gw` — сервер обновляется
  после шлюзов (держат его только шлюзы на связи), без него — сервер первым,
  затем шлюзы; `needs_main` агент проверяет сам, получив команду, и при
  обычном порядке оно выполнено по построению. Неверно поставленное условие
  не блокирует кнопку, а откатывает набор («нужен сервер AWG новее»), поэтому
  его ставят только там, где другая сторона без него действительно не
  работает.
- **Закрытый список настроек шлюза** (`awgbot/domain/gwkeep.py`: `CONF_KEYS`,
  `FW_KEYS`, `MAIL_KEYS`, пределы и отпечаток) обязан совпадать у сервера и
  агента: при разных списках отпечатки блока расходятся, и агент шлёт свой
  блок на каждом такте, а сервер задаёт вопросы о «других» настройках. Любая
  правка списка — релиз обеим ролям с условием: `needs_main` у `gw` (и
  `needs_gw` у `main`, если сервер без нового списка ломает агентов) на
  версию, где список уже новый.
- Нет ассета у релиза с 3.3.2 или ассет битый (`digest`, JSON, схема,
  `version`) — бот релиз не рассматривает, и он становится барьером: обе
  роли берут цель только ниже него (раздел «⬆️ Обновления»: «пропущен:
  метаданные релиза не прочитаны»). Поэтому релиз без метаданных — не
  косметика, а остановка обновлений у всех, кто ниже. Новые поля — только
  добавлением с тем же номером схемы; смена номера — через релиз, который
  читает оба. Неизвестные роли в `roles` бот пропускает (нужна хотя бы одна
  из `main`, `gw`); опечатку в имени роли ловят инструмент и сторож журнала.
- **Откуда брать текущие значения.** С 3.3.0 текущий минимум роли — `requires`
  в последнем файле `docs/releases/vX.json`, адресованном этой роли (а не в
  теле записи журнала); поколение ядра в метаданные ставит инструмент из
  `install/awg.lock`, руками его не пишут.

**Переход с хэштегов тела.** Боты 3.2.x метаданных не читают — им адресатов
по-прежнему говорят первые строки записи журнала:

```
## vX.Y.Z.P — заголовок одной строкой

#requires_main_A.B.C
#requires_gw_D.E.F
#awg_genN

текст…
```

- **3.3.0 и 3.3.1** (и их хотфиксы) — метаданные **и** эти строки в теле,
  совпадающие с метаданными (`python -m tools.release_meta --hashtags
  docs/releases/vX.json` печатает их), — только в первом блоке записи: бот
  3.2.x ищет хэштеги по всему телу, и строка в тексте тоже стала бы для него
  адресатом.
- **Ступень перехода — правило, а не совпадение.** Первый релиз после 3.3.0
  до первого ≥ 3.3.2 (3.3.1 или хотфикс 3.3.0.P) адресуется **обеим ролям с
  минимумом 3.3.0** (`--main 3.3.0 --gw 3.3.0`) — независимо от задетого
  кода и матрицы адресатов ниже. Именно эта ступень держит старых
  читателей: хост 3.2.x любой роли видит релизы с 3.3.2 «общими без
  минимума», и только минимум 3.3.0 в цепочке опустит его на 3.3.0, откуда
  он пойдёт читателем метаданных. Сторож журнала требует её для каждой
  роли, как только в журнале появится запись ≥ 3.3.2. Снимать её с GitHub
  нельзя.
- **С 3.3.2** — только метаданные; тело записи — только для людей, машинных
  строк в нём нет.
- Условий на другую роль в теле нет никогда — они только в метаданных
  (строки вида `#gw_needs_main_…`, `#main_needs_gw_…`, `#needs_…` сторож
  журнала считает ошибкой).

  ради `I1` — `gateway_link/linki1.py`, `gateway_link/rekey_i1.py` (в пакете

  первого применения с 3.4.0 нет, ВПС этот скрипт не зовёт (кит везёт его
  в составе своей поставки, той же версии, что сервер) — строка `gw`; скрипт обвязки на шлюзе всегда той же версии,
  что агент. Если правка должна встать на шлюзе сразу, а не со следующим
  запуском, — отдельной строкой сказать: «🚑 Восстановить» в чате бота шлюза
  после обновления агента; строки юнита обвязки (`ADMIN_IPS`,
  `LAN_SUBNETS`, …) доезжают каналом документом конфигурации.
  Режимы `--link-apply`, `--uplink` и `--join` этого скрипта зовёт агент, а
  белые списки для них лежат в `install/gw-wg-allow.list` (`--join` — тем же
  разделом `link`, только `AllowedIPs` — /30 линка) — правку списка адресуют
  обеим ролям (см. ниже).
  Канал ВПС ↔ шлюз внутри линка разложен по ролям так: `runtime/linkserver/`
  и `domain/services/gwchannel/` живут только на ВПС — строка `main`;
  `runtime/linkclient/` только на шлюзе — строка `gw`. Но `util/gwlink.py`
  (конверт и подпись), `domain/gwsnapshot.py` (состав снимка) и общие модули
  данных, которые ездят каналом, — `domain/gwservices.py` (сервисы соседних
  сетей), `domain/gwownlists.py` (свои списки, общие для шлюзов),
  `domain/gwcfg/` (формат документа конфигурации и ответа на него, проверки,
  отпечатки), `domain/gwkeep.py` (закрытый список и отпечаток настроек шлюза
  в бэкапе сервера), `util/wgconf.py` (разбор конфигов WireGuard, белые списки,
  правило `AllowedIPs`) и данные к нему `install/gw-wg-allow.list` (их же
  читают `--link-apply` и `--uplink` скрипта обвязки на шлюзе) — **обе роли**:
  формат обязан совпадать на концах линка, и обновлённая половина со старой
  разговаривать не будет, даже если видимая часть правки на одной стороне.
  Новый вид сообщения канала (фиды, роль, раздел документа конфигурации,
  команда набора `upd` — `runtime/linkserver/upd.py` и `runtime/linkclient/upd.py`,
  сопряжение — `hello` с полями `join`/`eph`/`host`, `join_eph`, `join_wrong`,
  `join_refused`, `join_ok`, итог `join_done`/`join_done_ok` в
  `runtime/linkserver/join.py`, `inbound.py` и `runtime/linkclient/join.py`,
  `dispatch.py`)
  живёт в `linkserver/` и `linkclient/` разом: старая половина его пропускает,
  не рвя сессию, но и не выполняет. Такой релиз адресуют обеим ролям, а в теле
  записи для основного бота говорят, что агента шлюза нужно обновить следом.
  Сессия сопряжения возможностей не объявляет (`join1` есть только в `hello`
  полного агента): агент, подключаемый командой, стоит ровно на выпуске,
  который назвал сервер в токене, — поэтому правку её сообщений и формата
  токена адресуют обеим ролям одним релизом.
  Взаимный резерв серверов AWG (с 4.0.0) разложен так. Только основной бот —
  строка `main`: сервисный слой `domain/services/reserve/`, канал пары
  `runtime/pairlink/`, задания `runtime/scheduler/reserve.py`, раздел
  «🛟 Резерв» `handlers/settings/reserve/`, экран админа второго сервера
  `handlers/peeradmin.py`, тексты `bot/texts/reserve/` и клавиатуры
  `keyboards/reserve.py`, слияние `domain/backup/merge/reserve.py`,
  `domain/services/selfhost.py` (собственный адрес сервера для линков
  шлюзов и токена подключения), пакет переезда `util/rsvpkg/`, приглашение в
  пару `util/pairtoken.py`, API провайдеров DNS `util/dnsapi/`, сетевые
  пространства `util/netns.py` и скрипты зоны и пары
  (`install/reserve-zone-setup.sh`, `install/reserve-pair-setup.sh`): их не зовёт ни один агент, и общее
  правило «`util/…` — обе» к ним не относится. Туда же — пакет переезда
  (сборка у основы и приём у резерва — `domain/services/reserve/package.py`),
  бот основы на резерве (`config.GUEST`: `domain/services/reserve/guest.py`,
  `runtime/main/guest.py`, `runtime/webhook.py`, локальный канал
  `runtime/pairlink/guestctl.py`, планировщик `runtime/scheduler/guest.py` и
  вынесенные из основного задания данных клиентов `runtime/scheduler/jobs.py`,
  `bot/handlers/guest.py`, тексты `bot/texts/reserve/guest.py`), слияние при
  возврате (`domain/backup/merge/policy.py`, `reserve.py`), процесс открытия
  `tools/rsvopen.py`, сторож обновления и восстановления `tools/rsvbusy.py` (его зовёт общий
  `install/lib/update.sh` на обеих ролях, но у агента пары нет — он всегда «свободен»), обёртка зоны `infra/rsvzone.py` и файервол резерва в
  `infra/nftguard/`. Туда же — запись DNS, переезд кнопкой и возврат:
  автоматы `domain/services/reserve/{dns,outbound,outbound_return,merge_ops,inbound,openproc,notify,traffic,away}.py`,
  уведомления `domain/notices/reserve.py`, управляемый поллинг `runtime/pollctl.py`
  (право отвечать в Telegram) и исполнитель действий `runtime/rsvactions.py`,
  экраны `handlers/settings/reserve/{move,dns}.py`. Туда же — шлюзы и переезд
  по взглядам: стороны основы и резерва
  `domain/services/reserve/{gwside,zonelinks,vote,codewin,rfblock}.py` (ключи шлюзовых сторон, `slots`/`slots_ok`,
  стороны зоны, матрица случаев, демпфер, `ask`/`ask_no`, аварийный код),
  слушатель гостевого канала в зоне `runtime/pairlink/guest.py`, ввод кода в
  роли админа второго сервера `handlers/peercode.py`, ключи без `awg genkey`
  `util/wgkeys.py` (его зовёт только сервер). Туда же — РФ-доступ в зоне и
  пул адресов Telegram: `domain/services/reserve/{rfzone,tgpool,peeradmin}.py`,

  `domain/services/routing/`), кэш списков в пакете (`util/rsvpkg/bot.py`),
  экран роли общего админа (`bot/filters.py` — `PeerAdminFilter`,
  `handlers/settings/reserve/card.py`). Правка `jobs.py` задевает и обычный основной бот (те же
  задания), но не агента. `bot/middleware.py` и `core/access_cache.py` (роль
  админа второго сервера и его «👤 Меню клиента» на полчаса) собирают обе роли —
  их правка, как всякий общий код, адресуется обеим, даже когда меняет только
  поведение основного бота. **Только агент** — строка `gw`: скрипт линка к
  резерву `install/reserve-gw-setup.sh` (на ВПС его не зовут; на шлюзе юнит
  `awg-rsv-gw.service` выполняет копию в `/usr/local/sbin`, которую кладёт сам
  скрипт при `--up`), его обёртка `infra/gwguard/rsv.py` и клиент гостевого
  канала `runtime/guestlink.py`. **Обе роли**: код агента
  `domain/gateway/reserve/` вместе с разделом `reserve` документа
  конфигурации (`domain/gwcfg/`, белый список `rsvlink` в
  `install/gw-wg-allow.list`), полем `rsv` снимка (`domain/gwsnapshot.py`),
  пробой `ping`/`pong` канала конфигурации (`runtime/linkserver/inbound.py` и
  `runtime/linkclient/dispatch.py`), машиной живости `util/livestep.py` и словарём сообщений
  пары и гостевого канала `util/pairproto.py` (гостевым каналом говорят
  агенты; поля `st`, добавленные внутри линии, — необязательные
  (`pairproto.OPTIONAL`), поэтому старая сторона их не отвергает), ключи и доли — `util/shamir.py`, `util/rsvkeys.py` (доля шлюза
  едет в разделе `reserve`), месячный накопитель `util/monthacc.py` (им
  копят трафик линка агент и трафик через резерв сервер) — формат обязан
  совпадать на концах, как у канала. Блок `reserve` в `conf/app.yaml` и
  ключ `network.self_host` — шаблон конфига, общий для поставки; читает их
  основной бот, а ключи резерва в разделе `gateway` (`reserve_suspect_seconds`,
  `reserve_probe_seconds`, `guest_channel_port`, `rf_block_minutes`) — агент. Стенд `tests/lab/` (в том числе сценарии зоны) в поставку хостов не входит — адресата
  у его правки нет.
- Число в строке — **минимальная версия роли**, с которой на этот релиз
  прыгают напрямую; хост ниже сначала обновляется на неё. Минимум — только
  версия, которая этой роли была адресована и раскатана. Минимум сдвигается,
  когда релиз ломает совместимость (схема БД, снятие шимов) — и тогда сама
  ступень-минимум должна быть адресована обеим ролям. Текущие минимумы —
  до 3.3.0 в последних записях журнала, с 3.3.0 — в последнем
  `docs/releases/vX.json`, адресованном роли; о сдвиге объявляется явно
  при выпуске. С 3.3.1 минимум обеих ролей — **3.3.0**, и условия на другую
  роль тоже 3.3.0 (`needs_gw`, `needs_main`): сервер 3.3.1 снял файл
  перевыпуска и доставку отдельных настроек по каналу, агент 3.3.1 — работу
  с сервером без документа конфигурации. Хост 3.2.x поэтому идёт через 3.3.0,
  а 3.3.0 уже читает метаданные — переход с 3.3.2 только на метаданные
  (строк в теле нет) никого не оставляет без пути. Шаги перехода, которые
  3.3.1 ещё держит ради пары 3.3.0 ↔ 3.3.1 (чтение прежних имён юнита и
  таблицы `awg_home`, поля `bundle.home_*` в снимке, ручной приём
  пересланного токена пометки), снимаются со следующим сдвигом минимума.
- **4.0.0** (вычистка контейнерного режима и взаимный резерв серверов)
  адресуется **обеим ролям**: код меняют обе (резерв — у основного бота и у
  агента, раздел `reserve` документа конфигурации, общий словарь пары), и
  выпуск поднимает версию совместимости (ниже). **Минимумы не двигаются**:
  строк «минимум … →» в коммитах нет, `requires` у `main` и `gw` — прежние,
  **3.3.0** (последний `docs/releases/v3.4.0.json`), то есть `--main 3.3.0
  --gw 3.3.0`. Условий на другую роль у 4.0.0 нет (`needs_*` не ставятся):
  сервер 4.0.0 со шлюзом ниже 4.0.0 работает, шлюз только не голосует и не
  держит долю ключа; агент 4.0.0 с сервером 3.4.x — без раздела `reserve`.
  Машинных строк в теле записи (`#requires_*`, `#awg_genN`) нет — с 3.3.2
  только метаданные; поколение ядра (`awg_gen`) инструмент берёт из
  `install/awg.lock`.
- `#awg_genN` / `awg_gen` — поколение AmneziaWG в поставке
  (`install/awg.lock`); по нему боты решают, нужен ли переезд профилей и
  можно ли обновляться сразу.
- Формат сторожит `tests/unit/test_changelog_format.py`: адресаты и
  минимумы (`test_required_floor_is_a_release_that_role_actually_received` —
  и по метаданным), у каждой записи с 3.3.0 есть `docs/releases/vX.json`,
  строки тела у 3.3.0–3.3.1 совпадают с метаданными, с 3.3.2 их нет, `needs_*`
  — версия, адресованная той роли
  (`test_metadata_and_bodies_agree_with_the_transition_rule`); каждый файл
  `docs/releases/` — по схеме и с версией из имени.

Тело записи — по пунктам, каждый пункт называет проблему и что изменилось;
для агента и для основного бота, если релиз адресован обоим, — что везёт
каждый.

**Версия совместимости и бэкапы.** Минимум роли говорит, с какой версии на
релиз прыгают; версия совместимости — `COMPAT_FLOOR` в `awgbot/core/compat.py`,
одна константа на код и `awg-bot.sh`, — ниже какой версии установка не
возвращается и чьих бэкапов не принимает: бэкап ниже неё не применяется, а
`awg-bot update` на поставку ниже неё отказывает до остановки сервиса (откат —
только чистой установкой). С 4.0.0 она — **4.0.0**: раздел `app.yaml`
`docker:` стал `awg:`, ключи `runtime` и `container` сняты (до того, с
3.4.0, — 3.4.0; строка коммита — «версия совместимости → 4.0.0: раздел
app.yaml docker → awg, ключи runtime/container сняты»). Значит, бэкапы ниже
4.0.0 на 4.0.0 не применяются, а атомарный откат набора обновлений и сторож
через этот выпуск не взводятся: набор, перешедший 3.4.x → 4.0.0, назад не
откатывается, код 3.4.x на установку возвращает только ловушка второй
половины самого перехода (README §9, «Переход на 4.0.0»). Шлюзы, оставшиеся
ниже новой линии, из набора не выпадают: сервер держит в сохранённом списке
релизов и выпуски, на которых стоят агенты (`fleet_gateway_versions`), и
догоняет их обычным порядком (README §9a, «Метаданные релиза»). Миграций и переходов для
бэкапов нет: восстановление возможно только в своей линии совместимости — и
ставит код выпуска, на котором бэкап снят (README §10, «Бэкапы»).

**Инвариант линии.** Откат обновления в той же установке (сторож, откат
набора), восстановление бэкапа на выпуск ниже текущего и шлюзы, идущие за
сервером вниз, ставят прежний код на базу и `conf`, которые уже тронул новый.
Это работает, только если **в пределах линии `COMPAT_FLOOR` схема базы и
`conf` только растут**: таблицы и колонки добавляются, но не удаляются, не
переименовываются, не меняют тип и смысл; ключи `conf/*.yaml` добавляются, но
не пропадают и не меняют тип. Нарушить — значит поднять `COMPAT_FLOOR` (ниже,
«Когда двигать»). Сторож — `tests/unit/test_schema_line.py` против снимка на
версию совместимости: `tests/fixtures/schema_floor.sql` (DDL свежей базы) и
`tests/fixtures/conf_floor.txt` (ключи шаблонов `conf` с типом значения);
текущее обязано быть их надмножеством. Снимок переснимается только вместе со
сдвигом `COMPAT_FLOOR` — `.venv/bin/python -m tests.unit.test_schema_line`
(тест, увидев в снимке прежнюю версию совместимости, сам называет эту
команду); переснимать его, чтобы прошёл упавший тест, — значит молча сломать
откат.

- **Когда двигать.** Только когда новый код не может применить бэкап прежней
  версии без перехода (схема базы, состав или формат архива, смысл ключей
  `server_state`, которые читает слияние) — то есть когда держать чтение
  прежнего значило бы тащить мёртвый код. Колонка, добавленная в пределах
  линии, сдвига не требует: слияние переносит только колонки, общие для
  обеих баз. Сдвиг — отдельной строкой коммита, как сдвиг минимума:
  `версия совместимости → X.Y.Z: причина`.
- **Запись журнала выпуска, поднимающего `COMPAT_FLOOR`, начинается
  предупреждением**: бэкапы прежних версий с него не применяются, вернуться
  на прежние версии можно только чистой установкой, и что сделать сразу
  после обновления (снять новый бэкап). Такой выпуск адресуется обеим ролям.
  У 3.4.0 в шапке — ещё строка «откат на выпуски ниже 3.4.0 — только чистой
  установкой; старый awg-bot.sh из архива не запускать»: скрипт прежней
  версии границы `COMPAT_FLOOR` не знает и откатил бы поверх базы и `conf`
  новой линии (её просит строка коммита «в шапку журнала выпуска: …», §3).
- **Метка бэкапа** (`state/backup-meta.json`, `domain/backup/meta.py`):
  `schema` (сейчас 2) — раскладка архива; `version` — версия бота, снявшего
  бэкап: ниже `COMPAT_FLOOR` — отказ, другая (старше или новее кода) —
  переход на выпуск бэкапа; `awg_gen` — поколение AmneziaWG (другое — отказ:
  интерфейсы другого поколения слиянием не сводятся); `digest` — sha256
  установленного релиза (его пишут установщик, `awg-bot update`, обновление
  кнопкой и восстановление с переходом; установка не из релиза — пусто): по
  нему восстановление находит выпуск бэкапа на GitHub и сверяет его ассет,
  без него — только та же версия; `db_line` — линия базы: случайная метка, с
  которой база рождается и которую уносит с собой, — по ней слияние отличает
  тот же сервер от нового и чужого (README §10, «Бэкапы»); `gateways` — опись
  слотов на момент бэкапа. Новое поле метки — добавлением; смена смысла поля
  или раскладки — `schema` + 1 и сдвиг `COMPAT_FLOOR`.
- **Слотовые ключи `server_state`** (`<имя>_<слот>`) записаны один раз в
  реестре `domain/services/gateway_link/slotkeys.py` с пометкой, когда ключ
  снимается: `SLOT` — только со слотом, `DEVICE` — и при замене устройства в
  нём, — и что с ним делает восстановление (`CURRENT` или `OFFER`). Новый
  ключ без записи в реестре ловит сторож-тест. С 3.4.0 так, например,
  `gwcfg_backup_q_nudged` (документ дослан агенту прежнего выпуска с висящим
  вопросом о ключевой фразе) и `gwupd` — команда набора обновлений слота —
  оба `DEVICE`: новое устройство чужую команду не наследует.

## 3. Требования к коммитам

Запись журнала и номер версии рождаются при выпуске из сообщений коммитов
после последнего тега (при необходимости — с чтением диффов отдельных
коммитов). Поэтому сообщение — входная точка, и к нему требования:

- Первая строка — что изменилось и зачем, по существу, без номера версии
  (номер ставит выпуск). Дальше — подробности, если первой строки мало.
- **Сдвиг минимальной версии роли — всегда явно в сообщении**, отдельной
  строкой вида `минимум main → 3.0.0: схема БД, gateways.lan_mode` (или
  `минимум gw → …`). Нет такой строки — минимум не двигается, что бы ни
  менялось в коде. Сдвиг допустим только там, где релиз ломает
  совместимость: схема БД, снятие шимов под старые версии; и такая ступень
  адресуется обеим ролям. Переименование на месте при старте (`init_schema`
  доводит базу минимума, которую код новее получает и накатом, и
  восстановлением копии) минимум не двигает: в сообщении — что
  переименовано и что шаг снимается со следующим сдвигом минимума.
- **Условие на версию другой роли — тоже явной строкой**: `агенту нужен
  main ≥ 3.3.0: агент не обслуживает сервер без документа конфигурации` →
  `roles.gw.needs_main = "3.3.0"` в метаданных; `основному нужны шлюзы ≥
  3.3.0: сервер снимает файл перевыпуска` → `roles.main.needs_gw = "3.3.0"`.
  Нет такой строки — условия нет. Ставится только там, где
  новая версия роли действительно не работает со старой другой стороной
  (снятые шимы, новый обязательный вид сообщения канала), и только версией,
  которая другой роли была адресована.
- Если изменение требует действия на шлюзе (скрипты обвязки и линка,
  строки юнита обвязки) — сказать об этом в сообщении: строки юнита
  доезжают каналом документом конфигурации, скрипт обвязки — обновлением
  агента (встать сразу — «🚑 Восстановить»); подключить шлюз заново
  командой («🔁 Настроить заново») нужно только тому, что едет одним
  подключением (адрес линка, ключи на токене). Файла первого применения с
  3.4.0 нет, перевыпуска конфигурации шлюза — с 3.3.1; строка
  «перевыпуск конфигурации шлюза не нужен» в сообщении остаётся уместной.
- То, что должно встать в шапку записи журнала (предупреждение перед
  пунктами: откат, бэкапы, действие сразу после обновления), — отдельной
  строкой `в шапку журнала выпуска: <текст>`; выпуск переносит её в шапку
  записи как есть.
- Никаких строк атрибуции и подписей в сообщениях.

## 4. Порядок выпуска

Исходное состояние: ветка `main`, рабочее дерево чистое, все коммиты после
последнего тега — локальные. Выпуск — отдельный коммит с номером версии и
записью журнала.

1. Собрать сообщения коммитов после последнего тега: `git log <тег>..HEAD`.
   Определить номер версии по матрице §1; сдвиг минимумов — только по
   явным строкам в сообщениях (§3).
2. Прогнать проверки **по одному разу**, итог — по коду возврата:
   `.venv/bin/python -m pytest -p no:cacheprovider; echo rc=$?` (без `-q`:
   он уже в `pytest.ini`, второй `-q` прячет строку `N passed`, и вывод из
   одних точек — норма, а не повод перезапускать; набор идёт параллельно
   по ядрам через `pytest-xdist`, `-n auto` тоже в `pytest.ini`; чтобы
   разобрать один падающий тест по порядку — `-n 0`),
   `.venv/bin/python -m pyflakes awgbot tests tools`, `sh -n` по
   `install/*.sh`, `bash -n awg-bot.sh` и `install/lib/*.sh`. Провал — выпуск останавливается,
   номер версии не занимается; после правок процедура начинается заново.
3. Записать номер в `awgbot/__version__.py`; метаданные — `python -m
   tools.release_meta [--main A.B.C [--needs-gw X]] [--gw D.E.F [--needs-main
   Y]] --write` — хотя бы один адресат (адресаты — по §2, минимумы — из
   последнего `docs/releases/vX.json` роли и строк «минимум … →», условия —
   по строкам коммитов §3; ступень перехода — по правилу §2; поколение ядра
   инструмент берёт из `install/awg.lock`; пишет `docs/releases/vX.Y.Z.P.json`,
   проверив схему); запись в
   `docs/CHANGELOG.md` — у 3.3.0 и 3.3.1 с машинными строками из `--hashtags`
   (§2), с 3.3.2 без них; строки коммитов «в шапку журнала выпуска: …» (§3)
   и предупреждение выпуска, поднимающего `COMPAT_FLOOR` (§2), — первым
   абзацем записи, до пунктов; закоммитить всё вместе: `vX.Y.Z.P:
   <заголовок>`.
4. Собрать поставку: `bash build_release.sh <каталог>` — рядом с
   `awg-bot.tgz` ляжет `awg-bot-release.json` (копия `docs/releases/vX.json`
   после проверки схемы и совпадения версии; нет файла — сборка
   останавливается; локальной сборке без выпуска — `AWG_BUILD_LOCAL=1`, без
   этого артефакта); убедиться, что в
   `awg-bot.tgz` лежит `awgbot/__version__.py` с новым номером и есть
   `install/awg-bot-install.sh`, а владелец файлов в архиве — root
   (`tar tvzf <каталог>/awg-bot.tgz | head`): сборка пишет его сама
   (`--owner=0` у GNU tar, `--uid 0` у bsdtar), и другой uid в архиве значит,
   что `tar` сборки не принял ни одного из этих флагов. Файла юнита
   `awg-bot.service` в поставке нет: юнит пишет установщик (`install_unit` в
   `awg-bot.sh`) и переписывает его на каждом `update`. Состав поставки
   задан дважды — `build_bot` в `build_release.sh` и `_ENTRIES` в
   `awgbot/util/dist.py` — и меняется синхронно. Полный архив проекта
   `awg-bot-project.tgz` в релиз не идёт; в него не попадают `.git`, данные,
   локальные окружения (`venv`, `.venv`, `.venv-next`) и служебные файлы
   разработки.
5. Тег `vX.Y.Z.P`; `git push origin main vX.Y.Z.P`; при сетевом отказе — до
   трёх попыток с паузой; проверить `git ls-remote origin main vX.Y.Z.P`
   (один и тот же коммит).
6. Создать релиз **черновиком** и загрузить оба ассета: `gh release create
   vX.Y.Z.P <каталог>/awg-bot.tgz <каталог>/awg-bot-release.json --draft
   --title "vX.Y.Z.P — …" --notes-file <тело записи без заголовка>`; при
   отказе — до трёх попыток; ассет не загрузился — `gh release upload
   vX.Y.Z.P <файл> --clobber`. Черновик боты не видят (`/releases` отдаёт
   его только с токеном, и бот черновики отбрасывает). Без `--draft` `gh`
   сам создаёт черновик на время загрузки и публикует релиз сразу после неё
   (так описано в `gh release create --help`, раздел «Immutable Releases»),
   то есть до сверки шага 7 — а релиз с битым или недостающим ассетом
   метаданных, особенно ступень 3.3.1, опубликованным оставаться не должен:
   с 3.3.2 он становится барьером обновлений у всех (§2).
7. Скачать **оба** ассета из черновика (`gh release download vX.Y.Z.P`) и
   сверить sha256 каждого с локальной сборкой и с `digest`, который
   показывает GitHub (`gh release view vX.Y.Z.P --json assets`); всё
   сошлось — опубликовать: `gh release edit vX.Y.Z.P --draft=false`. Не
   сошлось — черновик остаётся черновиком, выпуск останавливается.
8. Отчёт: номер, адресаты, ссылка на релиз, совпадение хэшей; при провале —
   на каком шаге и что именно.

Снятый релиз не удалять, а помечать — удаление глушит обновления у тех, кто
его уже поставил, и делает невозможным восстановление бэкапов, снятых на нём.
Пометка — флаг `prerelease` и заголовок «vX.Y.Z.P — снят: <причина>»: `gh
release edit vX.Y.Z.P --prerelease --title "vX.Y.Z.P — снят: <причина>"`; тег,
ассеты и тело не трогаются (выпуски иммутабельны). Бот с 3.4.0 читает пометку
(`withdrawn_reason` в `infra/updates/github.py`): снятый выпуск — не цель
кнопки и не ступень вверх, но и не барьер; кто на нём — обновляется дальше;
восстановить бэкап на него можно — с предупреждением «Выпуск vX снят:
<причина>». Просто `prerelease` без «снят:» в заголовке — не пометка. Боты 3.3.x
пометку не читают.
