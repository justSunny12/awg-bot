# Условная маршрутизация — концепт

Статус: **код бота написан**, инфраструктура ВПС/ГВ — нет (§11–12). Версия после
разворота архитектуры (см. §14 — что изменилось относительно первоначального
замысла и почему).

Реализация в коде:

| Слой | Файл |
|---|---|
| Топология фичи | `conf/app.yaml` → `routing:`, `core/config.py` |
| Схема и CRUD | `infra/db.py` |
| Чистая логика (нормализация доменов, генерация dnsmasq) | `domain/routing.py` |
| Команды (ipset/iptables/ip/dnsmasq) | `infra/routing.py` |
| Бизнес-логика, реконсиляция, деградация | `domain/services.py` |
| Интерфейс | `bot/handlers/routing.py`, `keyboards.py`, `texts.py` |
| Самопроверка и мониторинг | `runtime/preflight.py`, `runtime/scheduler.py` |

**Фича спит, пока `routing.gw_interface` пуст**: UI её не показывает,
реконсиляция не трогает систему, планировщик пропускает. Это же и аварийный
рубильник — очистил ключ, перезапустил бота, маршрутизация выключена у всех.

---

## 1. Суть

Пользователь получает **российский IP для всего, кроме заблокированного**.
Банки, госуслуги и маркетплейсы перестают ругаться на зарубежный адрес, а
заблокированные ресурсы продолжают идти через VPN, как и раньше.

Ключевое свойство реализации: **конфиг устройства не меняется**. Режим — это
серверное состояние, а не отдельные учётные данные. Уже выданные `vpn://`
продолжают работать, перевыпускать нечего, переключение мгновенно и обратимо.

## 2. Топология

```
телефон ──awg, обычный конфиг──► ВПС (за рубежом)
                                  │
            src ∈ включённые устройства  И  dst ∉ «нужна заграница»?
                                  │
              ┌───────── нет ─────┴───── да ─────────┐
              ▼                                      ▼
        выход с ВПС                        линк-туннель → ГВ (малинка, дом)
        (зарубежный IP)                              │
                                                     ▼
                                            MASQUERADE в eth0
                                            (домашний РФ-адрес)
```

Обратный путь — по conntrack на ГВ: ответ приходит на домашний адрес,
разворачивается и уходит назад в линк-туннель, оттуда клиенту.

**Направление установления линка не меняется:** ГВ по-прежнему инициирует
подключение к ВПС (`Endpoint` прописан у ГВ, `PersistentKeepalive = 25`).
Входящих соединений на домашний адрес фича не требует вовсе — это лучшая
позиция и по ТСПУ, и по независимости от провайдера.

### Узлы

| | ВПС | ГВ (Raspberry Pi, дом) |
|---|---|---|
| Роль | вход клиентов, решение о разделении | боковой выход с РФ-адресом |
| Пиры клиентов | все | нет |
| dnsmasq + ipset фичи | да | нет |
| Пер-клиентское состояние | да | **нет** |
| Управление из бота | локально (`docker exec`), как сейчас | не требуется |

Отсутствие пер-клиентского состояния на ГВ — причина, по которой управляющий
агент там не нужен. ГВ обходится локальными systemd-юнитами, которые уже
написаны.

## 3. Модель данных

Минимальная. Три булевы колонки и одна ленивая таблица.

- `clients.routing_allowed` — **разрешение админа**. Пока не выдано, фича для
  клиента невидима: ни тумблеров, ни раздела со списком. По умолчанию выключено.
- `clients.routing_master` — **мастер-тумблер клиента**. Одно «выключить всё
  разом», не обходя каждое устройство.
- `devices.routing_enabled` — тумблер устройства.
- `client_routing_domains` (1:N, ленивая) — личный список доменов,
  `PRIMARY KEY (client_id, domain)`. Строк нет ⇔ список пуст; дедуп даёт сам PK.

Все три колонки доводятся аддитивной миграцией (`_migrate_additive`) — боевая БД
переживает обновление без пересоздания, данные не трогаются.

Эффективное значение = `routing_allowed AND routing_master AND routing_enabled`.

Отдельных пиров, ключей и адресов у режима нет. Проекция состояния в
инфраструктуру — членство туннельного адреса устройства в ipset на ВПС.

### Лимит устройств

Отдельной механики не нужно. Устройство есть устройство, `count_devices`
работает как работает. Требование «ключ с маршрутизацией идёт в зачёт лимита»
выполняется само: если пользователь хочет оба режима одновременно на одном
физическом устройстве, он заводит два устройства в боте, и оба честно считаются.

---

## 4. Инварианты

1. **Эффективный флаг ⇔ членство в src-сете.** Единственная проекция состояния.
   Реконсиляция при старте и по расписанию приводит сеты в соответствие с БД.
2. **Заблокированное устройство не маршрутизируется — автоматически.** Блокировка
   устройства ставит DROP по его адресу на ВПС; до стадии маркировки пакет не
   доходит. Отдельного каскада не требуется, зеркалить нечего.
3. **Снятие верхнего флага не стирает нижние.** Отзыв разрешения админом гасит
   эффект (адреса убираются из сетов), но `routing_master` и пер-девайсные флаги
   сохраняются — при возврате доступа настройка восстанавливается сама. То же для
   мастер-тумблера относительно устройств.
4. **Приватные диапазоны никогда не попадают в маршрутизируемые наборы.**
   См. §10.

## 5. Списки

### Правило работает ОТ ОБРАТНОГО

Список описывает то, чему нужна **заграница**, а не Россия. Всё, чего в наборе
нет, уходит на шлюз и выходит с российского адреса:

```
-m set --match-set rt_src_u<N> src \
-m set ! --match-set vpn_u<N> dst -j MARK
```

Почему так, а не перечнем российских сервисов (как задумывалось сначала):

- **не нужно вести перечень.** Российский адрес получает любой сервис, включая
  те, что на `.com`, — не дожидаясь, пока его внесут вручную;
- **основной путь не зависит от DNS.** Подсети попадают в набор напрямую из
  готовых списков. Резолвер участвует только в дополняющей части, а именно на
  DNS-звене схема ломалась трижды подряд: capabilities dnsmasq, затирание
  набора собственной реконсиляцией, кэш на клиенте — и каждый раз молча.

Цена — та, о которой сказано в §14: через домашний канал идёт почти весь
трафик, и его полоса становится общим потолком.

**Отказ инвертируется.** Пустой набор означает не «всё как обычно», а «на шлюз
уходит всё» — включая заблокированное, которое с российского адреса не
откроется. Поэтому `self_check()` отдельно проверяет, что базовый набор не пуст,
и не поднимает функцию, если наполнить его не успели.

### Наполнение базового набора

Бот качает и обновляет его **сам** — при старте и по расписанию
(`routing.lists_*` в conf). Требовать ручного запуска нельзя: однажды забудут, а
пустой набор при инверсии отправляет на шлюз весь трафик.

Два источника, и разделение принципиально:

- **подсети** — грузятся в ipset напрямую, без участия DNS. Это основной путь:
  он не зависит ни от резолвера, ни от кэша, ни от DoH у клиента;
- **домены** — через директивы dnsmasq, наполняются по мере резолва. Дополняют
  подсети там, где адреса меняются.

Недоступность источника ошибкой не считается: прежний набор остаётся в силе.
Устаревшие списки лучше пустых по той же причине.

### Наборы на ВПС

| Набор | Тип | Содержимое |
|---|---|---|
| `vpn_u<N>` | hash:net | набор профиля N: базовый список **+** его личные исключения |
| `rt_src_u<N>` | hash:ip | адреса устройств профиля N с включённым режимом |

Пер-юзерный merge, а не общий набор рядом с личными. Причина в dnsmasq: для
домена применяется **только одна** директива `ipset=`. С общим набором домен из
базы, добавленный кем-то себе, переставал бы попадать в общий — и у остальных
уезжал бы на шлюз. Один человек ломал бы маршрутизацию другим.

Правило — одно на профиль, с одним отрицанием:

```
-m set --match-set rt_src_u<N> src \
-m set ! --match-set vpn_u<N> dst -j MARK --set-xmark 0x1/0x1
```

Далее `ip rule fwmark → таблица → dev <линк>`. Удаление профиля уносит и правило,
и наборы.

### dnsmasq

Файл генерируется **целиком и один**: на каждый домен одна директива со списком
наборов всех, кому он нужен.

```
ipset=/rutracker.org/vpn_u2,vpn_u7      базовый — всем включённым
ipset=/example.com/vpn_u2                 личный — только этому
```

Применение — **`systemctl restart`, не `reload`.** SIGHUP перечитывает
`/etc/hosts` и чистит кэш, но не конфиг-файлы; новые `ipset=` через reload не
подхватываются.

> **Грабли, стоившие нескольких итераций.** Бот не должен перезаписывать наборы
> назначений: туда же dnsmasq кладёт адреса по мере резолва, и `replace_members`
> стирал накопленное на каждой реконсиляции. Подсети только **дописываются**
> (`add … -exist`).

### Ввод

Принимаются **только доменные имена**, IP и CIDR — нет. Поддомены dnsmasq
покрывает автоматически (`ipset=/example.com/…` ловит и `*.example.com`), поэтому
wildcard не нужен и не принимается.

Нормализация: срезать схему, путь, порт, `www.`, привести к нижнему регистру,
punycode, дедуп. Пользователь вставит `https://www.sberbank.ru/ru/person` — это
должно превратиться в `sberbank.ru` без вопросов. Ввод пачкой (несколько строк
за раз) обязателен.

Ответ на добавление показывает разбор: что принято, что отброшено и почему —
мусор, уже в базе, запрещено, упёрлись в лимит. Молчаливое проглатывание
половины введённого недопустимо.

Потолок записей на клиента — порядка сотни. Не ради ресурсов, а чтобы список
оставался просматриваемым.

## 6. UI

### Чего в потоке выдачи данных нет

Ничего. Конфиг одинаков в обоих режимах, выбирать при выдаче ссылки/QR/файла
нечего. Поток остаётся ровно сегодняшним.

### Что появляется

- **У админа в карточке клиента** — тумблер «разрешить условную маршрутизацию».
  По умолчанию выключен.
- **У пользователя в профиле** — мастер-тумблер режима, в одном разделе со
  списком доменов. Виден только при выданном разрешении.
- **У пользователя в карточке устройства** — тумблер устройства. Виден только
  при выданном разрешении и включённом мастере.
- **В списке устройств** — маркер у устройств с включённым режимом. В том же
  ряду, что существующие `[Доступ к серверу]` и суффикс `(APP)`.
- **В профиле** — раздел со списком доменов: просмотр с пагинацией, добавление
  (FSM, приём пачкой), удаление записи, «очистить список». Плюс строка вида
  «База: N сервисов · Ваши: 7».
- **В инфобоксе главного меню** — вторая статусная строка рядом с состоянием
  сервера ([`texts.py:520`](../awgbot/bot/texts.py#L520)). Показывается только
  тем, у кого есть хотя бы одно устройство с включённым режимом.

### Статусная строка

Ровно два состояния, ок/неок. «Ок» = линк с ГВ жив (свежий хендшейк) **и**
синтетическая проба выхода проходит. Значение берётся из кэша мониторинга —
открытие меню не должно порождать сетевых вызовов.

## 7. Друг

Друг пользуется, но не управляет — выполняется само собой. Ему передают
конкретное устройство; включён на нём режим или нет, решает владелец. Никаких
появляющихся и исчезающих кнопок, никакого наследования настроек.

Список доменов другу не виден и им не правится: маршрутизация его трафика идёт
по списку владельца (иначе никак — политика висит на клиенте), а сам список
отражает интересы владельца.

## 8. Учёт трафика

**Строить нечего.** Все клиентские пиры остаются на ВПС, и весь трафик
устройства — и российский, и зарубежный — проходит через его пир. Существующие
счётчики захватывают всё.

Дыра, ради которой планировался двухузловой мониторинг (российский трафик не
доходит до ВПС и невидим для квот), в этой топологии не возникает. Не нужны ни
пер-узловые `traffic_samples`, ни пер-узловой детект рестарта контейнера, ни
разбирательства «пир пропал или сеть моргнула».

Линк-туннель до ГВ несёт тот же трафик второй раз, но он не является пиром
устройства и в подсчёт не попадает — двойного учёта нет.

## 9. Отказы и деградация

**ГВ недоступен → маркировка выключается.** Бот видит устаревший хендшейк на
линк-интерфейсе и снимает `ip rule`. Помеченного трафика больше нет, всё уходит
обычным путём с зарубежным адресом.

Пользователь при этом видит, что банк ругается на IP, но интернет у него
работает. В схеме, где ГВ стоял бы на входе, отказ означал бы полную потерю
связи — здесь ГВ на боковой ветке.

**Уведомления:** об отвале ГВ сообщается **только админу**. Пользователи узнают
из статусной строки.

**MTU.** РФ-трафик инкапсулируется дважды (клиент→ВПС, затем ВПС→ГВ). Для TCP
закрывается MSS-клампом на линк-интерфейсе ВПС. Банковские приложения — почти
всегда TCP/TLS, поэтому риск существенно ниже, чем был бы для видео по QUIC.

## 10. Безопасность

**Доступ в домашнюю сеть закрыт структурно.** Единственный путь пакета к
малинке — быть помеченным на ВПС, а метится только то, чьё назначение лежит в
наборе РФ-сервисов. `<домашняя подсеть>` туда не попадает.

Остаточная защита — **одно статическое правило на ГВ**: DROP на `awg-линк →
RFC1918`. Оно нужно потому, что для работы фичи придётся разрешить новые
соединения из линк-туннеля в `eth0` (сейчас там только `RELATED,ESTABLISHED`).
Правило пишется один раз и не меняется — ни наборов, ни синхронизации с ботом.

**DNS rebinding — основной вектор, и он порождён именно пользовательскими
списками.** Пользователь добавляет домен, который контролирует, и отдаёт на него
`A <адрес шлюза в домашней сети>`. Адрес ложится в сет, трафик метится и приезжает к NAS. Вся
структурная защита обходится одной DNS-записью.

Меры, обе нужны:

- `stop-dns-rebind` в dnsmasq на ВПС — постоянная защита от приватных адресов в
  ответах апстрима;
- отбивать на входе в список домены, резолвящиеся в RFC1918 на момент
  добавления. Это не замена первому: адрес можно поменять после проверки.

Апстрим-резолверы ВПС стоит держать по DoT — ВПС за границей, ТСПУ туда не
достаёт, а подменённый по дороге ответ даёт тот же эффект без злого умысла.

**Денай-лист пользовательского списка:** приватные диапазоны, домены собственной
инфраструктуры (IMAP-хост email-выхода из паузы, домен ГВ), голые TLD и
односимвольные зоны.

**Личный доступ админа домой** обслуживается отдельно — существующим `awg1` на
малинке, как прямым туннелем. К боту, к фиче и к пользователям он отношения не
имеет. Это сознательное разделение: две разные задачи, склеенные раньше только
общим железом.

**Домашний адрес разделяется всеми пользователями** через NAT. Трафик выходит с
адреса, привязанного к вашему договору с провайдером. Отмечено один раз как
факт, решение ваше.

## 11. Работы на ВПС

0. **Базовый обвяз хоста** (ставится руками, ботом не трогается, проверяется
   `self_check()`):
   - `MASQUERADE` для `10.8.1.0/24` на внешнем интерфейсе — иначе трафик
     включённых устройств, выпущенный из контейнера немаскараженным, наружу не
     уйдёт;
   - маршрут до `10.8.1.0/24` через bridge-адрес контейнера — иначе обратный
     трафик не вернётся клиенту;
   - разрешения в `FORWARD` для этой подсети в обе стороны;
   - `ipset` и `dnsmasq` установлены на хосте.

1. **Отдельный AWG-интерфейс под линк с ГВ.** Нужен, чтобы у пира ГВ было
   `AllowedIPs = 0.0.0.0/0` — иначе не отправить туда произвольные адреса
   назначения, не сломав клиентские пиры на общем интерфейсе. Побочно уводит ГВ
   из клиентской подсети `10.8.1.0/24` и снимает две проблемы разом: `10.8.1.16`
   перестаёт конфликтовать с аллокатором, и `reconcile_peers` перестаёт видеть
   ГВ как «новое устройство из приложения».

   > Сейчас ГВ уже заведён в БД как app-устройство служебного клиента —
   > `reconcile_peers` подхватил его. Удаление через админ-UI снимет пир и уронит
   > линк. Почистить при переезде.

2. **dnsmasq + прозрачный перехват `:53`.** DNAT всего UDP/TCP на 53 от клиентов
   на локальный dnsmasq. Так выданные конфиги с `DNS = 1.1.1.1` продолжают
   работать без перевыпуска, и заодно перехватывается хардкод `8.8.8.8` в
   приложениях. `stop-dns-rebind` обязателен, `cache-size` задать явно.

3. **Политика маршрутизации:** ipset'ы из §5, правила mangle, `ip rule`,
   таблица с `default dev <линк>`, MSS-кламп.

Всё это — на машине, где бот уже живёт и работает через `docker exec`. Сетевого
API, токенов, идемпотентности по сети и общего кода парсинга не требуется.

## 12. Работы на ГВ

Немного, и почти всё — гигиена существующего.

1. **Разрешить новые соединения** из линк-туннеля в `eth0` (сейчас только
   `RELATED,ESTABLISHED`) и следом **DROP на RFC1918** — см. §10.
2. **Починить рестарт-петлю.** `awg-watch.sh` по событию `start` контейнера
   рестартует `awg-routing.service`, а `awg-routing.sh` в фазе 2 делает
   `docker restart awg-test` — что порождает новое событие `start`. Пока ВПС
   доступен, круг рвётся на первой итерации; при недоступности контейнер
   перезапускается бесконечно, роняя заодно `awg1`. Восстановлением линка должен
   заниматься вотчдог с backoff, а не скрипт, перезапускающий себя по событию,
   которое сам же порождает.
3. **Шейпер на микротике** — ограничение AWG-трафика до 200 Мбит через
   `mark-connection`/`mark-packet` + simple queue по метке. На микротике, а не на
   Pi: локальный трафик LAN↔NAS через роутер не идёт и очередями не задевается
   вовсе, тогда как шейпинг `eth0` на Pi пришлось бы отделять от Samba
   классификацией.

   Перед настройкой стоит измерить `iperf3` через туннель: `amneziawg-go` —
   userspace-реализация на Go, на ARM64 её потолок может уже быть ниже 200 Мбит,
   и тогда очередь не нужна.
4. **Исправить `systemctl reload dnsmasq` → `restart`** в
   `awg-lists-update.sh` — сейчас шестичасовое обновление домашнего списка качает
   файл, но не применяет его.
5. **Перезагрузка ГВ из бота** — по SSH через линк-туннель с forced command, а не
   HTTP-сервисом. Одна ручка, ключ с ограничением по команде.

Домашняя схема малинки (`vpn_domains`, `awg-lists-update.sh`, `awg-subnets.sh`,
`user-managed.conf`, `awg1`) продолжает жить своей жизнью и обслуживать вашу
домашнюю сеть. Бот туда не пишет, оттуда не читает и о существовании этих
списков не знает.

### Разделение по namespace: два плеча

Контейнер Amnezia на ВПС работает в режиме **`bridge`**, то есть в собственном
сетевом namespace. А `ipset` — сущность per-netns: набор, созданный внутри
контейнера, для dnsmasq на хосте не существует и наполняться не будет. При этом
различать клиентов можно только **до** MASQUERADE контейнера — за ним все пиры
выглядят одним bridge-адресом (ровно поэтому там же живут блокировки).

Отсюда конструкция:

| Где | Что |
|---|---|
| **Контейнер** | только исключения из MASQUERADE — по правилу `-j ACCEPT` в своей nat-цепочке на каждое включённое устройство. `ipset` там не нужен вовсе |
| **Хост** | наборы, маркировка, `ip rule`, dnsmasq, линк до шлюза |

Работает потому, что немаскараженный трафик приходит на хост с настоящим
`10.8.1.x`, а весь остальной — с bridge-адреса контейнера. Различение достаётся
даром, без передачи метки между namespace (она бы и не пережила переход).

`ACCEPT`, а не `RETURN`: `RETURN` вернул бы пакет в `POSTROUTING`, где его
подобрало бы следующее правило — то самое `MASQUERADE`, от которого мы уходим.

### Разведка ВПС (подтверждено)

| Факт | Значение |
|---|---|
| Виртуализация | KVM — полноценная, наборы ядра доступны |
| `ipset` | работает (доустановлен), `xt_set` на месте |
| Контейнер Amnezia | `bridge`, `iptables -t nat` внутри доступен |
| `dnsmasq` на хосте | установлен, **не запущен** — своего потребителя нет |
| `:53` на хосте | занят `systemd-resolved` на `127.0.0.53` |

Отсюда два ограничения для обвяза: dnsmasq **не должен** слушать `0.0.0.0`
(перекроет `127.0.0.53` и сломает резолвинг самого сервера), и ему нужен
выделенный адрес. Берём собственный `dummy`-интерфейс, а не bridge-адрес
докер-сети: последний уедет при пересоздании контейнера.

Отдельно: `amneziawg-dkms` помечен пакетным менеджером как автоматически
установленный и более не требуемый. `apt autoremove` снесёт модуль ядра и
положит VPN. Закрепить: `apt-mark manual amneziawg-dkms`.

### Статика против динамики

Бот управляет только тем, что зависит от состояния: исключения, наборы, цепочка
маркировки, `ip rule`. Базовый обвяз хоста — `MASQUERADE` для клиентской подсети,
маршрут обратно в контейнер, разрешения в `FORWARD` — ставится **один раз при
развёртывании** и ботом не трогается: менять на горячую базовый NAT боевого
сервера ради фичи неоправданно.

Наличие обвяза проверяет `self_check()` до того, как кого-то включат. Без этой
проверки отказ был бы худшим из возможных: у человека, которому включили режим,
просто пропадёт интернет.

### Грабли: dnsmasq без CAP_NET_ADMIN

Демон стартует от root и сбрасывает привилегии до пользователя `dnsmasq`, теряя
capability для записи в ipset. Директивы `ipset=` после этого выполняются
**вхолостую**: резолв работает, ошибок нет, наборы остаются пустыми — а значит
маркировать нечего, и весь трафик молча идёт мимо шлюза.

Диагностируется единственным способом — сравнением «резолв есть, набор пуст»:

```
dig +short @<адрес dnsmasq> sberbank.ru >/dev/null
ipset list vpn_u<N> | grep -c '^[0-9]'     # 0 при живом резолве ⇒ капабилити нет
```

Лечится возвратом ровно одной привилегии, без запуска демона от root:

```
/etc/systemd/system/dnsmasq.service.d/ipset.conf
[Service]
AmbientCapabilities=CAP_NET_ADMIN
```

`routing-host-setup.sh` ставит этот override сам (шаг 2a).

## 14. Что изменилось относительно первоначального замысла

Первоначально предполагалось: клиент подключается **к ГВ** отдельным конфигом,
на ГВ заводится второй пир устройства, режим определяется тем, какими данными
пользователь подключился.

Разворот точки входа (клиент → ВПС, ГВ на боковой ветке) убрал:

- управляющего агента на ГВ — сетевой API, токен, TLS, идемпотентность,
  реконсиляцию, общий с ботом код парсинга;
- двухузловой учёт трафика вместе с дырой в квотах, которую он чинил;
- второй пир на устройство и всю связанную механику: каскады блокировок на
  ГВ-двойника, усложнённый учёт слотов, «пир не удаляется при отключении»;
- второй формат конфига и риск, что приложение не переварит обфускацию ГВ
  (`H1..H4` диапазонами, шаблонный `I1`);
- шаг выбора режима в потоке выдачи данных;
- зависимость от входящих соединений на домашний адрес — а с ней вопросы CGNAT
  и лишнюю заметность для ТСПУ;
- пер-клиентское состояние на ГВ, включая набор «кому можно в локалку» с его
  атомарной подменой и краевым случаем «устройство админа передано другу»;
- огромный автообновляемый список — он превратился в поведение по умолчанию.

Взамен появилось: отдельный AWG-интерфейс на ВПС, dnsmasq с перехватом `:53`
там же, и крюк для российского трафика (клиент → ВПС → ГВ → сайт), из-за
которого латентность РФ-сервисов вырастает. Последнее признано некритичным.

## 15. Открытые вопросы

1. **Тумблер переключаемый или тип фиксируется при создании?** Ограничение
   «выбрать один раз и не менять» принималось, чтобы не городить два пира на
   устройство. Пиров больше нет, переключение стоит одну запись в ipset.
   Рекомендую сделать свободно переключаемым — это ровно та фича, про которую
   пользователь захочет «попробовать так, а потом обратно».
2. **Параметры линк-интерфейса на ВПС** — порт, подсеть, обфускация.
3. **Перезагрузка ГВ из бота** — SSH через туннель с forced command устраивает?
4. **Что показывать другу** в статусной строке и показывать ли вообще.
5. **Тяжёлые ресурсы в национальных зонах** (RuTube и подобное) — оставляем в
   базе или выносим сразу? Влияет на нагрузку домашнего канала.

*Закрыто:* источник базового списка — готовые перечни доменов и подсетей,
