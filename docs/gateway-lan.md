# v3.0 — локальная сеть за шлюзом: «без VPN» и доступ между подсетями

Статус: **концепт на вычитку** (19.09.2026). Сращивает два документа:
`gateway-lan-split-concept.md` (домашний слой, собранный руками на Pi 5 и
Pi 4) и концепт доступа между подсетями за шлюзами. Продолжение
`docs/gateway-failover.md`: те же слоты, линки, агент. Ничего из домашнего
слоя вне проекта не остаётся — он целиком переезжает в поставку. OMV, шары и
торренты в проект по-прежнему не входят.

---

## 1. Суть

Две функции, вторая зависит от первой.

**A. «За шлюзом — без VPN»** — по слоту. Роутер квартиры заворачивает весь
трафик локальной сети на малину, малина делит его сама: заблокированное —
в туннель до ВПС, остальное — напрямую со своего домашнего адреса. На
устройствах ничего не включается. Зеркало условной маршрутизации: та же
логика разделения, но на входе в сеть, а не на выходе из ВПС.

**B. «Доступ между подсетями за шлюзами»** — одним тумблером на все слоты.
Устройства квартиры А ходят в квартиру Б по настоящим адресам через ВПС и
два линка. Работает только между слотами, у которых включена A: ровно она
даёт условие «весь трафик подсети идёт через шлюз, с обеих сторон», без
которого ответы не находят дорогу назад.

**Зоны ответственности** — по одному признаку: кто владеет объектом и
перевыставляет его.

| зона | кто | что |
|---|---|---|
| ВПС | основной бот | флаги слотов и тумблер, файл конфигурации шлюза (всё ниже едет в нём), форвардинг линк ↔ линк, маршруты в домашние подсети, свой резолвер клиентов, проверки и тексты |
| малина, обвязка | скрипт `routing-gw-setup.sh` из поставки | таблицы nft, sysctl, dnsmasq, скрипты списков, юниты, миграция ручного слоя, откат |
| малина, живое | агент | обновление списков по расписанию, персональные списки из чата, панель, монитор здоровья, проверка заворота |
| роутер | человек | заворот трафика на малину по рецепту от бота; бот проверяет результат снаружи, в роутер не лезет |
| домашний слой вне проекта | — | ничего. OMV, NAS, торренты — как были, не наши |

**Что не меняется:** клиенты и их конфиги, условная маршрутизация на ВПС,
автомат переключения слотов, пометка шлюза, бандл и его безопасность.

**Версия 3.0.0:** первая цифра — потому что на малине появляется второй
слой ответственности (домашняя сеть), а не потому что ломается
совместимость. Обеим ролям. Этапы в §10.

## 2. Модель

Новой сущности нет. У слота (`gateways`) добавляется одно поле:

- `lan_mode INTEGER NOT NULL DEFAULT 0` — функция A включена для этого
  слота.

Одна настройка: `app.routing.peer_nets.enabled` (по умолчанию `false`) —
функция B.

Всё остальное выводится:

- **устройство слота = аплинк = «клиентский туннель» из ручного слоя.** В
  документе домашнего слоя малина «становится ещё и обычным клиентом ВПС со
  своим устройством в боте» — она им уже является: устройство слота, его
  конфиг — это `awg0`. Никакого второго туннеля;
- **LAN-интерфейс и адрес малины в квартире** — из `home_subnets` слота: тот
  интерфейс, у которого адрес в домашней подсети. Поэтому для A домашняя
  подсеть обязана быть задана (и одна, если их несколько — первая);
- **чужие подсети слота N** (для B) — `home_subnets` слотов с `lan_mode=1`,
  кроме N, без пересечений с собственными (§4.2);
- **резолвер ВПС** — строка `DNS =` конфига устройства слота (свой резолвер
  клиентов, `awg-bot resolver`), иначе запасной апстрим (§3.2).

Что и куда едет в файле конфигурации шлюза (шапка бандла, окружение
скрипта обвязки, юнит):

| переменная | откуда | зачем |
|---|---|---|
| `LAN_MODE=1` | `gateways.lan_mode` | включить раздел A в скрипте |
| `HOME_SUBNETS` | `home_subnets` слота | LAN-интерфейс, адрес резолвера, маскарад в LAN |
| `PEER_HOME_NETS` | §4.2 | AllowedIPs пира ВПС, набор `peer_nets4` |
| `RESOLVER` | `DNS =` устройства слота | апстрим dnsmasq через аплинк |
| `ADMIN_IPS`, `GATEWAY_PUBKEY`, `UPLINK_B64`, … | как сейчас | — |

## 3. Функция A: «за шлюзом — без VPN»

### 3.1 Пакет на малине

Ручной слой сросся с обвязкой шлюза не в одном месте (§5). Итоговая схема
— **одна метка, одно правило, одна таблица маршрутов, две таблицы nft:**

```
LAN-клиент ──► end0 (малина)
  awg_home / prerouting (mangle):
      iifname != "end0" accept              ← из линка и аплинка мимо
      ip daddr @lan_ru4 accept              ← исключения: российский адрес — напрямую
      ip daddr @lan_vpn4 meta mark set 0x1  ← заблокированное — метка аплинка
  ip rule fwmark 0x1 lookup 100 → default dev awg0      ← УЖЕ ЕСТЬ (PostUp аплинка)
  awg_gw_guard / postrouting: oifname "awg0" masquerade ← УЖЕ ЕСТЬ (v2.24.1)
  awg_gw_guard / forward: oifname "awg0" tcp … maxseg set rt mtu   ← НОВОЕ
  awg_home / postrouting: ip saddr <LAN> oifname "end0" masquerade ← НОВОЕ
непомеченное → main → шлюз по умолчанию (роутер) → напрямую
```

Почему так, а не как в ручном слое:

- **Метка `0x1`, а не `0x10`.** Ручной слой брал свою метку, чтобы не задеть
  агента, и вёл своё `ip rule` в ту же таблицу 100. Смысл у обеих меток один
  — «в аплинк», правило и маршрут уже ставит PostUp аплинка и чинит агент
  (`uplink_policy_heal`). Вторая метка — второе правило, которое никто не
  чинит.
- **Маскарад в аплинк один** — тот, что скрипт обвязки ставит с v2.24.1.
  Ручной `oifname "awg0" masquerade` был его дублем.
- **Маскарад в LAN нужен** (`ip saddr <LAN> oifname "end0" masquerade`):
  ответ на прямой трафик должен вернуться на малину, а не на клиента мимо
  неё — иначе conntrack роутера видит половину соединения. Чужих подсетей
  (функция B) это правило не касается: у них другой `saddr`, адреса между
  квартирами остаются настоящими.
- **Две таблицы nft.** `awg_gw_guard` перевыставляется атомарно (`delete
  table` + создать) при каждой загрузке и реассерте — а наборы `lan_vpn4` /
  `lan_ru4` наполняются dnsmasq на лету, и терять их при каждом реассерте
  нельзя. Поэтому они живут в отдельной таблице `awg_home`, которую скрипт
  создаёт идемпотентно **без** `delete table`: наборы переживают реассерт.
  Правила таблицы обновляются заменой цепочек (`flush chain` + `add rule`).
- **MSS-кламп в аплинк** — в `awg_gw_guard`, там же, где маскарад: это
  свойство аплинка, а не домашнего слоя (агенту он тоже полезен).
- **rp_filter=2 (loose)**, не 0: ответы из интернета приходят в `awg0`, а
  обратный путь до их источника по main лежит через `end0` — строгий
  rp_filter такое роняет. Loose пропускает, если маршрут к источнику есть
  хоть где-то; полное отключение не нужно. Ставится для `all`, `default`,
  LAN и аплинка; аплинк — командой при подъёме (PostUp), в sysctl-файл его
  не вписывать: интерфейса на момент применения ещё нет.
- **IPv6 на LAN-интерфейсе выключается** (`disable_ipv6=1`): наборы только
  v4, а AAAA-ответ увёл бы трафик мимо туннеля.

### 3.2 Резолвер

dnsmasq на малине, конфиги в `/etc/dnsmasq.d/awg-gw-*.conf`, единственный
владелец — скрипт обвязки:

```
# awg-gw-base.conf
bind-dynamic                      ← с bind-interfaces демон падает, пока awg0 не поднялся
listen-address=127.0.0.1,<LAN-адрес малины>
no-resolv
server=<RESOLVER>@awg0            ← апстрим ЧЕРЕЗ АПЛИНК: без @awg0 запрос уходит
                                    линком с адресом линка, и ВПС не отвечает
cache-size=10000
stop-dns-rebind
conf-file=/etc/dnsmasq.d/awg-gw-doh.conf
```

- **Апстрим — свой резолвер ВПС** (`awg-bot resolver`, адрес `<подсеть>.1`
  из `DNS =` устройства слота). Без него провайдер одной из квартир ломал
  ответы («missing question section»), и в наборы попадали подменённые
  адреса. Если у ВПС резолвер не поднят — запасной апстрим `1.1.1.1@awg0`:
  тоже через туннель, тоже без подмены, но без DoH-защиты и кэша ВПС;
  экран включения об этом говорит.
- **DoH-хосты** — статический список известных (dns.google, cloudflare-dns,
  quad9, mozilla, nextdns, adguard…) с ответом `0.0.0.0`: браузер, не
  сумевший поднять DoH, возвращается к системному DNS. **DoT** —
  `iifname "end0" tcp dport 853 drop` в forward `awg_home`. Как на ВПС для
  клиентов.
- `AmbientCapabilities=CAP_NET_ADMIN` в оверрайде юнита dnsmasq — сразу, а не
  когда наборы окажутся пустыми молча.
- Оверрайд `Restart=on-failure`.
- DHCP роутера раздаёт адрес малины как DNS — сторона роутера (§3.6).

### 3.3 Списки

Три слоя, как в ручном, но с одной моделью данных и одним владельцем:

| файл | содержимое | кто пишет |
|---|---|---|
| `awg-gw-vpn-feed.conf` | домены из фида (`Russia/inside-dnsmasq-ipset.lst` → `nftset=…awg_home#lan_vpn4`) | агент, по расписанию |
| `awg-gw-vpn-user.conf` | домены, добавленные руками — в туннель | агент, из чата / CLI |
| `awg-gw-ru-user.conf` | домены-исключения — российский адрес напрямую (`lan_ru4`) | агент, из чата / CLI |
| набор `lan_vpn4` (подсети) | itdoginfo `Subnets/IPv4/{telegram,meta,twitter,cloudflare,discord}` + Google `goog.json` | агент, по расписанию |
| `/var/lib/awg-gw/lan_vpn4.dump` | слепок набора | агент после каждого обновления; скрипт грузит при старте |

- **Обновление — задача агента**, не systemd-таймер: тот же планировщик,
  что и у прочих сетевых задач, с джиттером (строго периодический запрос —
  маячок), раз в 6 ч, первая — через 3 мин после старта. Панель показывает
  «Списки: N доменов, M подсетей, обновлены N ч назад», как основной бот.
- **Доступность фидов.** `raw.githubusercontent.com` с v2.24.6 идёт через
  аплинк (`gh_nets4`) — из любой квартиры. `gstatic.com` — напрямую.
- **Вычитание исключений**: домен из `ru-user` убирается из фидового файла
  (dnsmasq применяет одну директиву на домен, и какая победит — зависит от
  порядка чтения каталога). Логика ручного слоя переезжает как есть.
- **Дифф-скип**: dnsmasq перезапускается только когда файл фида изменился
  (рестарт роняет кэш всей квартиры). Именно `restart`: SIGHUP конфиги не
  перечитывает.
- **Слепок набора** закрывает «первую минуту после загрузки»: скрипт
  обвязки при старте заливает `lan_vpn4` из слепка до того, как агент
  сходит за свежими фидами. В ручном слое этой минуты не было чем закрыть.
- **Персональные списки** правятся с панели агента и командой на малине
  (`awg-bot lan add <домен>`, `awg-bot lan ru <домен>`, `awg-bot lan del`,
  `awg-bot lan list`) — `awg-add` из ручного слоя, переехавший в общий
  инструмент. После правки: рестарт dnsmasq, резолв домена, адреса сразу в
  набор. Персональные списки — свои у каждой квартиры (открытый вопрос
  §11.1).
- **Запрещённые домены** — те же, что на ВПС (`routing_denylist`): хост
  бота, почта email-выхода. Увести в туннель собственную инфраструктуру —
  запереть себя.

### 3.4 Что кладёт скрипт обвязки (`routing-gw-setup.sh`, раздел «5. Домашняя сеть»)

Только при `LAN_MODE=1`; без него раздел печатает «выключено» и **снимает
всё своё**, если было (выключили функцию — перевыпустили — применили).

```
/etc/nftables.d/awg-home.nft                таблица awg_home (наборы без delete, цепочки flush+add)
/etc/sysctl.d/98-awg-gw-lan.conf            rp_filter=2 all/default/<LAN>, disable_ipv6 на LAN
/etc/dnsmasq.d/awg-gw-base.conf, awg-gw-doh.conf
/etc/dnsmasq.d/awg-gw-vpn-user.conf, awg-gw-ru-user.conf   (создаются пустыми, не перезаписываются)
/etc/systemd/system/dnsmasq.service.d/awg-gw.conf          (Restart, CAP_NET_ADMIN)
/etc/systemd/system/awg-quick@<аплинк>.service.d/awg-gw.conf  (StartLimitIntervalSec=0, Restart)
/etc/systemd/network/99-awg-gw-unmanaged.network           ([Match] Name=awg* / Unmanaged=yes)
/opt/awg-gw/lan-lists.sh                    фиды → conf + набор + слепок (зовёт агент и `awg-bot lan update`)
/opt/awg-gw/lan-domain.sh                   add/ru/del/list для персональных списков (зовёт агент и CLI)
```

Оверрайд `awg-quick@` и `unmanaged.network` — **не только для A**: аплинк и
линк есть у каждого шлюза, а именно они страдали от networkd (OMV: любой
Apply останавливал оба туннеля молча) и от лимита перезапусков на загрузке.
Ставятся всегда, в разделе аплинка.

Реассерт (юнит при загрузке, `systemctl restart awg-link-gw`): таблица
`awg_home` — цепочки заново, наборы на месте, слепок в `lan_vpn4`; dnsmasq
не трогается, если конфиги не изменились. Откат `--rollback`: снять таблицу,
sysctl-файл, конфиги dnsmasq (персональные списки **остаются** — это данные
человека, файлы переименовываются в `.bak`), оверрайды, скрипты.

`--plan` перечисляет всё; проверка занятого :53 (другой dnsmasq, Pi-hole,
systemd-resolved на 0.0.0.0) — до применения, с честным отказом.

### 3.5 Агент

- **Задача** `lan_lists` в планировщике роли gateway: раз в 6 ч с джиттером
  40 %, первая через 3 мин; зовёт `lan-lists.sh`, результат — в панель и в
  журнал; два провала подряд — замечание (не критичное).
- **Панель**, новый блок после линка:
  ```
  🏠 За шлюзом — без VPN: 🟢 работает
     заворот с роутера: есть (1 234 пакета за такт)
     резолвер: жив, апстрим 10.9.1.1 через awg0
     списки: 1 180 доменов, 412 подсетей, обновлены 2 ч назад; свои: 4 в туннель, 1 напрямую
  ```
- **Проверки** в мониторе здоровья: dnsmasq active и слушает LAN-адрес;
  апстрим отвечает через аплинк (один резолв тестового имени); наборы не
  пусты; таблица `awg_home` на месте с правилами по файлу; **заворот с
  роутера** — счётчик правила маркировки в prerouting растёт между тактами
  (нет пакетов из LAN сутки — «роутер не заворачивает трафик на шлюз»);
  IPv6 на LAN выключен.
- **Кнопки**: «➕ В туннель» / «➕ Напрямую» (ввод домена, тот же разбор, что
  у `awg-add`: схема и `www.` отбрасываются, денилист), «📋 Свои списки»
  (показать/удалить), «🔄 Обновить списки». Приглашения — служебные,
  убираются после ответа.
- **Устройство самого шлюза и РФ-доступ.** Шлюзу РФ-доступ не нужен никогда:
  его российский трафик на ВПС вернулся бы по линку на ту же малину. Сегодня
  устройство слота в списке РФ-доступа есть (и даже первым). В 3.0 — снимается
  **при назначении устройства шлюзом** (`gateway_setup`), устройства-шлюзы
  исключаются из списка переключателей и из счётчиков «включено на N из M»,
  ситуация «включить РФ-доступ шлюзу» становится недостижимой, и текста для
  неё нет. От `lan_mode` это не зависит — этап 1 (§10).

### 3.6 Роутер

Бот в роутер не лезет. При включении A основной бот показывает требования и
рецепт под модель (MikroTik RouterOS 7, OpenWrt) — тексты из
`gateway-lan-split-concept.md`, часть 4, переносятся в поставку как экран
«📖 Настройка роутера» (в карточке слота и в панели агента). Требования —
без них функция не имеет смысла:

- policy-based routing: весь трафик LAN, кроме самой малины и трафика
  внутри LAN, — на адрес малины;
- разрешение асимметричного пути (ответ от малины к клиенту идёт мимо
  роутера) — правило выше `drop invalid`;
- аппаратное ускорение (fasttrack, flow offloading) — выключить;
- DHCP раздаёт DNS = адрес малины; у малины статический адрес.

Что бот **проверяет**: заворот — по счётчику (§3.5); DNS — по факту
запросов с LAN-адресов к dnsmasq (счётчик `iifname "end0" udp dport 53` в
input `awg_home`). Обе проверки — в панели агента. Карточка слота на ВПС
показывает только то, что знает ВПС, то есть флаг: состояния малины
основной бот не видит (открытый вопрос §11.2).

### 3.7 Ограничения — сказать при включении

- **Малина становится точкой отказа квартиры.** Сейчас её падение оставляет
  без РФ-доступа клиентов ВПС, и слоты переключаются. С A падение малины
  оставляет квартиру без интернета вовсе: роутер заворачивает на конкретный
  адрес, переключение слотов не поможет. Прямым текстом в диалоге
  включения.
- **Собственные VPN-клиенты на устройствах** перехватывают маршрут и DNS —
  не наш случай, но симптом стоит описать.
- **DoH в браузерах**: закрыт списком, но новые эндпоинты появляются;
  симптом «часть сайтов через раз» — в тексте проверки.

## 4. Функция B: доступ между подсетями за шлюзами

### 4.1 Как ходит пакет

192.168.1.5 (дом 1, Pi 4) → 192.168.68.7 (дом 2, Pi 5); обратно зеркально.

```
дом 1: 192.168.1.5 ──► Pi4 (end0)
   awg_home prerouting: daddr ∉ lan_ru4, ∉ lan_vpn4 → без метки → main
   маршрут 192.168.68.0/24 dev awglink          ← из AllowedIPs, ставит awg-quick   НОВОЕ
   криптофильтр awglink: 192.168.68.0/24 ∈ AllowedIPs пира ВПС                     НОВОЕ
   маскарада нет: saddr ∉ tunnel_nets4, oif ≠ end0
              ▼ awglink
ВПС: пир Pi4 = 0.0.0.0/0 (Table = off)          ← уже так
   awg_bot_guard forward (policy drop): iifname awglink oifname awglink2 accept   НОВОЕ
   маршрут 192.168.68.0/24 dev awglink2 (main)  ← уже так, ensure_home_routes
   маскарада нет (saddr ∉ tunnel_nets4); MSS-кламп на awglink2 — уже стоит
              ▼ awglink2
дом 2: криптофильтр awglink2 у Pi5 (пир ВПС): CLIENT_SUBNET, LINK_CIDR, +192.168.1.0/24   НОВОЕ
   awg_gw_guard forward: iifname awglink2 ip saddr @peer_nets4 accept              НОВОЕ,
       выше iifname awglink2 ip daddr @private4 drop
   awg_home postrouting: saddr 192.168.1.x ≠ <LAN Pi5> → маскарада нет → адреса настоящие
              ▼ end0 → 192.168.68.7
ответ: 192.168.68.7 → роутер заворачивает на Pi5 (функция A!) → маршрут 192.168.1.0/24 dev awglink2 → …
```

Последняя строка — и есть зависимость B от A: без заворота ответ ушёл бы в
WAN роутера и умер. С A он приходит на малину гарантированно, и бот об этом
знает по флагу, а не по обещанию.

Что из разговора оказалось не так: AllowedIPs пира шлюза **на ВПС** менять
не нужно — там `0.0.0.0/0` при `Table = off` с самого начала. Не хватает
только форвардинга линк ↔ линк.

### 4.2 Что меняется

- **ВПС, `nftguard`**: `iifname {линки} oifname {линки} accept` в forward
  после `invalid drop`, при включённом тумблере и ≥2 линках. Тумблер читается
  из настроек, смена перевыставляет таблицу (`on_change`, как у файервола):
  выключение действует на ВПС сразу, без перевыпуска. Без наборов подсетей
  — в линк со стороны шлюза попадает только то, что пропустил его
  AllowedIPs, а таблица собирается и из CLI без БД.
- **Конфигурация шлюза**: `PEER_HOME_NETS` → в AllowedIPs пира ВПС
  (`--apply`/`--rekey` пишут сразу, `--bundle` правит строку по образцу
  правки порта в Endpoint) → маршруты ставит awg-quick, переживают ребут.
- **`awg_gw_guard`**: набор `peer_nets4`, правило по **источнику** выше drop
  по приватным. Сама малина с той стороны доступна (input policy accept —
  чужих подсетей в `tunnel_nets4` нет). Доступ — **только между локальными
  сетями шлюзов**, то есть между сетями админа; клиентам VPN в локальные сети
  хода нет, как и сейчас (`@private4 drop`, исключение — устройства админа).
  Это подчёркивается в текстах (§6).
- **Чужие подсети слота N** = `home_subnets` слотов с `lan_mode=1`, кроме N,
  без дублей, исключая пересекающиеся с собственными. Тумблер выключен или
  у слота `lan_mode=0` — пусто.
- **Пересечение подсетей** (`overlaps`, ловит вложенность) — предупреждение
  при вводе и в карточке, не отказ: доступ для этой пары недоступен, пока
  пересекаются; сменили — разблокировалось само, и наоборот.

### 4.3 Перевыпуск

| событие | чья конфигурация устарела |
|---|---|
| тумблер B включён/выключен | всех слотов с непустыми чужими подсетями |
| `lan_mode` слота N включён/выключен | N (раздел A) и всех остальных (чужие подсети) |
| изменены `home_subnets` слота N | N (LAN-адрес резолвера) и всех остальных |
| добавлен/снят слот с `lan_mode=1` и подсетями | всех остальных |
| пересечение появилось/исчезло | обоих слотов пары |
| изменён состав устройств админа | всех (как сейчас) |
| резолвер ВПС поднят/снят | всех с `lan_mode=1` (апстрим) |

Механизм — снимок зависимостей бандла: `gw_bundle_ssh_allow_{slot}`
расширяется до `gw_bundle_deps_{slot}` = `ADMIN_IPS` + `LAN_MODE` +
`HOME_SUBNETS` + `PEER_HOME_NETS` + `RESOLVER`; напоминание один раз на
расхождение, по слоту, своим текстом: какая из зависимостей изменилась.

## 7. Миграция ручного слоя

Обе малины уже несут ручной слой. Скрипт обвязки при первом применении с
`LAN_MODE=1` находит его по файлам и **переезжает, а не ломает**:

1. `home-split.service`, `awg-lists.timer`/`.service` — stop, disable, файлы
   в `.bak`;
2. `ip rule … fwmark 0x10 lookup 100` — снять; таблица `home_split` —
   `delete table`;
3. `/etc/dnsmasq.d/awg-base.conf`, `vpn-domains.conf` — снять (свои
   заменяют); `ru-force.conf` → `awg-gw-ru-user.conf`, `user-managed.conf`
   → `awg-gw-vpn-user.conf` с заменой имени набора
   (`home_split#vpn4` → `awg_home#lan_vpn4`, `#ru4` → `#lan_ru4`);
4. `/etc/sysctl.d/99-home-split.conf`, оверрайды `dnsmasq`/`awg-quick@awg0`,
   `99-awg-unmanaged.network`, `/usr/local/sbin/home-*.sh`,
   `/usr/local/bin/awg-add` — в `.bak` (свои встают на место);
5. отчёт применения перечисляет, что перенесено.

Роутеры не трогаются: их настройка совпадает с требованиями A.

Порядок на живых квартирах: обновить основного бота → обновить агентов →
включить A у обоих слотов → перевыпустить и применить конфигурации (в этот
момент миграция) → проверить панель агента (заворот, резолвер, списки) →
включить B → перевыпустить и применить ещё раз → ping между квартирами.

## 8. Границы безопасности

- Персональные списки и наборы — только на малине; в бандл не едут.
- Резолвер слушает только LAN-адрес и localhost; из туннеля к нему
  доступа нет (input guard: `tunnel_in`).
- Доступ между квартирами — полный в обе стороны, но только между
  локальными сетями шлюзов, то есть сетями админа; клиентам VPN локальные
  сети закрыты, как и сейчас (`@private4 drop`, исключение — устройства
  админа). Диалог включения это говорит.
- В файле конфигурации появляются домашняя подсеть и адрес резолвера —
  не секреты; секреты те же, что были.

## 9. Эксплуатация

- A: падение малины = квартира без интернета (§3.7); обновление агента
  перезапускает только агента, dnsmasq и таблицы живут.
- B: задержка ~150 мс, живёт, пока подняты оба линка, от активного слота
  не зависит.
- Полоса B — минимум из двух домашних аплоадов через ВПС.

## 10. Версия, адресаты, этапы

v3.0.0, обе роли (`#requires_main_2.24.0`, `#requires_gw_2.10.0`), схема
БД (`gateways.lan_mode`). Обеим малинам — перевыпуск и применение.

Этапы, каждый — рабочий релиз:

1. **База аплинка** (обеим ролям, без флагов): оверрайд `awg-quick@`,
   `unmanaged.network`, rp_filter loose, MSS-кламп в аплинк в guard;
   устройства-шлюзы вне списка РФ-доступа, флаг снимается при назначении;
   «Домашние подсети» → «Локальные подсети». Мелкий, снимает грабли ручного
   слоя.
2. **A**: поле, флаг, бандл, раздел скрипта, dnsmasq, `awg_home`, слепок,
   миграция ручного слоя, задача списков у агента, панель и проверки,
   `awg-bot lan`, рецепты роутера, запрет РФ-доступа у устройства слота.
3. **B**: тумблер, `PEER_HOME_NETS`, AllowedIPs, `peer_nets4`, форвардинг
   ВПС, снимок зависимостей и напоминания, тексты.
4. **Персональные списки из чата** у агента (кнопки) — можно вместе с 2,
   можно следом.

## 11. Открытые вопросы — решены 20.09.2026

1. **Персональные списки** — свои у каждой квартиры. Общие требовали бы
   канала синхронизации или перевыпуска на каждый домен.
2. **Состояние A на ВПС** — только флаг в карточке; живое состояние
   (трафик с роутера, резолвер, списки) — в панели агента.
3. **Запасной апстрим без резолвера ВПС** — предупреждение, не отказ:
   `1.1.1.1@awg0`, с настоятельной рекомендацией настроить резолвер.
4. **Кому открыт доступ между подсетями** — только локальным сетям шлюзов,
   то есть сетям админа, в обе стороны полностью, включая сами малины.
   Клиентам VPN — никогда; это подчёркнуто в диалоге включения и в §8.
5. **Маскарад в LAN для B как запасной режим** — снят: заворот есть по
   определению A.
6. **Три слота** — обобщается само; потолок 2 не меняется.
7. **IPv6** — нет.
