# awg-bot — Telegram-бот управления AmneziaWG (хост бота)

Telegram-бот управления AmneziaWG: роли админ/клиент/друг, инвайты, периоды
подписки с блокировкой трафика при истечении, приостановка подписки («в отпуск»)
с аварийным email-выходом, накопительная статистика, двусторонняя синхронизация
с приложением Amnezia. Мониторинг железа бот снимает сам — локально, с того же
хоста (co-located архитектура).

Документ самодостаточен: всё для установки и эксплуатации бота — ниже.

---

## 1. Роль компонента

Бот ходит в докерный контейнер AmneziaWG (`docker exec`), правит `awg0.conf` /
`clientsTable`, управляет блокировками через iptables внутри контейнера, ведёт
состояние в собственной SQLite-БД и общается с пользователями по Telegram Bot API.

Бот **co-located** с awg-контейнером — стоит на том же хосте и управляет им
локально; по сети до контейнера не ходит. Единственный внешний канал —
Telegram Bot API (плюс, если включён email-выход, исходящий IMAP/SMTP к вашему
почтовому серверу). Топологию установщик определяет сам из живого контейнера.

---

## 2. Требования

- VPS с Debian/Ubuntu-подобной системой и **собственным ядром** (KVM, не
  OpenVZ/LXC): модуль AmneziaWG собирается из исходников и загружается в ядро.
  Установщик ставит `dkms`, `build-essential` и заголовки ядра сам.
  Уже развёрнутая AmneziaWG не нужна — сервер поднимает установщик.
- Python **3.12+** (используется `enum.StrEnum`; сборка ведётся и тестируется на
  3.12 — не полагайтесь на голый минимум 3.11).
- `root` (управление awg, nftables, systemd).
- Исходящий доступ к Telegram Bot API.

Установки прежней схемы (бот при докерной Amnezia, `runtime: docker`)
продолжают работать как работали: ни ядро, ни сервер им не пересоздаются.

## 3. Быстрый старт

Поставка — **один архив** `awg-bot.tgz`: внутри и код, и установщик.
Установка — **одна команда** на чистом хосте:

```bash
curl -fsSL https://raw.githubusercontent.com/<repo>/main/install/awg-bot-install.sh | sudo bash
```

Аргументы передаются после `-s --`:

```bash
curl -fsSL …/awg-bot-install.sh | sudo bash -s -- --role gateway   # агент на шлюзе (если GitHub с него доступен;
                                                                   # штатно — файл первого применения, §6c)
curl -fsSL …/awg-bot-install.sh | sudo bash -s -- --port 51820     # порт awg
curl -fsSL …/awg-bot-install.sh | sudo bash -s -- --advanced       # все вопросы
```

**Что при этом происходит.** По ссылке едет не архив, а сам установщик. Из
трубы он видит, что запущен без файла, качает поставку во временный каталог,
сверяет её sha256 с релизом GitHub и **передаёт управление установщику из
архива**. Это не формальность: логика установки принадлежит поставке и обязана
ехать вместе с ней, иначе на хосте выполнялся бы код из ветки `main`, а
ставился бы релиз, и разъезжались бы они молча. Сорвалась установка — временный
каталог убирается тем, кто его создал.

Сверка целостности необязательна по последствиям: GitHub не ответил — ставим
дальше и говорим строкой (загрузку и так прикрывает TLS); не совпало —
отказываемся начинать. Для своей сборки есть `--skip-verify`.

Если архив уже скачан, работает и прежний путь:

```bash
tar xzf awg-bot.tgz && sudo bash install/awg-bot-install.sh
```

Без `--port` порт awg случайный (высокий), подсеть `10.8.1.0/24`. Оба ключа
относятся только к СОЗДАВАЕМОМУ серверу: на хосте, где awg уже настроен, они
игнорируются.

Установщик развернёт код в `/opt/awg-bot`, проведёт по шагам (топология,
секреты), соберёт валидный конфиг, поставит и запустит сервис, заведёт команду
`awg-bot` и удалит за собой архив с установщиком. Дальнейшее управление —
командой `awg-bot` (`status`, `logs`, `reconfigure`, `update`, `backup`,
`restore`, `uninstall`). Логи: `awg-bot logs`.

## 4. Что делает установщик (`awg-bot-install.sh` → `awg-bot`)

| Шаг | Действие |
|-----|----------|
| Preflight | Проверяет `root`, ищет Python 3.12+ (при отсутствии предлагает поставить через `apt`/deadsnakes PPA). |
| AmneziaWG | Ставит ядро версии, **прибитой к поставке** (`install/awg.lock`): модуль через DKMS под все установленные ядра и `amneziawg-tools`, из исходников. Уже стоит та же версия — пропускает. |
| Сервер | На чистом хосте создаёт `awg0.conf` сам: ключи, случайный высокий порт, обфускация, адрес `.1/24` (клиенты с `.2`), `ip_forward`, автозагрузка `awg-quick@awg0`. Сервер уже есть — не трогает и берёт топологию из него. |
| Код | Из трубы: качает архив во временный каталог, сверяет sha256 и передаёт управление установщику ИЗ архива. Дальше тот раскладывает поставку в `/opt/awg-bot`, симлинкует команду `awg-bot` и передаёт управление `awg-bot reconfigure --first-run`. |
| Уборка | В конце удаляет архив и временный каталог распаковки. Каталог — только если он в `/tmp` или `/var/tmp`: поставку могли распаковать и в домашний каталог. |
| venv | Создаёт `venv`, ставит `requirements.txt`. |
| Каталоги FHS | `/etc/awg-bot/conf` (конфиг), `/etc/awg-bot/env` (секреты, `600`), `/var/lib/awg-bot` (БД+бэкапы, `700`). |
| Конфиг | Копирует шаблоны `conf/*.yaml` (только отсутствующие) и **пишет валидные значения** из ответов (топология). |
| Секреты | Спрашивает **только** `BOT_TOKEN`. Кто админ — выясняет сам: печатает одноразовый код, ждёт его в чате бота и берёт id отправителя. Не вышло — спросит `ADMIN_ID` как раньше. |
| Топология | Ничего не спрашивает: внешний адрес — автодетектом, имя сервера «Сервер 1», таймзона из системы, порт и подсеть уже записаны при создании сервера. Правится в боте (⚙️ Настройки → 🖥 Сервер) и через `reconfigure`. |
| DNS клиентов | Поднимает **свой резолвер**: dnsmasq на собственном адресе сервера в туннеле (`<подсеть>.1`), оба поля DNS в конфигах клиентов — на него (§4c). Не поднялся — предупреждение, поля остаются публичными, позже `awg-bot resolver install`. |
| Файервол | Один вопрос: ограничить ли SSH адресом, с которого вы подключены (`y` / свой список / `N`). Применяется с таймером отката на 15 минут, а подтверждение с кнопками приходит в чат само. |
| Первое устройство | Печатает ссылку, QR и путь к `.conf` прямо в терминал: Telegram может не открываться — за этим VPN и ставят. |
| Почта | Не спрашивает: ящик подключается из чата (**⚙️ Настройки → ✉️ E-mail**, §6a). |
| Шифрование бэкапов | Не спрашивает: экран в чате (**⚙️ Настройки → 💾 Резервное копирование**). |
| Валидация | `config.validate()` — при нехватке параметра падает **до** запуска, с указанием, что и где задать. |
| Сервис | Генерирует и ставит `systemd`-юнит `awg-bot`, `enable --now`. |

Установщик — greenfield-only. Поверх **существующей** установки он ничего не
переписывает молча: обнаружив рабочий venv в `/opt/awg-bot`, предлагает меню —
обновить код из этой поставки (`update`), восстановить из резервной копии
(`restore`), удалить бота (`uninstall`) или выйти. Перенастройка живой
установки — `sudo awg-bot reconfigure`: тот же визард, текущие значения
предлагаются дефолтами (Enter — оставить как есть).

## 4a. Версия AmneziaWG прибита к поставке

`install/awg.lock` — манифест: теги модуля ядра и `amneziawg-tools`, их
sha256, **поколение** протокола и идентификатор, который уезжает в `vpn://`.
Версию awg определяет версия бота, и меняет её только новая поставка.

**Тождество ведётся по ТЕГУ, а не по версии.** Апстрим не бампает `version.h`:
теги `v3.1.20260812`, `…0827`, `…0828`, `…0906` все рапортуют `3.1.20260812`.
Сверка по `modinfo -F version` их не различает вовсе — и молча пропустила бы
смену тега в манифесте, ради которой механизм и сделан. Поэтому установщик
записывает собранный тег в `/etc/awg-bot/awg.state` и сверяет с манифестом, а
строка версии остаётся для показа. Нет записи о теге (собирали руками или до
появления состояния) — модуль пересобирается: узнать правду иначе неоткуда.

**«Работает ли то, что собрано» — по `srcversion`.** Это хеш исходников, и он
разный там, где строка версии одинакова. Сравниваются загруженный
(`/sys/module/amneziawg/srcversion`) и лежащий на диске
(`modinfo -F srcversion`); расходятся — нужен `awg-bot awg reload` или
перезагрузка.

**Дерево DKMS называется по тегу** (`/usr/src/amneziawg-3.1.20260906`), иначе
разные теги делили бы один каталог — с тем же исходом, что у апстримного
`1.0.0`: новая сборка затирает прежнюю.

**Почему не PPA.** Пакет из репозитория обновляется `apt` вместе со всем
остальным, и однажды ядро уезжает вперёд бота: клиенты прежнего поколения
перестают ходить, а причины не видно. Поэтому только сборка из исходников на
теге; репозиторий не подключается никогда.

**DKMS-дерево под версией.** Апстримный `dkms.conf` у всех сборок объявляет
`PACKAGE_VERSION="1.0.0"` — дерево одно, и новая установка затирает старую
вместе с возможностью отката. Установщик кладёт дерево в
`/usr/src/amneziawg-<версия>` с настоящей версией: сборки сосуществуют, а при
смене ядра через `apt` DKMS пересобирает модуль сам. Сборка идёт явным
перебором **всех установленных ядер**: `dkms install` без `-k` покрывает
только текущее, и загрузка в другое оставила бы хост без awg.

```bash
awg-bot awg status     # что стоит против манифеста (код 3 — расходятся)
awg-bot awg install    # довести до манифеста
awg-bot awg reload     # подменить работающий модуль установленным:
                       # ВСЕ awg-интерфейсы лягут на секунды
awg-bot awg prune      # убрать сборки прежних тегов (DKMS, /usr/src, кэш);
                       # отказывается, пока загружен не тот модуль, что собран
awg-bot awg plan       # что сделал бы install, ничего не меняя
```

**Прежние сборки не копятся.** Дерево прежнего тега живёт ровно до тех пор,
пока нужно для отката: при совместимой смене — до успешного старта бота на
новом модуле, при смене поколения — до финала переезда профилей. Дальше его
убирает сам бот.

Модуль на лету не подменяется: `rmmod` требует, чтобы ни один интерфейс не был
поднят. Поэтому `reload` гасит все awg-интерфейсы и поднимает обратно, а без
него собранная версия начнёт работать после перезагрузки.

### Поколения и обновление ядра

Обновление бота **трогает ядро**: версия awg — часть поставки. Порядок фаз у
апдейтера такой:

1. модуль и тулзы собираются из новой поставки, пока на диске ещё рабочая
   установка. Не собралось — код не подменён, версия прежняя, сервис поднят
   обратно, причина в выводе;
2. код подменяется;
3. если тег модуля изменился, работающий модуль подменяется собранным: все
   awg-интерфейсы гасятся и поднимаются обратно. Тег тот же — этого шага нет;
4. сервис стартует и отчитывается в чат, как обычно.

Пауза туннелей на третьем шаге — секунды. На шлюзе это значит потерю Telegram
до подъёма аплинка: отчёт придёт после.

**Поколение** в манифесте меняется только тогда, когда новое ядро не
обслуживает клиентов прежнего. Тогда апдейтер сам поднимает **второй
интерфейс** рядом со старым (свободное имя, свободная подсеть, параметры
нового поколения) и пишет ключи переезда в `app.yaml`, а бот при каждом старте
просит начать **переезд профилей**, пока он не начат. Дальше работает уже
описанная механика (§3 роадмапа): у каждого устройства рождается двойник,
люди переносят конфиги когда удобно, старые пиры всё это время работают.

Три числа, которые за этим стоят: поколение **поставки** (файл `awg.lock`),
поколение **основного интерфейса** и **цель идущего переезда** (оба — в
`/etc/awg-bot/awg.state`, его ведут установщик и финал переезда). Отсюда
правила:

| Поставка | Переезд | Что происходит |
|---|---|---|
| того же поколения | любой | модуль подменяется на месте |
| новее применённого | не идёт | поднимается второй интерфейс, бот просит переехать |
| равна цели переезда | идёт | обновляемся, переезд продолжается |
| дальше цели переезда | идёт | **обновление недоступно**, пока переезд не завершён |

Последняя строка — не перестраховка: профили, размазанные по трём
интерфейсам, мигрировать нечем. Экран «Обновления» показывает причину,
уведомление о такой версии не приходит до финала.

**Финал переезда переставляет основной интерфейс.** Новый становится
основным в `app.yaml` (интерфейс, подсеть, порт, идентификатор протокола
нового поколения), старый гасится и снимается с автозагрузки, применённое
поколение поднимается до цели, бот перезапускается. Без этого шага новые
устройства продолжали бы рождаться на старом интерфейсе — на параметрах, ради
ухода от которых переезд и затевался.

**Идентификатор протокола — атрибут интерфейса.** Он вморожен в каждую
выданную ссылку: у старых профилей остаётся прежний, двойники получают новый,
после финала новый достаётся всем новым устройствам.

### Смена порта или подсети — переездом, из бота

Порт и подсеть вморожены в каждую выданную ссылку, поэтому правкой не меняются.
Раздел «🖥 Сервер AWG» показывает их и даёт кнопку «🚚 Сменить порт или
подсеть»: бот поднимает второй интерфейс (свободное имя, свободная подсеть,
порт случайный или заданный вручную), пишет ключи переезда в `app.yaml` и
перезапускается. Дальше работает обычный переезд профилей: у каждого
устройства рождается двойник, люди переносят конфиги когда удобно, старые
пиры работают до финала.

**Запрет симметричный.** Переезд по кнопке и переезд по смене поколения — один
механизм с одной целью:

- идёт переезд по поколению — кнопка в «Сервере» не показывается, а раздел
  прямо говорит, почему смена порта сейчас невозможна;
- идёт переезд по кнопке — поставка с новым поколением не предлагается, а
  установщик, увидев поднятый второй интерфейс, **не трогает цель**: иначе на
  финале хост записался бы перешедшим на ядро, которого не видел.

После финала любого переезда бот сам проверяет, не ждёт ли смена поколения, и
предлагает подготовить следующий переезд кнопкой. Без этого получался тупик:
второй интерфейс заводит только обновление, а оно уже прошло.

**Раскладка подсети.** Новые установки: сервер `.1`, клиенты с `.2`
(`ip_host_start: 2`). У установок прежней схемы сервер на `.0`, клиенты с `.1`;
их конфиг не мигрирует, установщик определяет раскладку по адресу живого
интерфейса.

Раскладка делает возможным **свой резолвер**: адрес `.1` принадлежит самому
серверу, dnsmasq слушает прямо на нём, а клиентские конфиги называют его в поле
DNS напрямую — §4c.

---

## 4c. Свой DNS-резолвер клиентов

**Что это.** dnsmasq на сервере, слушающий собственный адрес интерфейса в
туннеле (`<подсеть>.1`); в конфигах клиентов **оба** поля DNS указывают на него.
Ведёт `install/awg-resolver-setup.sh` (`/etc/dnsmasq.d/awgbot-resolver.conf`:
`bind-interfaces` и `cache-size` — только если их нет в других файлах dnsmasq,
они однократные на всю конфигурацию; апстримы `1.1.1.1`/`1.0.0.1`,
`stop-dns-rebind`, NXDOMAIN на DoH-эндпоинты и канарейку Firefox; override
юнита с `Restart=on-failure` без лимита попыток — адрес интерфейса появляется
позже старта демона). Конфиг проверяется `dnsmasq --test` до рестарта; не
прошёл или демон не поднялся — свой файл откатывается.
CLI: `awg-bot resolver status | install [addr] | add <addr> | remove <addr>`.

**Зачем.** Публичный адрес в поле DNS — это Chrome/Edge, которые молча уходят
на DoH мимо любого перехвата `:53`; набор адресов условной маршрутизации
наполняет только наш резолвер, и у такого человека РФ-сайты ругаются на адрес
«через раз». Приватному адресу браузеру не за что подхватить DoH. Заодно
запросы клиентов не уходят третьей стороне открытым текстом, есть кэш и защита
от DoH-обхода и DNS rebinding — с первого дня, а не только со шлюзом.

**Свежая установка** получает его сразу, без вопросов. **Живая установка с
публичным адресом** видит инфобокс при каждом старте (до решения) и кнопку
«🔒 Свой DNS-резолвер» в «🖥 Сервер AWG» с тремя ответами: **переехать
сейчас** (открывает подготовку переезда — адрес вшит в каждую ссылку, значит
перевыпуск), **при следующем переезде** (ручном или при смене поколения —
конфиги и так перевыпускаются, DNS сменится бесплатно), **не нужно** (кнопка
остаётся, передумать можно). Docker-режим не предлагается: сервер там на `.0`.

**Переезд.** При включении рычага резолвер начинает слушать `<новая
подсеть>.1` — **до** рождения двойников (не поднялся — переезд не начинается);
двойники получают этот адрес (`app.docker.migration_dns`), старые пиры — прежний.
Финал переписывает `dns1/dns2`, снимает старый адрес с резолвера; отмена
снимает новый. На хосте, где адрес уже приватный (`10.9.1.1`), переезд обязан
дать новый — старый умирает вместе со старым интерфейсом.

**Обвязка маршрутизации** при резолвере бота dummy-интерфейс `awgdns0` не
поднимает: перехват `:53` старых профилей ведёт на адрес резолвера, а в своём
`awgbot-base.conf` она держит только адрес перехвата. `--rollback` **не
роняет** `awgdns0` и его dnsmasq, пока `10.255.53.1` (или фасад на нём) указан
в `dns1/dns2`: адрес вшит в выданные конфиги, снимет его только переезд.

**Здоровье.** Тик монитора шлёт UDP-запрос на каждый приватный адрес из
конфига: не отвечает — алерт со звуком (и на почту, если запасной канал
включён) один раз, «снова отвечает» — один раз; preflight предупреждает на
старте. Упавший резолвер = люди без DNS, поэтому юнит перезапускается сам.

## 5. Модель конфигурации

Два раздельных, предсказуемых источника:

- **Топология и правила → yaml** в `/etc/awg-bot/conf`. Это источник истины.
  Установщик генерит валидные значения под ваши ответы; в эксплуатации правите
  файлы руками **на холодную**. Живут в `/etc`, поэтому **переживают обновление
  кода** (код — в `/opt/awg-bot`, это разные каталоги).
- **Секреты → env** в `/etc/awg-bot/env` (`600`). Только чувствительное
  (`BOT_TOKEN`, `ADMIN_ID`, ключи шифрования бэкапов). Для топологии env **не
  используется**.

Приоритет для деплой-значений: **активная строка yaml → хардкод-дефолт**.
Env-«люка» для топологии нет намеренно — вместо него `config.validate()` при
старте падает с сообщением вида:

```
Не заданы обязательные параметры конфига: app.yaml: network.server_host;
```

Где читается конфиг: `config.py` резолвит `/etc/awg-bot/conf`, если каталог
существует (иначе — `./conf` для запуска из исходников). Переопределить —
`AWG_BOT_CONF_DIR`. Аналогично `AWG_BOT_DATA_DIR` для данных, `AWG_BOT_ENV` для env.

### 4b. Что установщик больше не спрашивает — и где это теперь

Вопросов при установке ровно два: токен бота и (одной строкой) файервол.
Остальное живёт в чате, потому что менять его приходится не в первую минуту, а
потом.

- **🖥 Сервер** — адрес сервера, имя в ссылках, DNS клиентов (и переход на свой резолвер, §4c), MTU. Всё это
  уезжает в **новые** ссылки: уже выданные конфиги несут то, с чем их выдали.
  Значения читаются в момент выдачи, а не при старте, поэтому правка
  применяется сразу, без рестарта. Порт, подсеть, интерфейс, версия ядра и
  поколение показываются, но не правятся: их смена — это перевыпуск профилей
  всем, и живёт она в переезде.
- **🛡 Доступ по SSH** — порт SSH (кнопка «Изменить порт», §6b), список
  адресов для входа снаружи, добавление и удаление, включение и выключение
  фильтра. Из чата всё применяется **сразу, без таймера отката**: чат от SSH
  не зависит, и любое действие отменяется той же кнопкой. «Включить фильтр»
  появляется только при заданных адресах — фильтр без адресов открывает SSH
  всем и не фильтрует ничего. NAT клиентов таблица держит всегда, выключение
  фильтра не оставит людей без интернета.

  Таймер отката остался у установщика и CLI (`awg-bot firewall setup`,
  `deny`): там другого пути, кроме терминала, нет. **Подтверждение приходит
  в чат само**: сообщение с кнопками «Вход работает, подтверждаю» и
  «Откатить сейчас» отправляется в момент применения из любого процесса
  (`awgbot/infra/tgsend.py`, обычный POST без aiogram), бот эти кнопки
  обслуживает. Это не украшение: правила могли отрезать именно тот SSH, из
  которого их применяли, и совет «выполни `awg-bot firewall confirm`»
  отправлял бы человека туда, куда он уже не попадёт. Команда осталась как
  запасной путь. Если таймер всё-таки сработал, в чат приходит и это:
  молчаливый откат означал бы, что админ считает файервол включённым, а он
  выключен.
- **Первое устройство** — `awg-bot first-device` печатает ссылку, QR и путь к
  файлу в терминал в любой момент, не только при установке.

### 5a. Горячая конфигурация и экран «⚙️ Настройки»

Часть параметров применяется **на горячую**, без рестарта: правку подхватывает
либо экран настроек в чате, либо ручное редактирование yaml (за `conf/` следит
отдельный вотчдог). Механика — модуль `awgbot/core/settings.py`: все `conf/*.yaml`
держатся в горячем кэше, код читает значения в точке использования через
`settings.get(...)`, а запись из чата идёт через ruamel.yaml (комментарии и
порядок в файле сохраняются). YAML остаётся **единственным источником истины** —
отдельной БД настроек нет.

Экран **⚙️ Настройки** (в админ-меню) правит ходовые параметры кнопками:
уведомления (тихие часы, алерты хоста, события клиентов), параметры подписок
(бонус-квота, пауза, grace), мониторинг, автобэкап, сервис (перезапуск AWG/бота)
и обновления (расписание проверки, уведомления). Сюда вынесены и бывшие кнопки
главного меню «Бэкап», «Обновление бота», «Перезапустить AWG».

Три класса применения:
- **на месте** (лимиты, пауза, grace, тихие часы, пороги алертов) — новое
  значение видно сразу при следующем обращении;
- **расписания планировщика** (частота монитора, автобэкап, проверка обновлений,
  очистка истории) — job перевешивается на лету (`reschedule_job`);
- **инфраструктура/деплой/секреты** (таймзона, docker/сеть, `BOT_TOKEN` и т.п.) —
  в чат-настройки не входят, читаются при старте, меняются на холодную + рестарт.

Ручная правка yaml по-прежнему работает и применяется так же горячо; при
повреждённом файле кэш сохраняет прежнее значение и пишет предупреждение в лог.

## 6a. Аварийный email-выход из приостановки

Опциональная страховка от «запирания в паузе»: если клиент заходит в Telegram
только через этот же VPN, то, поставив подписку на паузу, он теряет доступ и к
боту — и снять паузу сам не может. Email-выход даёт независимый канал: при входе
в паузу клиент получает одноразовый код (8 символов, алфавит без похожих 0/O и
1/l) и, заперевшись, отправляет письмо с этим кодом **в теме** на настроенный
адрес. Бот исходяще опрашивает ящик по IMAP, находит код, снимает паузу,
уведомляет клиента в Telegram и отвечает письмом «Код принят».

Свойства (важно понимать при настройке):

- **Портов на хосте не открывается.** Бот только сам исходит на почтовый сервер
  (IMAP — опрос, SMTP — ответ об успехе), как браузер открывает сайт.
- **`From` письма — не аутентификация** (спуфится): единственный секрет — код,
  известный лишь тому, кто ставил паузу. Тело письма не читается вообще.
- **Невалидный код игнорируется молча**: письмо помечается прочитанным, ответа
  нет — по реакции нельзя понять, существует ли код.
- **Код одноразовый** и живёт только пока активна пауза; снять по почте можно
  только паузу, которую клиент поставил себе сам, — не административную.
- **Интервал опроса — не менее 60 сек**: меньшее значение бот сам откатывает к 60.

**Включение — из чата**: **⚙️ Настройки → ✉️ E-mail → Подключить ящик**. Мастер
спрашивает адрес; для `gmail.com`, `icloud.com`, `yandex.ru` серверы
подставляются сами (и подсказывается, что нужен пароль приложения), для прочих
доменов спрашиваются IMAP/SMTP-серверы и порты; затем пароль — сообщение с ним
бот удаляет сразу после приёма. Перед сохранением бот живьём входит по IMAP и
SMTP; ошибка — ничего не сохранено. Логин и пароль хранятся в БД (она под root,
600, в бэкап уходит только шифрованной), серверы — в `conf/email.yaml`. В
разделе: «Проверить соединение», «Тестовое письмо», «Сменить ящик», «Отключить»
(через подтверждение) и функции на канале — пока одна, аварийный выход из
приостановки, со своим рубильником, адресом для писем с кодом (по умолчанию сам
ящик), интервалом опроса и длиной кода. Всё применяется горячо, без рестарта.

Прежняя схема держала креды в `/etc/awg-bot/env`: при старте бот один раз
переносит их в БД и напоминает удалить строки `EMAIL_RESUME_*` из env.

Помимо email-выхода у паузы есть ещё два выхода: кнопка «Возобновить» у клиента
и «▶️ Вывести из приостановки» в карточке клиента у администратора.

## 6b. Файервол хоста и SSH из туннеля — одна точка

Файервол хоста бота — **одна** nft-таблица `inet awg_bot_guard`, и ведёт её
бот. Раньше на пути SSH-пакета стояло четверо ворот (nft-таблица скрипта,
цепочка iptables `AWGBOT_SSH`, PostUp-страж в conf интерфейса, `Match
Address` в sshd) плюс ufw рядом, и отказ на любых выглядел одинаково. Теперь
разбирать нечего: правило либо есть в таблице, либо его нет.

**Что в таблице** (`/etc/nftables.d/awg-bot-guard.nft`, генерирует бот):

- `input`, политика **drop**: established/related, lo, ICMP, UDP-порты всех
  awg-интерфейсов (`ListenPort` каждого conf в каталоге awg — клиенты, переезд,
  линк до шлюза), DNS с подсетей туннеля, прочие порты из `firewall.open_tcp`
  / `open_udp`, и SSH:
  1. с адресов **устройств админа** из туннеля — accept (set `ssh_tunnel4`,
     бот правит его при создании/удалении устройства и сверяет каждый тик);
  2. с остальной подсети туннеля — drop;
  3. с вашего вайтлиста `firewall.ssh_allow` (IP, CIDR, имя DynDNS — имя бот
     резолвит сам) — accept;
  4. всё прочее на порт SSH — **drop до TCP-рукопожатия**, не до аутентификации.
     Пустой вайтлист означает «SSH открыт всем адресам» (остаются ключи) — бот
     предупредит об этом на старте.
- `forward` (host-режим), политика drop: established, пир-к-пиру внутри
  awg-интерфейсов только устройствам админа (остальным клиентам друг до друга
  и до шлюза пути нет), подсети туннеля в обе стороны. Блокировки устройств
  (`DROP` в iptables FORWARD) и отказ DoT работают поверх: drop в любой
  таблице окончателен. Трафик пир → пир не маскарадится (исключение ставит
  `routing-host-setup.sh`), иначе шлюз видел бы всех пиров адресом сервера.

Таблицу грузит `nftables.service` до подъёма интерфейсов — fail-closed с
загрузки, без PostUp-строк. Применение всегда атомарное (`table; delete
table; table {…}` одним `nft -f`): момента с полупустой цепочкой нет. Сверка
по тику дешёвая: текст желаемой таблицы сравнивается с файлом, живой set —
одним `nft -j list set`.

**Включение** — не правкой conf, а мастером с таймером отката:

```
awg-bot firewall setup            # вайтлист, порты, показ таблицы, применение
# → НОВЫМ подключением проверить вход, затем:
awg-bot firewall confirm --disable-ufw
```

Без `confirm` через три минуты таблица снимается и `firewall.enabled`
возвращается в `false` — самозапереться нельзя. `confirm --disable-ufw`
выключает ufw: второй владелец правил на тех же портах больше не нужен, а
«accept в одной таблице не отменяет drop в другой» — ровно та ловушка, из-за
которой ворот и стало четверо. Прочее: `status` (расхождения файла, ядра и
conf), `allow <ip…>` / `deny <ip…>` (вайтлист; `deny` — с таймером отката),
`apply` (после правки conf руками), `off`.

После включения бот **сам снимает старые ворота**: PostUp-строки с
`AWGBOT_SSH` из conf интерфейсов и цепочку `AWGBOT_SSH` с джампами. `Match
Address` в sshd_config уберите руками — адресную фильтрацию делает пакетный
фильтр, sshd оставляет ключи, `PermitRootLogin prohibit-password`, `AllowUsers`.

> **Не сводите вайтлист к адресу туннеля.** Туннель живёт на этом же сервере:
> упал awg, слетел конфиг — и чинить неоткуда. Внешние белые IP обязательны;
> нет статики — DynamicDNS-имя в `ssh_allow`.

> **Не делайте `systemctl restart nftables`** на живом хосте: стандартный
> `/etc/nftables.conf` начинается с `flush ruleset` и снесёт правила iptables
> (маршрутизация, блокировки) до ближайшего реассерта. Наша таблица применяется
> только `awg-bot firewall apply` / ботом, без перезапуска сервиса.

**Docker-режим** (рудимент): хост видит пиров с bridge-адреса контейнера и
различить их не может, поэтому SSH из туннеля там решается по bridge-подсети
целиком, а `forward` остаётся docker'у.

**Куда ходить из туннеля:** на адрес awg-интерфейса хоста (у нас `10.9.1.0`).
На внешний IP хоста из-под туннеля зайти нельзя — адрес эндпоинта всегда
маршрутизируется мимо туннеля (иначе не работал бы сам хендшейк).

**Порт** — `conf/app.yaml` → `network.ssh_port`, должен совпадать с
`/etc/ssh/sshd_config`; смена порта в conf пересобирает таблицу без рестарта.
Менять порт лучше кнопкой **«🅿️ Изменить порт»** в разделе «Доступ по SSH»:
она проверяет, что порт свободен (`ss`; занятый — отказ с именем процесса),
пишет `Port` в `sshd_config` (и
гасит лишние `Port` в `sshd_config.d/`, на socket-активированном sshd —
drop-in к `ssh.socket`), проверяет `sshd -t` и `sshd -T`, обновляет conf и
перезапускает sshd; не принял — файлы и conf возвращаются как были. Текущие
SSH-сеансы рестарт не рвёт; вход проверяйте новым подключением. Файервол
провайдера (security group) бот не видит — новый порт там открывайте сами.

## 6c. Условная маршрутизация («Доступ к РФ-сервисам»)

Российские сервисы часто не пускают с зарубежного адреса. Функция даёт клиенту
**российский IP для всего, кроме заблокированного**: трафик уходит через шлюз с
российским адресом, а то, что перечислено в списке «нужна заграница», продолжает
идти обычным путём через этот сервер.

**Конфиги устройств при этом не меняются.** Режим — состояние на сервере, а не
отдельные учётные данные: выданные ссылки и QR остаются валидными, переключение
мгновенно и обратимо.

### Что нужно помимо бота

Отдельная машина с российским адресом (шлюз) и туннель до неё. Всё остальное
ставится скриптами из `install/`.

### Порядок развёртывания

Всё делается **из бота**, в три нажатия и две команды на машине-шлюзе.

1. **⚙️ Настройки → 🇷🇺 Условная маршрутизация → 🚀 Развернуть.** Бот ставит
   `dnsmasq`, настраивает перехват `:53`, NAT и маршруты клиентов, поднимает
   линк-туннель, закрепляет всё от перезагрузки и вписывает интерфейс линка в
   конфиг. Занимает до минуты, после чего бот перезапускается: имя интерфейса
   читается при старте. Любой шаг не отработал — не применяется ничего
   наполовину, причина показывается текстом.
2. **🛰 Назначить шлюз → ➕ Новое устройство.** Первый раз бот спросит токен бота
   шлюза (второй бот от @BotFather — домашняя машина не должна знать токен
   этого) и запомнит его. Дальше он создаёт устройство «Шлюз», меняет ключи
   линка и выдаёт **файл первого применения**.
3. **Одна команда со своей машины** — копирует файл и сразу ставит агента:

```bash
scp awg-gw-bundle.sh root@ШЛЮЗ:/root/ && \
  ssh -t root@ШЛЮЗ 'sudo sh /root/awg-gw-bundle.sh --install'
```

Установка на шлюзе вопросов не задаёт, поэтому её незачем отделять от
копирования. `ssh -t` нужен для пароля sudo; под root пароль не спросят вовсе.
Поставка агента едет **внутри файла** (основной бот собирает её из своей
установки, версия та же): шлюз стоит в России, GitHub там без туннеля
недоступен, а туннель этим файлом и ставится — в интернет за поставкой шлюз
не ходит. Нужны только репозитории системы (apt) и PyPI. Файл ~1,5 МБ.

Установка агента **не задаёт ни одного вопроса**: токен агента и `ADMIN_ID`
лежат внутри файла, установщик находит его в `/root` сам (или берёт путь из
`--bundle`), применяет (аплинк, линк, обвязка, файервол шлюза) и только потом
ставит агента — тому нужен уже поднятый аплинк, иначе Telegram недоступен.
Нет файла — установка честно останавливается и печатает обе команды.

**Скрипты остаются** для ручных сценариев и для реассерта по ребуту:
`routing-host-setup.sh`, `routing-link-setup.sh`. Каждый по умолчанию
**показывает план и ничего не делает**; `--apply` применяет, `--rollback`
снимает. Повторный запуск ничего не дублирует.

**Про бандл.** Это один самодостаточный файл: внутри и скрипт настройки шлюза, и
конфиг линка с приватным ключом. Раньше на шлюз несли два файла по отдельности —
скрипт и конфиг, — и забыть один из двух было делом времени. Файл секретный
(права 600), после установки его на шлюзе стоит удалить.

Пересобрать бандл позже — `sudo awg-bot gw-bundle`. **Ключи при этом не меняются**:
он собирается из уже выданного конфига, поэтому работающий шлюз от пересборки не
отваливается. Смена ключей — режим `--rekey` того же скрипта; его зовёт сам бот
при смене и снятии шлюза, руками он не нужен. После смены ключей прежняя машина
теряет линк по построению, а новой нужен файл первого применения.

**Версия контракта линка** штампуется в шапку бандла и в конфиг на шлюзе. Сверять
её автоматически некому и не нужно: набор обфускации симметричен, и если стороны
разъедутся, хендшейка не будет вовсе — линк ляжет, а бот сообщит об этом своим
тиком живости. Штамп нужен человеку, чтобы на шлюзе было видно, чем его ставили.

Списки бот качает и обновляет **сам** — при старте и раз в несколько часов;
источники зашиты в код. Руками ничего запускать не нужно, править конфиг тоже.

**Как это работает.** На домашний шлюз уходят только те сервисы, что перечислены
в списках — банки, маркетплейсы, госуслуги: им нужен российский адрес. Всё
остальное выходит зарубежным адресом обычным путём, домашний канал не нагружая.

Списки бот ведёт сам. Если какой-то российский сервис в них не попал и ругается
на адрес — пользователь добавляет его в свой список исключений, в том же разделе
«Доступ к РФ-сервисам».

### Как пользоваться

- **Админ:** «⚙️ Настройки → 🇷🇺 Условная маршрутизация» — общий выключатель и
  список профилей, которым функция доступна. Единственное место, где раздаётся
  право.
- **Клиент:** в меню появляется «Доступ к РФ-сервисам» — там переключатель и
  личный список исключений (сайты, которым нужна заграница). Режим действует на
  **все** устройства профиля сразу.
- У админа доступ есть всегда, отдельного разрешения ему не требуется.

### Если не работает

Бот проверяет окружение сам и не поднимает функцию, если чего-то не хватает, —
причина пишется в журнал и приходит админу при старте:

```bash
journalctl -u awg-bot -n 50 | grep -i routing
```

Диагностика по цепочке (каждый шаг должен быть непустым):

```bash
ls /var/lib/awg-bot/routing-*.lst           # списки скачаны?
ipset list rt_src_u<ID>                     # адрес устройства попал в набор?
iptables -t mangle -L AWGBOT_RT -n -v       # счётчики маркировки растут?
awg show <интерфейс-линка>                  # есть хендшейк со шлюзом?
```

Если шлюз недоступен, бот сам снимает маркировку: сайты открываются с
зарубежного адреса, но связь не пропадает. Админу приходит уведомление.

### Выключение

Тумблером в настройках — мгновенно и для всех, пользовательские настройки при
этом сохраняются. Полностью убрать обвяз: `--rollback` у каждого скрипта.

## 6e. Переданные устройства и роль «гость»

Подробно — `docs/guest-role.md`. Коротко:

- У устройства две стороны: **владелец** (профиль, чьи это слот, квота,
  подписка и разрешение РФ-доступа) и **держатель** (кто управляет им через
  бота). Своё устройство — держатель и владелец совпадают. «➕ Добавить →
  👥 Другу» или «👤 Передать другу» в карточке выдаёт код `F…`; тот, кто его
  активирует, становится держателем. Слот у держателя не занимается.
- Держатель без своей подписки — **гость**: профиль `kind = guest`, имя из
  Telegram, свой главный экран (статус сервера, подписка владельца, «Мои
  устройства», выдача, помощь, при фиче у владельца — РФ-доступ). Без
  устройств профиль не закрывается — список адресов и история остаются, новый
  код можно принять от любого владельца. Держать устройства может и обычный
  клиент: они видны в его «Моих устройствах» после своих, с пометкой «от кого».
- **Один даритель:** держатель принимает устройства только от одного
  владельца; код от другого отбивается, сам код не сгорает. Перепривязка
  админом переданного устройства к другому профилю снимает держателя и
  перевыпускает ключи: доступ у него пропадает, уведомление уходит.
- Держатель может подключить, заблокировать и удалить переданное устройство
  (удаление — с предупреждением, что новое он создать не сможет; владельцу
  уходит уведомление). Владелец видит переданное с пометкой «передано … и
  управляется им», может переименовать и удалить (держателю уходит
  уведомление).
- **РФ-доступ:** субъект — держатель (свои тумблеры и список адресов),
  разрешение — владельца устройства. Выдача/отзыв разрешения владельцу
  уведомляет и держателей его устройств; переданные устройства у владельца в
  разделе видны без переключателя.
- Гость, активировавший клиентский инвайт, становится владельцем: все
  переданные ему устройства переходят в новый профиль независимо от лимита
  («3 из 2» честно), даритель получает слоты обратно и одно уведомление.
- Прежние «друзья» (v2.19 и раньше) при обновлении становятся гостями
  автоматически, имя подтягивается из Telegram при первом сообщении.

## 6d. Агент на шлюзе (роль `gateway`)

Шлюз условной маршрутизации (домашняя машина с российским адресом) получает
**собственного бота** — тот же код, та же поставка, `role: "gateway"` в
`app.yaml`. Это не второй проект, а вторая роль первого: notifier, тихие часы,
настройки, самообновление — общие. Клиентской механики у роли нет вовсе.

**Архитектурный принцип:** между хостами НЕТ канала управления. Агент — свой
Telegram-бот со своим токеном, малина не открывает ни одного входящего порта;
root-ключ домашней машины никогда не лежит на VPS. Цена: без ВПС агент нем (см.
ограничение ниже).

### Установка

```bash
# на шлюзе; файл первого применения уже скопирован в /root — вопросов не будет,
# поставка агента внутри файла, GitHub с шлюза не нужен
sudo sh /root/awg-gw-bundle.sh --install
```

Токен бота шлюза спрашивает ОСНОВНОЙ бот — один раз, при «Новое устройство», — и
запоминает: переустановишь машину, файл выпустится заново без похода в
@BotFather. Внутри файла он и едет, вместе с `ADMIN_ID`, ключами линка и
конфигом аплинка. Строки с секретами лежат в файле ПОСЛЕ `exec`: при запуске
бандла они не исполняются, это данные для установщика.

Установщик не задаёт вопросов вовсе: секреты приезжают в файле первого
применения. Подсеть клиентов ВПС он не спрашивает — она приезжает в
конфигурации шлюза и закрепляется в юните обвязки, агент читает её оттуда
(`gateway.client_subnet` в `app.yaml` остаётся как ручное переопределение).
Юнит тот же — `awg-bot.service`; конфиг — `/etc/awg-bot/conf/app.yaml`,
секция `gateway:`.

На шлюзе установщик тоже ставит ядро версии манифеста (§4a): модуль и тулзы
на обоих хостах обязаны быть одного поколения, иначе линк не поднимется.

**Обвязка и файервол шлюза — одна nft-таблица `inet awg_gw_guard`.** Её
ставит `routing-gw-setup.sh` из конфигурации шлюза (бандла) и перевыставляет
юнит `awg-link-gw.service` при каждой загрузке, до подъёма линка. В ней всё,
что раньше было россыпью iptables: MASQUERADE клиентов и линка в WAN, изоляция
клиентов от приватных сетей (DROP выше ACCEPT), метки Telegram и GitHub `0x1`
для самого агента (шлюз стоит там, где оба без туннеля недоступны: до Telegram
он достаёт по метке через свой туннель, с GitHub так же обновляется; списки
сетей — в скрипте и в агенте, тот проверяет их по таблице; маскарад в аплинк —
тоже здесь: без него локальный пакет уходит в туннель с домашним адресом, и
ВПС его отбрасывает) и **защита самой
машины от туннеля**: с адресов туннеля на
шлюз пускаются только ВПС по линку (SSH, ICMP) и **устройства админа** — им
открыто всё, и сам шлюз, и домашняя сеть за ним (NAS, OMV, торрент-клиент).
Их список бот ВПС вшивает в бандл (`ADMIN_IPS`) и напоминает о перевыпуске,
когда состав меняется. Прочим клиентам с туннеля на порты шлюза — drop ещё до
рукопожатия, в домашнюю сеть — изоляция. Политика INPUT для домашней сети не
меняется. Чтобы админ доставал до домашней сети, ВПС должен знать её адрес:
`routing.home_subnets` в `conf/app.yaml` основного бота, бот держит маршрут в
линк вместе с остальной обвязкой. Пир-к-пиру на ВПС тоже только устройствам
админа: остальные клиенты друг до друга и до шлюза по туннелю не достают.

На шлюзе: `awg-bot firewall status` (таблица, устройства админа, политика
чужого FORWARD), `allow`/`deny <ip>` (доверенные адреса сверх бандла, файл
`/etc/awg-gw/firewall.env`), `apply` (перевыставить). Агент проверяет таблицу
одним `nft -j list table` каждый тик и при пропаже перевыставляет её рестартом
юнита. Прежние правила iptables (`AWGLINK_FWD`, MASQUERADE, метки) скрипт
снимает сам; строки с метками в `PostUp` вашего `awg0.conf` можно убрать, они
теперь дублируют таблицу. Сессия агента прибита к IPv4 (`gateway.ipv4_only`):
туннель v4, а резолвер отдаёт API сначала AAAA.

### Шлюзовое устройство

Малина является устройством админа в основном боте: её клиентский туннель к
ВПС (аплинк, обычно `awg0`) выпущен ботом, как любое устройство. Пометка
«это шлюз» ставится на это устройство, и с ней:

- 🛰 в списках, в онлайне и в потреблении, **шлюз всегда первой строкой**, в
  счёт «онлайн N устройств» не входит;
- не считается в лимите устройств и в трафике профиля (через него идёт весь
  РФ-трафик клиентов), лимит самого устройства не действует;
- нельзя заблокировать (никакой причиной), удалить, передать, отдать другу,
  выдать ссылку, QR или файл; карточка: имя, «⚙️ Конфигурация шлюза» (та же
  кнопка, что в настройках) и «🛑 Не шлюз?».

**Как назначается шлюз.** Владение — через ключи линка, без токенов и
подтверждений в обычном пути. Раздел «Условная маршрутизация» без шлюза
показывает «🛰 Назначить шлюз», с одним шлюзом — его состояние одной строкой
(🟢 работает / ⏳ конфигурация выпущена, жду хендшейка / 🔴 не отвечает),
кнопку «🛰 Шлюз: имя» (карточка слота: «⚙️ Конфигурация шлюза», «🔁 Заменить
устройство», «🛑 Снять шлюз», домашние подсети, подпись, галочка
предпочтительного, «📡 Пинг») и «➕ Резервный шлюз». Назначение и замена — из
двух вариантов, и оба идут **полным путём**: ключи линка слота новые, токен
агента (один раз на слот), открытый файл первого применения и инструкция:

- **из моих устройств** — устройство админа, уже созданное в боте (оно линка
  не знает, поэтому ключи линка выпускаются заново; прежняя машина слота, если
  была, теряет линк по построению, ей ничего сообщать не нужно);
- **новое устройство** — бот создаёт устройство «Шлюз» в профиле админа, выпускает
  новые ключи линка и отдаёт **открытый файл первого применения**. Внутри
  ключи (тот же уровень доверия, что у ссылок vpn://), поэтому он ровно один
  раз применяется на машине руками: `sudo sh awg-gw-bundle.sh`; скрипт ставит
  аплинк из бандла (чистая машина без аплинков), линк, обвязку и юнит, после
  этого бот шлюза появляется в чате, и дальше всё через него. Файл после
  применения удалить.

«🛑 Снять шлюз» (и «🛑 Не шлюз?» в карточке) снимает слот, меняет ключи
линка и выключает условную маршрутизацию до нового назначения; никаких
`release`-токенов старой машине. Финал переезда профилей с назначенным шлюзом
сразу выдаёт конфигурацию для двойника.

Агент после применения отвечает человеческим итогом из статуса скрипта
(«Аплинк обновлён и поднят, линк поднят, шлюз подтверждён»), хвост вывода
показывается только при отказе. Запасной путь остался один: если шлюз в
основном боте не назначен, агент присылает подписанный токен `GW1:…` с
кнопкой «Скрыть», его пересылают основному боту, тот находит устройство по
ключу аплинка, назначает и выпускает конфигурацию. При назначенном другом
шлюзе токен отвергается: менять шлюз — только «🔁 Сменить шлюз». Токен
подписан ключом линка (общий секрет сторон, им же шифруется бандл): чужой
или искажённый текст ничего не пометит; повтор того же токена отвергается.
Шлюзом может быть только устройство профиля админа.

**Конфиг аплинка едет в бандле.** У помеченного шлюза бандл несёт его ключ и
клиентский конфиг в форме для шлюза: без DNS и с `Table = off`, PostUp с
правилом «метка → таблица 100» дописывает скрипт. Скрипт ставит его только
машине с тем же ключом (или со старым ключом пары в окне переезда), подменяя
рукописный `awg0.conf` стандартным без потери: те же ключи, те же PostUp.
Переезд профилей поэтому не требует ручной правки шлюза: двойник шлюза
получает флаг на финале, а новый конфиг приезжает файлом сразу. Машина с
ЧУЖИМ аплинком (ключ не совпал ни с текущим, ни со старым ключом пары) шлюзом
не становится и линк не поднимает. Ключ `gateway.uplink_interface` в conf
агента задаёт аплинк явно; по умолчанию он определяется по хосту `Endpoint`
линка.

### Резервный шлюз (несколько слотов)

С v2.24.0 шлюзов может быть два (`routing.gateways_max`): один несёт трафик,
второй ждёт в резерве, оба линка подняты постоянно и меряются каждый такт
живости (docs/gateway-failover.md). Второй шлюз — право, не обязанность: с
одним слотом всё работает как прежде.

- **Добавить:** ⚙️ Настройки → 🇷🇺 Условная маршрутизация → «➕ Резервный
  шлюз» → из моих устройств или новое устройство. Для второго слота на ВПС
  поднимается свой линк (`awglink2`, порт `routing.link_ports[1]`, по
  умолчанию 8443; открывается в файерволе хоста сам), у второго агента —
  **свой бот и свой токен** (спрашивается один раз на слот). Файл первого
  применения — `awg-gw-bundle-awglink2.sh`, ставится той же одной командой.
- **Автомат:** в скользящем окне последних `routing.failover.window_samples`
  (10 замеров ≈ 5 мин) доступность ниже `min_availability` (50 %),
  то есть пятый неуспешный замер, подряд или вразнобой, — и резерв три такта
  проходит → трафик перекладывается на резерв одной командой `ip route
  replace` сразу, на пятом неуспешном; письмо админу — «переключён».
  Неудачи старше пяти минут выпадают из окна и не считаются. То же окно
  гасит маркировку, когда резерва нет, и рисует статусы «не отвечает N мин»;
  стрика «плохих подряд» больше нет. Оживший
  прежний шлюз **остаётся в резерве** (каждое переключение меняет исходящий
  адрес и рвёт сессии в банках). Второе автоматическое переключение раньше
  `routing.failover.min_interval_minutes` не делается — гашение, как без
  резерва. Резерв, молчащий всё окно, — письмо без звука. Тумблер
  «🔁 Автопереключение» — в списке шлюзов. Такт зонда, ширина окна, порог и
  автопереключение — ⚙️ Настройки → Условная маршрутизация → «📡 Мониторинг
  и резервирование». Письмо «переехали на резерв» без звука, критичны только
  отказы без резерва.
- **Руками, в обе стороны:** карточка слота → «▶️ Переключить трафик сюда»
  (для обслуживания дома: переложить, работать, переложить обратно).
- **Предпочтительный** (галочка в карточке слота, ⭐ в списке) берёт трафик
  при **холодном старте** — когда перезагружался сам ВПС (сдвинулся момент
  загрузки хоста). Перезапуск одного бота активного не меняет.
  Предпочтительный не отвечает на старте → сохранённый, иначе любой
  отвечающий.
- **Пинг с ВПС до шлюза** («Пинг с AWG-SRV: 43 мс», ICMP по линку; кэш
  сутки, заполняется при первом открытии экрана, снимается при отвале хоста,
  кнопка «📡 Пинг» меряет заново) и **внешний IP шлюза** (эндпоинт пира линка
  с последнего хендшейка, читается живьём) в карточках слота и
  устройства-шлюза.
- Файл первого применения удаляет себя после успешного применения; повторный
  запуск установщика с `--role gateway` на машине с агентом не задаёт
  вопросов — применяет файл и перезапускает агента.
- **Домашние подсети** задаются в карточке слота и ведут в его линк
  (`routing.home_subnets` в app.yaml читается один раз при переносе в слот 1).
- Порт линка меняется на ВПС правкой `ListenPort` в `awglink.conf` и
  перезапуском `awg-link@awglink` (реассерт переподнимает линк, если порт в
  ядре разошёлся с конфигом); при следующем старте бот подхватит порт в слот,
  откроет его в файерволе и напомнит перевыпустить конфигурацию шлюза.
- Юнит линка — шаблон `awg-link@<интерфейс>.service`; прежний
  `awg-link.service` переезжает на него сам при первом старте бота после
  обновления. `awg-bot gw-bundle --link awglink2` — бандл второго слота.

### Что агент видит и о чём алертит

Панель — зеркало панели основного бота: «🛰 РФ-шлюз (hostname)», сервер и
аптайм машины, линк до ВПС (возраст хендшейка; имя ВПС приезжает в
конфигурации шлюза, переопределяется `gateway.server_name`), железо (CPU и
температура, RAM без свопа и свободно, диск со свободным местом и вердиктом
SMART, если корень не на SD-карте, питание Pi), строка «Монитор здоровья» и
потребление линка за календарный месяц (копится по дельтам счётчиков, рестарт
интерфейса не обнуляет). Панель по /start и «К панели» рисуется из снимка
последнего тика монитора — ноль проб, мгновенно; строка «Обновлено …» говорит,
насколько он свеж. «🔄 Обновить» ходит по пробам живьём.

В мониторе здоровья — **выход наружу**: TCP-проба через домашний канал к российскому и
зарубежному адресу с временем ответа; без неё здоровье шлюза не подтверждало,
что интернет за ним есть.

Алерты с гистерезисом: мёртвый линк (два тика; громкость — настройка), выход
наружу, поломка обвязки, ядро без модуля, недонапряжение, перегрев, CPU/RAM/диск
по порогам из «Уведомлений». «Не смог посмотреть» — третье состояние, не норма
и не отказ. Тик монитора и все задачи, которые ходят в сеть по расписанию
(проба наружу, живость шлюза на ВПС, проверка обновлений, списки), идут с
**джиттером**: строго периодический запрос — маячок для поведенческого анализа.

Оба бота после перезагрузки хоста шлют «⚠️ Хост … был перезагружен. ✅ Запуск …
успешен» — по смене boot_id ядра, а не по аптайму, поэтому рестарт сервиса за
перезагрузку не считается.

### Кнопки

- **🌡 Монитор здоровья** — все проверки строками (обвязка, маршрут к Telegram,
  линк, ядра) плюс справка: модуль awg с `srcversion`, загружаемые ядра,
  история питания с загрузки.
- **🔧 Мастер восстановления** — через подтверждение: юнит шлюза переставит
  правила и переподнимет линк (РФ-доступ у всех оборвётся на секунды).
- **⚙️ Настройки**: **🔔 Уведомления** (тихие часы, пороги CPU/RAM/диска/
  температуры, «E-mail при недоступности Telegram» — только критичные алерты),
  **✉️ E-mail** (ящик приезжает в конфигурации шлюза с ВПС, чтобы не вводить его
  дважды; можно подключить и руками — тот же мастер, что у основного; бэкап на
  почту — как у основного), **📊 Мониторинг** (частота опроса, стрик, громкость и порог
  простоя линка), **💾 Резервное копирование** (день и час автобэкапа, «создать
  сейчас»: один архив — БД агента, все conf, env и все конфиги awg-интерфейсов —
  только шифрованно, парольная фраза в «🔐 Шифрование»);
  **🔄 Обслуживание**: «🔁 Перезапустить AWG» (down/up линка) и
  «🔁 Перезапустить бота» (агент перезапускается вне своего cgroup, обещание
  «вернётся через несколько секунд» исполняет новый процесс — как у основного);
  **⬆️ Обновления бота** — версия, расписание, тумблер уведомлений, ручная
  проверка; механизм тот же, что у основного бота (§9a).
- **Конфигурация шлюза файлом**: на ВПС «Условная маршрутизация» →
  «⚙️ Конфигурация шлюза» → экран «что произойдёт» → файл приходит админу →
  переслать боту шлюза → «Применить». Файл читается только ботом шлюза: ключ
  выводится из приватного ключа линка — общего секрета обеих сторон, который
  через Telegram не ходил никогда. Первая конфигурация (секрета ещё нет) едет
  ногами, как и вся первая установка.

### Ограничения и красная линия

- **Без ВПС агент нем**: Telegram недостижим иначе как через туннель. Взаимный
  контроль остаётся односторонним — зонд живости ВПС-бота видит шлюз.
- **Обновление ядра AWG кнопкой не делается**: ядро бывает обратно
  несовместимо, каждое обновление требует чтения коммитов — ручная процедура
  (`docs/ROADMAP.md` §5). Агент показывает версию и покрытие ядер.
- **Терминала в боте нет и не будет**: произвольная команда из Telegram — root
  домашней машины ценой уведённой сессии. SSH на шлюз остаётся резервом.

## 7. Секреты (`/etc/awg-bot/env`)

Файл `600`, только чувствительные значения. Обязательные:

| Ключ | Значение |
|------|----------|
| `BOT_TOKEN` | Токен бота от @BotFather. |
| `ADMIN_ID` | Telegram ID администратора (число; узнать у @userinfobot). |

Секретов почты и шифрования бэкапов в env больше нет — оба задаются из чата и
хранятся в БД:

- **шифрование бэкапов** — **💾 Резервное копирование → 🔐 Шифрование**: парольная
  фраза, бот принимает её сообщением дважды, удаляет сообщения и никогда не
  показывает обратно; без фразы копии уходят открытыми, а по почте не уходят
  вовсе. Восстановление на другом хосте — `restore_backup.py` с той же фразой;
- **почта** — **✉️ E-mail** (§6a).

`BACKUP_KEY`/`BACKUP_PASSPHRASE` и `EMAIL_RESUME_LOGIN`/`EMAIL_RESUME_PASSWORD`
в env бот больше не читает (их переносили в БД до v2.10.0 — минимальной
поддерживаемой версии); если строки остались — просто удалите.

## 8. systemd и пути

Установщик генерирует `/etc/systemd/system/awg-bot.service`:

```ini
[Service]
User=root
WorkingDirectory=/opt/awg-bot
EnvironmentFile=/etc/awg-bot/env
Environment=AWG_BOT_CONF_DIR=/etc/awg-bot/conf
Environment=AWG_BOT_DATA_DIR=/var/lib/awg-bot
ExecStart=/opt/awg-bot/venv/bin/python -m awgbot
Restart=on-failure
```

Точка входа — пакет `awgbot` (`WorkingDirectory` = каталог с `awgbot/`). Форграунд
для отладки — `./run.sh` (тот же `python -m awgbot`, без systemd).

Раскладка на диске:

| Путь | Что |
|------|-----|
| `/opt/awg-bot` | Код + `venv`. Перезаписывается при `update`. |
| `/etc/awg-bot/conf` | yaml-конфиг. Правится руками, `update` не трогает. |
| `/etc/awg-bot/env` | Секреты (`600`). `update` не трогает. |
| `/var/lib/awg-bot` | `bot.db` + `backups/`. **Не терять** — там приватные ключи bot-устройств. |

Управление: `systemctl {status,restart,stop} awg-bot`, логи `journalctl -u awg-bot -f`.

## 9. Обновление и удаление

```bash
sudo awg-bot update                     # архив awg-bot-update.tgz рядом
sudo awg-bot update ./awg-bot-new.tgz   # или явный путь
```

`update` останавливает сервис, заменяет код и зависимости из архива,
переустанавливает юнит, **не трогая** `conf`/`env`/данные (если явно не
согласиться на их удаление), валидирует конфиг и перезапускает. Работает
благодаря разнесению код↔конфиг по разным каталогам.

Обновление идёт в две половины: старый скрипт распаковывает код и через `exec`
передаёт управление новому (`__post_update`), который уже ставит venv, юнит и
досевает конфиг. Иначе эти шаги выполнялись бы функциями, разобранными из
СТАРОГО файла, и правка в них не могла бы применить сама себя — доехала бы до
сервера и промолчала ещё одно обновление.

```bash
sudo awg-bot uninstall                  # снять сервис
```

Снимает и отключает сервис, удаляет юнит. Каталог кода, `/etc/awg-bot` (секреты)
и `/var/lib/awg-bot` (БД!) удаляются **только по явному подтверждению** — по
умолчанию сохраняются.

### 9a. Автообновление из GitHub-релизов

Бот сам следит за новыми версиями в **публичном** релиз-репо
(`justSunny12/awg-bot`) и умеет обновляться по кнопке. Токены/секреты не нужны —
релизы и ассеты качаются анонимно; sha256 берётся из `assets[].digest` (GitHub
считает его сам).

Как работает: по расписанию (по умолчанию раз в сутки в 10:00 в TZ бота;
периодичность настраивается — см. ниже) и при каждом старте бот
смотрит список релизов, выбирает **цель** — последний релиз новее установленной
версии (`awgbot/__version__.py`) — и, если она есть, шлёт админу уведомление с
changelog этой версии (тело релиза в сворачиваемой цитате) и кнопками
**Обновить / Скрыть / Не уведомлять**. Промежуточные версии перепрыгиваются:
ядро прибито к поставке, миграции БД идемпотентны, conf досеивается — цепочка
ступеней давала бы лишние сборки ядра и лишние переезды профилей. Пропущенные
версии перечислены в уведомлении ссылками на их страницы релизов — changelog
не теряется. Уведомление о каждой цели — ровно
один раз (дедуп по тегу в БД). «Обновить» скачивает ассет `awg-bot.tgz` цели,
сверяет sha256 и запускает `awg-bot update` отдельным транзиентным юнитом
(`systemd-run`), чтобы апдейтер пережил остановку сервиса; после рестарта
проверка повторяется. «Скрыть» убирает сообщение; «Не уведомлять» глушит
автопроверку (и по расписанию, и стартовую) — при этом ручная проверка в
**⚙️ Настройки → Обновления бота** остаётся живой и всегда показывает цель.

**Адресат и обязательная ступень — одной строкой на роль** в теле релиза:
`#requires_main_X.Y.Z` (основной бот), `#requires_gw_X.Y.Z` (агент шлюза).
Есть строка — релиз этой роли адресован; X.Y.Z — минимум, с которого на него
прыгают напрямую: хост ниже сначала обновляется на X.Y.Z (ближайший релиз
своей роли не ниже неё), потом дальше; у ступени может быть своя ступень. Так
у проекта появляется **минимальная поддерживаемая версия** — с v2.18.0 это
**v2.10.0** (манифест ядра, файл состояния, единый архив): всё старше проходит
через неё и получает там свои миграции, а код новее держит шимы совместимости
только для v2.10.0+. Идёт переезд профилей — цель не выше его поколения
(релизы дальше не рассматриваются; экран «Обновления» объясняет, чего ждём).

Каждая роль берёт среди релизов новее установленного **последний со своей
строкой**, чужие не в счёт и в списке пропущенных не показываются: агент на
2.4.5 при релизах 2.4.6 (только `#requires_main_…`) и 2.4.7 (`#requires_gw_…`)
идёт на 2.4.7. Установленные версии ролей поэтому расходятся — это норма,
поставка едет целиком. Прежние хэштеги `#main_bot` / `#gw_bot` / `#all_bots`
(без минимума) остались у старых релизов и читаются; релиз без хэштегов вовсе
считается общим. Ступень, названную минимумом для роли, лучше адресовать этой
роли — иначе она возьмёт ближайший свой релиз не ниже него.

Если установленной версии нет среди тегов релизов (локальная/кастомная сборка) —
обновления **полностью выключены**: ни уведомлений, ни доступного апдейта.

Настройки — `conf/updates.yaml`: `repo`, `asset_name`, `poll_schedule`
(`day`/`week`/`month`/`never`), `poll_hour`/`poll_minute`. Расписание проверки,
уведомления и ручную проверку удобнее менять из **⚙️ Настройки → Обновления
бота** (применяется на горячую). По умолчанию всё преднастроено.

### 9b. Процесс релиза (для мейнтейнера)

Матрица номера версии `X.Y.Z.P`, шапка записи журнала (адресаты
`#requires_main_…` / `#requires_gw_…` только той роли, чей код меняется, затем
`#awg_genN`), требования к сообщениям коммитов и пошаговый порядок выпуска —
в `docs/RELEASING.md`. Публикация публичного релиза = бот у всех предложит
обновиться в течение суток (или сразу после их следующего рестарта).

## 10. Эксплуатация

- **Крипто-материал сервера** (обфускация, ключ сервера, psk, порт) читается
  **live из контейнера** и кэшируется (TTL 10 мин + инвалидация вотчдогом);
  генерация клиентского конфига обычно не трогает docker вообще.
- **Блокировки — в БД.** iptables-DROP'ы эфемерны; после рестарта контейнера бот
  переналагает их автоматически (детект по `StartedAt`).
- **Мутации конфига сериализованы** (`mutation_lock`): параллельные добавления
  устройств не теряют peer'ов и не выдают одинаковые IP.
- **Планировщик навёрстывает пропуски**: месячный сброс и автобэкап догоняются на
  старте, если бот лежал через границу месяца.
- **Вотчдог гибридный**: inotify + страховочная mtime-сетка (~10 сек худшая
  задержка подхвата внешних изменений в приложении Amnezia).
- **Поллер email-выхода** (§6a) стартует только при полностью заданной
  конфигурации (креды + хосты); трафик исходящий, интервал — из
  `poll_interval_sec` (не менее 60 сек).
- **Бэкапы** пишутся автобэкапом (1-го числа) и по кнопке — **одним архивом**:
  `state/bot.db`, `state/conf/*.yaml` (все настройки, из UI и не из UI),
  `state/env`, `awg/<iface>.conf` (конфиги awg-интерфейсов с ключами; у агента —
  все). При заданной парольной фразе архив шифруется целиком (`*.tgz.enc`).
  Внутри — метка `state/backup-meta.json` (роль и время снятия): дата в
  сообщениях берётся из неё, а не из имени файла, и копия основного бота не
  разворачивается на агенте и наоборот. Разворачивает `awg-bot restore <файл>`
  на любом хосте (шифрованный спросит фразу, конфиги интерфейсов — после
  подтверждения) или **сам бот**: пришли файл в чат — он покажет дату копии,
  спросит подтверждение с предупреждением и восстановится через
  `awg-bot restore --yes` вне своего процесса; отчёт пришлёт уже новый процесс.
- **Самопроверка на старте (preflight).** Стоп-факторы (нет записи в data-dir,
  повреждённая БД — `PRAGMA integrity_check`, отвергнутый Bot API токен) валят
  запуск с человекочитаемым сообщением в `journalctl -u awg-bot`. Не-блокирующие
  замечания (мало места на диске, контейнер не отвечает, `awg0.conf` не
  читается, IMAP email-выхода недоступен при активной фиче) приходят админу
  первым сообщением после подъёма. Временная недоступность сети на старте не
  фатальна — поллинг дождётся сети сам.
- **Объявления пользователям.** Кнопка **«📢 Объявление пользователям»** в
  админ-меню: выбор режима, затем профилей-адресатов. *Простое* — текст и/или
  картинки владельцам отмеченных профилей и держателям их устройств, по одному
  разу на человека. *С продлением подписки* — только владельцам: перед
  отправкой подписка каждого продлевается на N дней (1–365; активной — конец +
  N, истёкшей — сегодня + N со снятием блокировки, бессрочной — без продления),
  шапка с датами у каждого своя, лимит текста — за вычетом шапки. Перед
  отправкой — превью и число получателей; после — отчёт о доставке. Тихие часы
  к объявлениям не применяются.
- **Время везде UTC+3.** Сервер живёт в UTC, бот конвертирует.

## 11. Траблшутинг

| Симптом | Причина / что делать |
|---------|----------------------|
| При старте: `Не заданы обязательные параметры конфига: …` | Впишите указанные ключи в `/etc/awg-bot/conf` (это и есть адрес ошибки) и перезапустите. |
| При старте: `Не заданы обязательные секреты: …` | Заполните `/etc/awg-bot/env` (`BOT_TOKEN`, `ADMIN_ID`). |
| Сервис не активен | `journalctl -u awg-bot -e` — смотрите трейс. Частое: недоступен docker/контейнер, неверный `BOT_TOKEN`. |
| В логах нет «Вотчдог подключён…» | inotify не пробил namespace контейнера; страховочная mtime-сетка (~10 сек) всё равно подхватит изменения. |
| Клиент не «онлайн» сразу | «Онлайн» определяется по свежести handshake (`online_handshake_seconds`), значение может отставать до интервала опроса. |
| После `docker restart` контейнера пропали блокировки | Нормально: бот переналожит их на следующем цикле мониторинга (`monitor_minutes`). |
| Письмо с кодом выхода из паузы «не срабатывает» | Код должен быть **в теме** письма (тело не читается); проверьте, что письмо ушло на адрес из предупреждения при постановке на паузу, и подождите интервал опроса (`poll_interval_sec`, мин. 60 сек). В логах ищите `email_resume`. Невалидный/уже использованный код игнорируется молча — это штатно (§6a). |

## 11a. Восстановление доступа и чужие пиры

Здесь три РАЗНЫХ сценария — не путайте их.

### A. Не потерять SSH к серверу

Сервером управляет бот, локально. Приложение Amnezia серверную сторону больше не
трогает, и запасного «входа из приложения» у вас нет — значит SSH остаётся
единственным способом починить хост, если бот встанет.

**Не гейтите SSH адресом туннеля, который даёт этот же сервер.** Это замкнутый
круг: чтобы зайти по SSH, нужен поднятый туннель; чтобы починить туннель, нужен
SSH. Мы уже один раз в него попали — рекомендация «пускать SSH только с адреса
VPN» была ошибкой и отменена.

Правильно: вайтлист **ваших постоянных IP** (дом, офис, выход стороннего VPN);
нет статики — DynamicDNS или аналог. В идеале эти адреса лежат за пределами РФ и
маршрутизируются через ваши туннели туда, чтобы природа управляющего трафика не
выдавала себя. SSH — на нестандартном порту.

Второй независимый канал (консоль хостера, отдельный ключ с другого адреса)
стоит проверить заранее, а не в тот момент, когда он понадобится.

### B. Потерянный клиентский конфиг: восстановление и перевыпуск

Важно различать «извлечь ТОТ ЖЕ ключ» и «восстановить доступ»:

- **Тот же самый приватный ключ уже существующего пира заново получить нельзя** —
  в WireGuard/AWG сервер хранит только публичный ключ клиента; приватный жил лишь
  на самом устройстве в момент генерации. Если устройство, где он лежал, утрачено —
  этот ключ не восстановить ниоткуда.
- **Но с самого́ устройства, которое уже подключается**, свой конфиг вытащить
  можно: приватный ключ лежит в его локальном хранилище (иначе туннель бы не
  поднялся) — экспортируйте свою запись через шаринг в приложении.
- **Восстановить ДОСТУП** (не тот же ключ) — можно всегда через **перевыпуск**:
  в приложении Share → вкладка **Users** показывает клиентов с сервера, позволяет
  отозвать старого и выпустить нового; либо, что удобнее в нашей схеме, — **завести
  устройство заново через бота** (карточка клиента → добавить устройство): бот
  сгенерит новую пару и выдаст конфиг/QR/файл, доступные для повторного просмотра
  сколько угодно раз. Старый пир при этом отзывается/удаляется.

Практический вывод: раздавать и перевыпускать конфиги удобнее через бота — там они
всегда доступны повторно, и не нужно ловить «единственное окно» приложения.

### C. Пиры, созданные мимо бота

Пиров заводит **только бот**. Всё, что появилось в `awg0.conf` иначе, — ручная
правка, восстановление конфига из чужой копии или чужое вмешательство.

Реконсиляция такие записи не усыновляет: пир попадает в **карантин** (профиль
«Устройства без профиля», имя `Неизвестный пир 10.8.1.X`), а админу уходит
тревога — со звуком и мимо тихих часов, потому что это событие безопасности.

Ключа у бота нет и взять его неоткуда — WireGuard хранит приватный ключ только на
самом устройстве. Поэтому выдать по такому пиру ссылку/QR/файл нельзя, передать
другу тоже. Разберитесь, откуда он взялся, и либо привяжите к профилю (трафик
будет считаться, блокировки — работать), либо удалите.

Осиротевшие пиры (пропавшие из живого конфига, при живой записи в БД) бот убирает
сам после порога сверок (`missing_sweeps_threshold`) и сообщает об этом: сам он
так не удаляет — снимает пира и строку разом.

## 12. Ручная установка (для справки)

```bash
mkdir -p /opt/awg-bot && cd /opt/awg-bot   # скопировать сюда проект
python3.12 -m venv venv                    # ЯВНО 3.12 (StrEnum)
./venv/bin/pip install -r requirements.txt
mkdir -p /etc/awg-bot/conf /var/lib/awg-bot
cp conf/*.yaml /etc/awg-bot/conf/          # вписать network.server_host и
                                           # network.server_port (app.yaml)
printf 'BOT_TOKEN=…\nADMIN_ID=…\n' > /etc/awg-bot/env && chmod 600 /etc/awg-bot/env
./venv/bin/python -m awgbot                # проверить форграундом (или ./run.sh)
cp awg-bot.service /etc/systemd/system/ && systemctl daemon-reload
systemctl enable --now awg-bot
```
